# 検索・外部からの流入を増やす計画（2026-09-02）

> 現状の実測は `seo-audit-2026-09.md`。**この文書は「次に何をするか」だけ**を置く。
> 着手前に実物を測り直す（`docs/agents/measuring.md`）。

## 結論

**「他のところ」は、既に書いたもの・配ったものが、全部よそのサイトの中にある、
というところだった。**

江口秋は note.com に**16本の文章を公開している**（2025-04-11 〜 2026-06-15）。
展示にも出ていて、自作の Lightroom プリセットも配っている。**その全部が
note.com の中にあり、akieguchi.com には見出し3本の抜粋しか出ていない。**
書いた文章の検索評価は、いま全部 note.com が受け取っている。

写真の題でもカメラでもなかった理由は単純で、**この人は写真より先に「言葉」を
もう持っていて、それを置く場所だけが自分のサイトに無かった**から。

| 測ったもの | 数 |
|---|---:|
| note の記事 | 16本 |
| note 記事1本の本文（オールドコンデジの回・実測）| 1,067字 |
| 16本の本文の合計（調査での実測）| 約10,875字 |
| note の本文に akieguchi.com へのリンクがある記事 | **0本** |

**記事1本のほうが、写真497枚を並べたページより6倍以上たくさんの言葉を持っている。**

## 重複の扱い（結論を1つに決める）

**note の16本は消さない。自サイトに全文コピーもしない。
これから書く文章は自サイトを本体にして、note には自サイトへのリンクを足すだけにする。**

過去の記事でどうしても自サイトに欲しいもの（コンデジの3本）は、**コピーせず
1本に書き直す。**書き直したものは別の文章なので、重複にならない。

理由。note.com のほうが検索側からの信用が圧倒的に高いので、同じ文章を両方に
置くと、ほぼ確実に note が本物と判断される。そのとき自サイトに残るのは、
1本平均680字の薄いページが16枚だけ。逆に note を消すのは、既にいる読者と
267のスキを捨てる行為で、取り消せない。

## やること（流入への効き目が大きい順）

**効き目の順であって、手をつける順ではない。**着手順は末尾。

### 1. オールドコンデジの記事を1本（効き目 大）

機種ごとに分けず、**Z1・F450・OLYMPUS を1本にまとめた1ページ**にする
（機種ごとに割ると、作例3枚しかないページが2〜3枚できる）。

効く理由。「オールドコンデジ」は検索候補が9件に広がり（おすすめ／作例／
人気ランキング／ixy／秋葉原／nikon／ccd など）、検索結果の1ページ目に個人
サイトと note が半分以上入っている。大手に埋め尽くされていない。しかも
**note でいちばん反応が大きかった記事（スキ41）がこの話題**。

- **オーナー:** 先にコンデジの写真をアップロードする（note 側に29枚ある。
  いまサイトには**0枚**）。カメラ欄に `FinePix Z1` `FinePix F450` を入れる。
  本文600〜1200字。**機種名は見出しではなく本文の中に全部入れる。**
- **コード:** 新しいページの仕組みは作らない。既存のシリーズでそのまま公開できる。

### 2. プリセット配布のページを1本（効き目 大）

「すきぴいろプリセット」を、note の添付ではなく自サイトの1ページにする。

効く理由。**もう完成品が手元にある唯一の案。**「写ルンです風 プリセット 無料
ダウンロード」の日本語の枠は note の個人2本だけで、**自分のドメインのページは
0件＝席が空いている。**「Lightroom プリセット 無料」は検索候補が10枠埋まる語。

- **オーナー:** 適用前/後の作例3組。狙った色と合う光を5〜10行。主要スライダーの
  数値。利用条件1行。**ページの題は商品名にしない**（「すきぴいろプリセット」は
  検索候補0件。入口は「フィルム風」「無料」「Lightroom」の側。商品名は本文の中へ）。
- **コード:** v1 はコード変更ゼロ。既存のシリーズ1本として作れる。
  **ダウンロード先は当面 note の添付URLのまま**（ページが評価を受け取り、
  ファイルは note が配る）。
- **メールアドレスと引き換えにしない。**問い合わせフォームの無料枠が月50件で
  アカウント全体の枠。配布が当たった月ほど、撮影依頼の問い合わせが止まる。

### 3. note の16本に、自サイトへのリンクを1本ずつ（効き目 中・確実）

新しい順位を1つも取りに行かずに効く唯一の案。**既にいる読者を動かす**話なので失敗しない。

- **オーナー:** 記事末尾にリンクを1行。1本2分、全部で30分ほど。送り先は中身に
  合わせる（コンデジ→ギャラリー、中判→石垣島、展示→About、プリセット→配布ページ）。
  **Amazon のリンクは消さない**（収入源。足すだけ）。全記事に同じ定型文を貼らない。
  **本文にリンクが1本も無い10本から先に**貼るほうが効く。
  末尾に `?utm_source=note` を付けると人数を数えられる（解析は設置済み）。
  **このURLは note にだけ貼る**（他所へ転記すると住所が2つに割れる。www と apex で
  一度やったのと同じ事故）。
- **コード:** 無し。

### 4. 中判フィルムの記事を1本（効き目 小）

正直に書く。**検索からの流入はほぼ期待できない。**「中判フィルム」の検索候補は
値段／中古／おすすめ／現像で、**「作例」は一度も出てこない。**買う人の言葉であって
見に来る人の言葉ではない。上位もカメラ屋の中古在庫ページ。

やる理由は2つ。写真が**既にサイトにある**こと（フィルム280枚）。棚が1本だと空に
見えるので、**2本目として一番安い**こと（コード追加ゼロ）。

- **オーナー:** 280枚から67とハッセルを目で選ぶ。**カメラ欄が280枚とも空なので
  絞り込みができない。この選ぶ作業が一番時間を食う。**

## オーナーに決めてほしいこと

1. **コンデジの写真を、ギャラリー本体にも出すか。**
   A1 や A7RV の写真の中に、128MB のカードで撮った低解像度が混ざる。
   「記事のページの中だけに置く」も選べる。**作品の見え方の話なので、オーナーが決める。**
2. **プリセットのファイルを DNG のままにするか。**
   いま note で配っているのは 42.9MB の DNG 1本。**このサイズをサイトに直接置けない**
   （リポジトリと毎回のデプロイに永久に乗る）。`.xmp` なら数十KBで置き場所の問題が消える。

## やらないほうがよいこと

- **写真1枚ごとの題と説明** — 価値はあるが流入の本命ではない。**人は写真の題で検索しない。**
- **カメラ別・レンズ別の一覧ページ** — 写真をカメラ名で並べただけの棚には本人の言葉が
  1行も無い。案1との違いは、**あれは一覧ではなく本人の文章がある記事**だという点。
- **フィルム銘柄ごとの記事** — 相手は専業ブログと大手カメラ店。280枚の銘柄は記憶からしか
  埋められず歯抜けになる。DB の作り変えも要る。払うものと見返りが釣り合わない。
- **展示専用のページを新設** — 「江口秋 写真」も「すちるらいふ」も検索候補0件。
  **作る手間が最大で検索需要が最小。**展示のことは記事として書けば同じ場所に置ける。
- **展覧会情報サイトへの掲載申請** — Tokyo Art Beat は会場が先に登録されている必要があり、
  江口秋は主催者ではなく参加者。ギャラリーの参加作家一覧はリンクが1本も張られていなかった。
- **壁紙・ZINE テンプレートの配布** — 相手は20万点の素材サイトと印刷会社。497枚では桁が足りない。
- **`/journal` のような新しい棚を先に作る** — 1週間前に同じやり方で `/work` を作り、
  7回の修正が必要になった（うち3回は本番だけページが消える事故）。**その `/work` は
  今も中身ゼロのまま生きている。**空の棚をもう1つ増やさない。

## 着手順

### 済み: シリーズの本文を、最初のHTMLに全文入れる（`a2ad7a3`）

上の1・2・4は全部**既存のシリーズの仕組みに乗る。**新しいページの仕組みは要らない。
題・URL用の名前・本文・写真の割り当て・公開の切替は揃っていて、公開すれば
canonical・OGP・JSON-LD・画像サイトマップまで自動で付く。

**穴が1つあった。**作家の言葉（`statement`）が `server.ts` で200字に切られてから
差し込まれ、段落は空のまま渡されていた。**シリーズページに書いた文章は、最初に返す
HTML に先頭200字しか入っていなかった。**残りは JavaScript を実行した後にしか存在しない。

> **正確に言うと。**Google は JavaScript を実行するので、Google には全文が見えていた
> 可能性が高い。**確実に届いていなかったのは、JS を実行しない側**（多くのAI・SNS・
> 小さめの検索）と、最初のHTMLだけを読む経路。**「Google に全く見えていなかった」
> ではない。**それでも、書いた文章が最初のHTMLに入らない状態で記事を増やすのは筋が悪い。

`desc`（検索結果に出る一文）は200字のまま、本文だけ全文を流すようにした。

**本番反映済み**（2026-09-02）。ただし**自分で push したのではない。**同じワークツリーで
並行していた別セッションの push（`4d53d30`）に、祖先として乗って出ていった。
反映後に本番8ページを確認し、どれも200で noscript 本文も正常だった。
シリーズの statement は両方とも空なので、**画面の見た目は変わっていない。**

> **並行作業の注意。**同じワークツリーで2セッションが動くと、**片方の push が
> もう片方の未 push commit を巻き込む。**`git add` をパス指定にしても防げない
> （commit は分けられるが、push は枝ごと出ていく）。commit した時点で
> 「いつ本番へ出てもよい状態」でなければならない。

### 次: 本文の見た目

いま `statement` は改行だけの1つの塊として表示される。見出しも本文中のリンクも入らない。
**なので1本目の記事は600〜800字に抑える。**それより長く書きたくなったら、そのとき直す。

### 棚（`/journal`）は最後

記事が3本たまって、Search Console で実際に検索から人が来ていることを確認してから。
それまでは作らない。
