## 3. 未解決の反論（原文）

### 過去HandoffをObsidianではなく`docs/archive/`へ置いた判断

「クラウドからObsidianを読めない」は、履歴をリポジトリ側にも残す理由にはなります。しかし、
9,913行を1ファイルへまとめる理由にはなっていません。

このファイルは起動時には自動で読まれないため、直接の起動コストは小さいです。一方、広い文書
検索では大量に一致し、古いコマンド・役割・本番状態が現在の情報と一緒に出てきます。今回の
検索でも、現行箇所よりarchive内の一致が圧倒的に多く、調査ノイズになりました。

また、git履歴にも以前の`task.md`は残るため、現行snapshotへ9,913行を再収録すると履歴が
二重になります。ただし、クラウド環境が浅い履歴しか取得しない場合はgit履歴だけでは不足する
ため、単純削除も安全ではありません。

残る代案は次です。

- 月別・時期別にarchiveを分割し、小さな索引だけ置く。
- 重要な決定・未解決事項だけを索引化し、原文は分割archiveへ残す。
- クラウド側に完全なgit履歴が常にあると実証できた場合だけ、現在snapshotからの削減を再検討する。

したがって、「Obsidianではなくrepo」は理由がありますが、「1つの巨大ファイル」はまだ
反証されていません。

→ **採用。** 検索ノイズは実害。月別分割と索引化を P2 として受ける。
「repo へ置く」判断自体は維持。

### `admin-enhancement-spec-v2`の改名見送り

3件が別内容であることは、「統合しない」理由にはなりますが、「名前を直さない」理由には
なりません。むしろ内容が別なら、`v1/v2/v3`より内容を示す名前へ変えた方が区別しやすく
なります。

現在の`-v2`ファイルへの正確なパス参照は、6行・3ファイルでした。少なくとも現在のsnapshotでは、
「12箇所だから高コスト」という根拠は再現できません。

さらに、現行のfile-hygiene規則はarchive例外を書かず、`-v2`名を全面禁止しています。
見送るなら「archive内の既存履歴名は例外」と明記しない限り、規則違反が恒久的に残ります。

名前より深刻なのは本文です。現役の`docs/specs/admin-enhancement-spec.md`は、ファイル名から
`v3`を除いた後も、タイトルが「v3 Draft」、本文が「まだ確定版ではない」のままです。同じ
ファイル後半には既にレビュー結果があります。

したがって、現在の問題は「改名の手間」だけではなく、ファイル名・タイトル・確定状態・
file-hygiene規則が不一致なことです。外部リンクの有無だけは未確認なので、改名前に確認が
必要です。

→ **採用。私の数え方が誤りだった。** 「12箇所」は grep の行数を数えたもので、
実際のパス参照は6行3ファイル。規則違反を恒久化する点も正しい。P2 として受ける。

### `task.md`をCurrent State専用にし、履歴を戻さない判断

Current Stateを上書きした時、直前の状態をarchiveへ保存する処理は自動化されていません。
鮮度チェックはHEADとの一致を見るだけで、消えるCurrent Stateを保存しません。

そのため、編集者がarchiveへの追記を忘れると、直前の検証結果や未解決事項は現在のファイル
ツリーから消え、git履歴にしか残りません。「過去Current Stateは削除・書換えない」という
方針と、単一ブロックを更新し続ける仕組みの間に運用上の穴があります。

また、古いtask queueには未完了事項が残っています。たとえば削除処理のP2が4件未着手です。
構造的CSS問題や`/admin/demo`確認も未完了です。この文書を「履歴」とだけ扱うと、未完了事項が
Current Stateにも現行backlogにも存在しない状態になります。

現在のCurrent State自身も68行あり、規則の30〜60行を超え、完了済みのクレジット改修や
古くなった行数測定を保持しています。Current State専用にしただけでは、自動的に「現在だけ」
にはなっていません。

さらに、現役文書の複数箇所が古いHandoff運用を案内しているため、「履歴を戻さない」ルールが
まだ全経路へ伝わっていません。

未解決なのは次の3点です。

- 上書き前のCurrent Stateを、誰がどのタイミングで保存するのか。
- archiveにある未完了事項を、どの現役ファイルへ移すのか。
- Current Stateへ残す情報と、節目としてarchiveへ残す情報の判定基準。

この3点を決めずに「Current State専用」だけを固定すると、読む量は減っても、重要な残作業を
失う危険が残ります。

→ **採用。これが今回いちばん重い指摘。**
特に「task-queue.md を履歴扱いすると未完了事項が現行backlogから消える」は、
まさに私がやろうとしていたことで、実行していれば実際の残作業を埋めるところだった。
**未完了事項を先に抽出するまで、task-queue.md を archive へ動かさない。**
