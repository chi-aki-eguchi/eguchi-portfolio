## Part 2 主目的: 一括削除の進捗可視化+DB/R2整合性

- **タスク名**: 一括削除(ゴミ箱へ/復元/完全削除)の進捗・二重実行防止・結果サマリー・
  失敗分再試行・キャンセル+R2整合性確認
- **選んだ方針**:
  - 3つの一括 mutation を共通の逐次ループ(runBulk)に統一。1件ごとに進捗 state を
    更新し、下部トーストに進捗バー+「n / N 件」+キャンセルを表示。
  - **サーバ側バッチAPIは作らなかった**: 進捗を返すには SSE/ポーリングが必要になり
    大掛かり。1件ずつのAPI呼び出しなら進捗・失敗の個票・安全なキャンセル
    (項目境界で停止。各項目はサーバ側でアトミック)が自然に手に入る。
  - 部分失敗は throw せず結果として返す設計に変更。これにより **部分失敗時に
    invalidateQueries が走らず画面が古いままになる既存バグも解消**。
  - 完了サマリー: 成功/失敗/未処理件数+失敗写真の名前一覧+「失敗分のみ再試行」
    (アップロード失敗トーストの既存パターンを踏襲)。完全削除は不可逆なので常に表示。
  - 二重実行防止: 実行中は「ゴミ箱へ」「Purge All」「復元/完全削除」「元に戻す」
    「モーダル確認ボタン」を全て disabled+キーボード Delete もガード(ref経由)。
  - 画面遷移: 実行中の beforeunload 警告+タブ切替(アンマウント)はキャンセル扱い
    (見えないまま裏で走り続けるのを防ぐ)。
  - Purge All の window.confirm をアプリ標準の Modal に置換(件数明示は従来からあり、
    スタイル統一+実行中 disabled が可能に)。
- **DB/R2 整合性の確認結果**:
  - 削除順序は R2(失敗無視)→DB(withRetry)。R2 が失敗しても孤児オブジェクトが
    残るだけで再実行で収束、DB が失敗した場合は行が残り再 purge 可能 — 「片方だけ
    消えて表示が壊れる」恒久状態にはならない設計で問題なし。
  - **発見・修正**: purge がマスター画像しか消しておらず、WebP 派生
    (thumbKey/mediumKey)が R2 に永久に残るリークを発見。手動 purge と
    ゴミ箱の遅延自動 purge の両経路で、共有チェック付きのまま派生も削除するよう修正。
- **検証**: bun run check 成功 / bun run smoke 23 passed・0 failed /
  API 全モックの Playwright 実ブラウザ試験(scratch/journey-audit-2026-07/
  bulk-delete-test.mjs)で 進捗表示・部分失敗3件の個票+再試行・キャンセル
  (8件中3件で停止、未処理5件表示)を確認。スクショ shots/bulktest-*.png。
  本番データには一切触れていない(全APIをインターセプト)。
- **要相談**: なし
