- **発見したバグ(実測で確認・要件2「S/M/Lが実際に見て分かる大小差になるか厳しく確認」対応)**:
  行の目標高さが `base * Math.max(現在行の重み)` で決まる実装だったため、
  (a) S(重み0.8)はM/Lと同じ行に混ざると常に無効化される(max が M/L に張り付く)。
  (b) L(重み1.45)は登場位置によって効果が一貫しない — 既にM数枚分のratioを
  消費した後にLが来ると、新しい(高い)目標に対してovershootし、実測で
  「Lが入っているのに高さがM単独行と同じ(183.1px)」というケースを確認。
  ランダム構成500試行でL含有行の実測: 最悪218px/最良362.5px と、位置依存でばらついていた。
- **修正方針**: 「行は同じ表示サイズだけで構成する」よう強制break条件を追加
  (`weight !== current[0].weight` で新しい行を開始)。これにより連続する同一サイズのみが
  1行にまとまり、S/L は前後に何があっても必ず専用の行を得る。
  修正後、ランダム500試行で L含有行1510件すべてが M平均行より確実に大きい

## 追記: Codex push前レビューでP1発見・修正(commit 106f837後)

- **Codexの指摘(実測つき・自己検証済み)**: 上記の「強制break」修正
  (`weight !== current[0].weight` で行を区切る)は、S/M/Lを毎回確実に見せる代わりに
  **強制break後のcloseRowが常にnon-flush(non-stretch)** だったため、
  最終行でない行にも大きな空白が生じていた。containerWidth=976, 3:2写真の
  M,M,S,M,M構成で自己検証: 行0(非最終)がgap=216px、行1(非最終)がgap=676px
  ——`justified`の核となる定義(最終行以外は行幅ぴったり)に反する重大なバグ。
- **設計判断**: Option A(行組みの完全flush優先)を採用。理由:
  「justified」という名称/仕様自体が非最終行flushを前提とするため、これを
  崩すと別レイアウトになってしまう。S/M/Lは「行の目標高さへの強い影響」
  (保証ではない)へソフト化。
- **実装**: 強制break機構を撤去。ループ中はcloseRow(true)(flush)のみを呼び、
  配列末尾の余りだけがcloseRow(false)(非stretch)対象——構造上、非最終行が
  常にflushであることを保証する(個別チェックではなく、ループ中に非flush分岐が
  存在しないことで保証)。
  - lookback(直前アイテムを含める/除外するかを比較して閉じる案)も試作したが、
    2000試行のスイープでSの信頼性を悪化させる(lookback有: 44.8% → lookback無: 70.0%、
    Lは81.7%→87.7%とわずかに改善するのみ)ことが判明したため不採用、単純greedyを採用。
- **修正後の実測(2000試行スイープ)**: 非最終行のflush違反 0/13093件(完全ゼロ)。
  L含有行がM平均行より高い: 81.7%。S含有行がM平均行より低い: 70.0%
  (いずれも「毎回確実」ではなく「統計的に強い傾向」——非最終行flushの原則と
  数学的に両立しないため、これは受け入れた設計上のトレードオフ)。

## タスク: task-queue.md Q-4 — hero/profile画像差し替え時の旧ファイル調査（読み取りのみ）

- **背景**: `docs/specs/audit-2026-07.md` P2-2。差し替えのたびに旧R2オブジェクトが
  残っている可能性がある。ストレージの削除は取り返しがつかないため、今回は
  **調査と設計2案の提示のみ**（コード変更・削除は一切行わない）。

### 呼び出し元の調査

- `POST /admin/hero/upload`(`packages/web/src/api/index.ts:1319`)は、**現在フロントエンドに
  呼び出し元が無い（死んでいるルート）**。`packages/web/src/server.ts:71-73`のコメントに
  「the legacy `heroPhotoUrl` setting is no longer written」と明記されており、
  hero画像は現在 `hero_photos`テーブル（複数のphotosを選ぶ方式、
  `admin-tabs.tsx:505-572`の`HeroTab`）に置き換わっている。`heroPhotoUrl`設定値は
  GET /settings のdefault(`index.ts:893`)と `ogp.ts:247`のOGPフォールバックとしてのみ
  読まれる、書き込みが起きない過去の値。
- `POST /admin/profile/upload`(`index.ts:1345`)は**現役**。呼び出し元は
  `admin-tabs.tsx`の`handleProfilePhoto`(875-909行)。ファイル選択→アップロード成功
  →`saveSettings.mutateAsync({ profilePhotoUrl: url })`を**手動保存ボタン無しで
  即座に自動保存**する構造(904行)。つまり「差し替え」は実質、この関数内で
  同期的に完結する一連の処理。

### 旧値の形式

- `keyToProxyUrl()`(`index.ts:503-508`)が返す`/api/images/{key}`形式のプロキシパス
  （R2の生キーでも絶対URLでもない）。R2から削除するには既存の
  purgeコード(`index.ts:1622`, `1686`)と同じ`value.replace("/api/images/", "")`で
  生キーへ変換する必要がある。
- キーのprefixは`hero/`(`index.ts:1337`)・`profile/`(`index.ts:1363`)で、
  ギャラリー本体の`photos/`(`index.ts:1281`)とは名前空間が分離している。

### photos行と共有され得るか

- **共有され得ない**。hero/profile画像は`schema.photos`への insert を一切経由せず
  （両ハンドラともR2アップロードして`{url,key,size}`を返すだけ）、
  既存の複製写真purgeロジック(`index.ts:1607-1633`, `1673-1699`、
  「他に参照が無い場合のみ削除」の参照カウント方式)の対象にもならない。
  各hero/profileキーは、対応する設定値(`heroPhotoUrl`/`profilePhotoUrl`)から
  常に**最大1箇所からしか参照されない**。photos側の「複製がR2オブジェクトを共有する」
  問題とは構造が異なり、削除しても他の行を壊すリスクは無い（が、下記の通り
  タイミングには注意が要る）。

### 設計案

**案A: 保存時に旧キーを削除**

- `POST /admin/settings`（またはprofile/hero upload専用の保存経路）が
  `profilePhotoUrl`/`heroPhotoUrl`の**新しい値を書き込んだ直後**に、
  書き込み前の旧値を`.replace("/api/images/","")`で生キー化し、
  新旧キーが異なる場合のみ既存purgeと同じbest-effort(`try/catch`で握りつぶす)の
  `DeleteObjectCommand`を1回発行する。
- メリット: 差し替えごとに即座に片付く。ストレージが増え続けない。既存の
  削除パターン(purge)をそのまま踏襲でき実装が小さい。
- デメリット: 削除は**設定値の書き込みが成功した後**でなければならない
  （先に消すと、直後の設定保存が失敗した場合に「今表示されているはずの画像」が
  消えてしまう）。実装の順序を誤ると壊れる。取り返しがつかない操作なので、
  将来もし同じURL文字列を別の設定キーが使い回すような変更が入った場合
  （現状は無い）、監査なしに気づかず消してしまうリスクがある。「何がいつ
  消えたか」の記録も残らない。

**案B: 削除せず「未参照hero/profileオブジェクトの棚卸し」管理エンドポイントを追加**

- 新規read-only管理エンドポイント（例: `GET /admin/storage/orphaned-hero-profile`）が
  `ListObjectsV2Command`（既存依存`@aws-sdk/client-s3`に含まれる。新規パッケージ追加
  不要）で`hero/`・`profile/`prefix配下のR2オブジェクト一覧を取得し、
  現在の`heroPhotoUrl`/`profilePhotoUrl`設定値（＝生きている参照はこの2つだけ）と
  突き合わせて「未参照」を一覧表示する（key・サイズ・更新日時）。削除は
  この一覧を見た後にオーナーが個別に(あるいは一括で)明示的に実行する
  別アクションとして後日実装する。
- メリット: 誤削除リスクがゼロ（追加のみ、既存動作に一切影響しない）。
  「削除方式はオーナーが選ぶ」原則に対し、方式選択に加えて**個々の削除実行も
  オーナーが都度確認**できる。死んでいる`/admin/hero/upload`ルート自体の
  今後の扱い（削除するか放置するか）を判断する材料にもなる。
- デメリット: 棚卸し画面をオーナーが見に行かない限りR2にオブジェクトが
  溜まり続ける（1件あたりmozjpeg q92 3200pxのJPEGで数百KB程度、profile写真の
  差し替え頻度は低いと想定されるため増加は緩やか）。「消す」ボタンまで作るなら
  結局2チケット分の実装が要る。

### 補足（Q-4の範囲外の観察）

- `/admin/hero/upload`自体が死んでいるルートである点は、Q-4のスコープ
  （旧ファイル掃除の設計）とは別問題。ルート自体を削除するかどうかは
  別途オーナー判断が要る小さな別チケットとして切り出すのが良さそう
  （本タスクでは実装しない）。
