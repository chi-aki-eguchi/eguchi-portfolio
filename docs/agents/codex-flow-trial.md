## 分かったこと（2026-07-28 時点）

- **効いたのは段数ではなく「反論を要約しないこと」。** Finder型の共通記録は、
  16件の反論を書き換えずに残して実装Codexへ読ませた。その結果、実装Codexは
  記録に無い判断（媒体不明の扱い・flagの持ち方）で**自分から止まって確認してきた**。
- **原因が明確な作業にAを挟まなかったのは正解だった。** 390pxの見出しは実測値を
  渡してDのみで完了している。
- **Codexの報告をそのまま採用しないことが2回効いた。**
  1回目は「focusで見えるようにした」が本当に効いているかの確認（結果: Codexが正しく、
  私の測り方が誤り）。2回目は読み込み失敗の判定条件（結果: 私の指摘が正しく、修正）。
- **失敗**: Codexの実行環境ではローカルの待受ポートが開けず、Playwrightを1度も
  実行できない。ブラウザ検証は毎回Claude側でやり直す前提で依頼を書くべき。
  同様に、Codexは `.git/index.lock` を作れずcommitできないことが多い。

## 追記（2026-07-29）

- 上の「Playwrightを実行できない／commitできない」は環境固有だった。今回のCodex Desktop
  Goalでは、同じリポジトリでPlaywrightをPC・1024px・390px・mobile Safariまで実行でき、
  Phase 1〜4の論理commitも作成できた。今後は「Codexは常に実行不能」と決め打ちせず、
  そのタスクの環境で実行可否を確認する。
- 長時間Goalでも、各Phaseを0 failで閉じてからcommitしたことで、最後のCSS名衝突を
  「Libraryの安全処理の故障」ではなくPhase 5の新規共通部品に限定して直せた。

## 判定

期間終了後、次がすべて満たされていれば恒久化する。満たされなければ、どのルールが
原因かを書いてから見直す。

- 手戻りが減った
- Codexの反論が要約で消えていない
- 追加時間が許容範囲

## 記入の目安

- **Codex実行回数**: そのタスクで `codex exec` を何回起動したか（resumeは含めない）
- **追加時間**: 発動条件に従ったことで増えた時間。減った場合はマイナスで書く
- **実装前に防げた手戻り**: A や C が実装前に潰した誤り。無ければ「無し」
- **消えかけた反論**: Claude が要約や不採用で落としかけ、後から正しかったと分かったもの
