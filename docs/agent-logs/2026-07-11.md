## タスクB: 配布版Postgresのreorder失敗(42804)修正 + ロック復帰UX

- **経緯**: 当初仮説は sessionStorage の librarySort による reorderLocked。作業中に
  オーナーが先輩側の実症状(「並び替えに失敗」表示・矢印操作でも失敗)を確認し、
  保存経路(POST /admin/photos/reorder)の失敗が本命に変わった。
- **原因特定(推測修正の禁止に対応)**: PostgreSQL の型解決ルールで「THEN 側が全て
  未型付けパラメータの CASE」は text と解決され、integer 列 sort_order への代入が
  42804 で失敗する。SQL文面の生成確認(Codex実施)では正しく見えるが、サーバ側の
  実行時型推論で落ちる。**PGlite(実Postgres/WASM)で再現し、CAST 修正で解消する
  ことも実行確認した**(scratch/pg-reorder-repro/repro.ts, verify-fix.ts)。
  SQLite/libSQL は動的型付けのため本番 Turso では一度も発現しない=「先輩側だけ」
  の説明がつく。
- **選んだ方針**: `api/reorder-sql.ts` に CASE 組み立てを共通化し
  `THEN CAST(? AS INTEGER)` で両方言とも整数に固定。photos/categories/series/
  pricing/hero-photos の5エンドポイント全てに適用(同一パターンのため)。
  失敗時ログはテーブル名+エラーコード/メッセージのみ(ids・秘密値なし)。
- **迷った点**: 5箇所への1行修正 vs 共通ヘルパー化。→ ヘルパー化を選択。
  dialect 生成テストで CAST の存在を固定でき、将来の reorder 追加でも同じ轍を
  踏まないため。
- **UX側**: reorderLocked の判定を pure 関数 `reorderLockReason` に切り出し、
  原因別の文言+「並び替えできる状態に戻す」1クリック復帰(librarySort=manual +
  clearLibraryFilters。写真データ不変更)+ドラッグ/タッチ矢印の案内を追加。
  `draggable={!reorderLocked}` で見かけ上のドラッグ可能も解消。
- **テストの学び**: render テストで librarySort に "newest" を seed しても
  サニタイズ effect が正規リスト外の値を "manual" に戻すため無効。正規値
  "createdAt-desc" を使用(テスト内コメントに明記)。
- **PGlite の隔離**: `bun add` が workspace root の package.json / bun.lock に
  依存を追加してしまった(Codex 指摘)。両ファイルを revert し、
  scratch/pg-reorder-repro/ に専用 package.json を置いて隔離。最終差分に
  PGlite は含まれない。
- `bun run check`: 成功(323 tests / 0 fail)。

  admin-trash-signal.spec.ts のみ**(2026-07-10 Handoff と同一・今回変更起因 0件)。
