## 0. 目的と評価軸

オーナー確定の6軸（デザイン／使用感／完成度／高級感／AI感の削減／可愛さ）に対し、
本再設計は次の一文を判断基準にする。

> **写真が画面の中で最も強い視覚要素であり、操作は「探さなくても、いつも同じ場所にある」。**

一般的な SaaS 管理画面（カード・タブ・pill・塗りボタンの反復）ではなく、
**写真家の静かな編集室**を目指す。

### 設計の核 — 空間の文法（Admin 全体で1つだけ）

現在の最大の問題は「操作が上・左・中央・右へ散らばっている」ことである。
場所ごとに**意味**を固定し、全画面で例外を作らない。

| 位置 | 意味 | 置いてよいもの | 置いてはいけないもの |
|---|---|---|---|
| **左** | **行き先** — どの画面へ行くか | 9画面への移動、サイトを見る、ログアウト | 画面内の操作 |
| **上** | **現在地と文脈** — 今どこで、何がいくつあるか | 画面名、件数、モード切替、探す（検索・絞り込み・表示）、画面を出る操作 | 破壊的操作、保存 |
| **中央** | **素材** — 実際の仕事 | 写真、フォーム、プレビュー | 装飾のカード枠 |
| **下** | **する** — 今の状態に対する操作 | 選択中の一括操作、並べ替えの移動、未保存の保存／破棄 | 文脈が無いときの常設帯 |
| **右** | **選んだ1つの詳細** | inspector（写真1枚の編集） | 常設パネル |

この「下＝する」は既に `admin-layout-implementation.md` §5-3 が Library の下部帯で採用している。
**本再設計はそれを Admin 全体の憲法へ格上げする。** 新しい規則を増やすのではなく、
既にある1つの規則を全画面へ適用して、画面ごとのローカルルールを消す。

## 2. なぜ「AI 生成の管理画面」に見えるのか

見た目の印象は主観だが、原因は具体的なコードに帰着できる。**5つある。**

### 2-1. 「全部ボタン、全部同じ形」— 一括リセットの副作用

```css
.admin-atelier button:not(.absolute):not([class*="bg-black"]) {
  border-radius: var(--admin-radius-sm) !important;
  min-height: 40px;
  border-color: var(--admin-line) !important;
  background-color: transparent !important;
}
```

この1つの規則が、**役割の異なる要素をすべて「40px の角丸枠付きチップ」に均す**。
言語切替も、目次の節も、モード切替も、Import も、保存も、同じ形になる。

人間のデザイナーは「これは移動、これは実行、これは切替」と形を変える。
一括リセットは、その区別を消す。**これが「何でも pill 型ボタン」の正体である。**

### 2-2. 「状態が全部黒塗り」— 意味の異なる3つが同じ表現

`aria-pressed="true"`（選択中）・`aria-expanded="true"`（開いている）・`.admin-btn-primary`（主要操作）が
**すべて `background: var(--admin-ink)` の黒塗り**になる。

結果、1画面に黒い塊が5〜8個散る。どれが「今の状態」でどれが「押すべき操作」か分からない。
静かな画面にならない最大の理由。

### 2-3. 「12px が既定」— 補足サイズで UI 全体を書いている

`--admin-text-note`(12px) の使用が 314回、`--admin-text-body`(14px) が 95回。
**12px は本来「補足」のサイズ**なのに、ボタンラベル・モード名・件数・入力欄まで 12px で書かれている。

これが「余白はあるのに操作部分だけ窮屈」の正体。
文字が小さい → 情報密度が上がる → 詰まって見える → さらに小さくして詰める、の悪循環。
狭い幅で `font-size: 0` にする対処（B3）も同じ発想の延長線上にある。

### 2-4. 「明朝とゴシックの境界が曖昧」

`h1, h2, h3` すべてに明朝 ＋ `letter-spacing: 0.06em` ＋ `!important`。
日本語の見出しに 0.06em の明朝を当てると、字間が空いて締まらない。
一方で本文・ラベル・ボタンは全部ゴシック 12px。
**「明朝＝格調」「ゴシック＝実務」という役割分担が無く、大きさだけが違う。**

### 2-5. 「線と枠が写真より強い」

角丸 285箇所（JSX 245 ＋ CSS 40）、workbar・ヘッダー・inspector・下部帯それぞれに境界線。
写真グリッドは、四方を線で囲まれた「中身」になっている。
**写真が主役の画面では、線は写真の輪郭であるべきで、UI の輪郭であってはならない。**

### まとめ

これらはすべて**「個別に直すたびに規則が増える」構造**から来ている（D1/D2）。
特異度で勝てないから `!important` を足す → 次の人はさらに `.admin-atelier` を重ねる → 28箇所。
**再設計の本体は見た目ではなく、この規則の増殖を止めることである。**

## 3. 左ナビのクリック不能バグ — 原因確定

**状態: 実測で再現・原因確定・修正案検証済み。コード未修正。**

### 3-1. 再現条件

1. 画面幅 **1200px 以上で左ナビを折りたたむ**、または **1024〜1199px**（自動で折りたたまれる）
2. Library（または任意の Workspace 画面）を開く
3. レールの「**見せ方**」または「**サイト**」を押す（子が2つ以上あるグループ）
4. 右に出るポップオーバーの項目（ヒーロー／シリーズ／カテゴリー等）を押す

→ **押せない。** 代わりに背後の Library ツールバーのボタンが反応する。

### 3-2. 実測結果

ポップオーバーの幾何（1440px・折りたたみ時）:

```
popover rect = { x: 68, y: 112, w: 200, h: 138 }, z-index: 60
sidebar right edge = 64        → overflowsIntoMain: true
```

ポップオーバー項目3つの当たり判定（`document.elementFromPoint` で最前面要素を確認）:

```
"Hero"       reaches: false  blockedBy: div.admin-workspace__header
"Series"     reaches: false  blockedBy: button (fieldset.admin-library-mode-switcher の中)
"Categories" reaches: false  blockedBy: div (グリッドのスクロール領域)
```

実クリック:

```
click → INTERCEPTED:
  <div class="admin-workspace__header ..."> from <div class="admin-main"> subtree intercepts pointer events
  tab: "gallery" -> "gallery"   （遷移しない）
```

**「Series」を押したつもりが、Library のモード切替（閲覧／選択／並べ替え）のボタンに当たる。**
これがオーナーの言う「クリック判定が重なり、他のボタンが反応しない」の実体である。

### 3-3. 原因 — z-index がスタッキングコンテキストに閉じ込められている

```css
.admin-atelier .admin-glass {          /* ← .admin-sidebar が使っている */
  backdrop-filter: var(--glass-blur);  /* ① スタッキングコンテキストを作る */
  transform: translateZ(0);            /* ② スタッキングコンテキストを作る */
  will-change: transform;              /* ③ スタッキングコンテキストを作る */
}
.admin-atelier .admin-sidebar { position: relative; }   /* z-index の指定なし */
.admin-atelier .admin-sidebar-compact__popover { z-index: 60; }
.admin-atelier .admin-library-workbar { position: relative; z-index: 20; }
```

- `.admin-sidebar` は `admin-glass` により**スタッキングコンテキストになる**（①②③のどれか1つで成立。3つある）
- しかし `z-index` は指定されていない（`auto`）→ 親の中では **z-index 0 相当**で描画される
- ポップオーバーの `z-index: 60` は**そのコンテキストの内側でしか効かない**。外へは出られない
- 一方 `.admin-library-workbar` は `z-index: 20` で、サイドバーとは別（上位）のコンテキストに属する

結果、**20 > 0 となり、作業面がサイドバー（とその中の z-60 ポップオーバー）より前面に描画される。**
数字だけ見ると 60 > 20 なので直感に反するが、比較対象が違う。典型的な
「z-index がスタッキングコンテキストに閉じ込められる」問題である。

### 3-4. 原因の確証（対照実験）

原因と考えた宣言**だけ**を打ち消して再測定した。

```css
/* 検証用に注入（本番コードは未変更） */
.admin-sidebar.admin-glass {
  backdrop-filter: none; transform: none; will-change: auto; z-index: 80;
}
```

| | Hero | Series | Categories | 実クリック |
|---|---|---|---|---|
| **打ち消し前（現状）** | 押せない | 押せない | 押せない | 遮断。`gallery` → `gallery`（動かない） |
| **打ち消し後** | 押せる | 押せる | 押せる | 成功。`gallery` → **`hero`** |

原因は確定。**推測ではない。**

### 3-5. 併せて判明したこと

- **グループボタンの実寸が 40px**（CSS 宣言は `min-height: 52px`）。
  `.admin-atelier button:not(...)...`（特異度 (0,3,1)）が
  `.admin-atelier .admin-sidebar-compact__group-button`（(0,2,0)）に勝ち、`min-height: 40px` が適用されている。
  仕様§6-1 の「44×44px の当たり判定」を満たしていない（D3）。
- レール上のグループボタン自体（x=4〜60）は押せる。**壊れているのはポップオーバーだけ。**
- 詳細欄の暗幕（`z-30`, `top: 268px`）はサイドバーと**横方向に重なっていない**（overlap.x = 0）。
  暗幕はこのバグの原因ではない。1200px 未満での実測で確認済み。

### 3-5b. Phase 0 の状況（2026-07-31・**未実装**）

**ポップオーバーは Phase 4 まで残す前提で、Phase 0 では原因だけを取り除きたい。
2つの方式を試し、どちらも採用しなかった。**

#### 方式A — `.admin-sidebar` に `z-index: 45` ＋ `isolation: isolate`

左ナビは直り、`bun run smoke` も 282 pass / 0 fail だった。
しかし Codex の独立監査で「45 とトースト 50 は別の重なり枠なので数値を直接比較
できない」と反論を受け、実測したところそのとおりだった。

| 要素 | 所属する重なり枠 | z-index |
|---|---|---|
| `.admin-sidebar` | **html（ルート）** | 45 |
| `.admin-library-workbar` | **`.admin-screen`（transform で層を作る）** | 20 |

作業面 `.admin-screen` は自前の層を持つので、その内側の値（20 も 9998 も）は
サイドバーと直接比較できない。**45 という値の根拠を示せない**ため不採用。

> **訂正**: 当初「方式Aは全画面表示を覆う回帰を起こす」と報告したが、これは
> 測定の誤りだった。`.admin-screen` の `transform` により配下の `position: fixed` は
> ビューポートではなくその箱に閉じ込められるため、検証用に注入したオーバーレイは
> 元々サイドバー領域へ届いていなかった。**方式Aに実害が確認されたわけではない。**

#### 方式B — glass の副作用を打ち消し、ぼかしを疑似要素へ逃がす

`.admin-sidebar.admin-glass` で `transform` / `will-change` / `backdrop-filter` を
打ち消し、ぼかしを `::before`（`z-index: -1`, `pointer-events: none`）へ移す。
左ナビは直り、browser test も 11/11 成功した。

しかし `admin-workspace-layout.spec.ts:95` が**同一条件で 10/10 → 8/10 に悪化**し、
full smoke も 2 failed になった。`translateZ(0)` / `will-change` を外したことで
GPU レイヤー昇格を失い、`backdrop-filter` を持つ疑似要素の描画が重くなったと
推測している（未確認）。あの2宣言は元々そのために置かれていたと考えられる。

#### 次に試す方式（未着手）

**ポップオーバーだけをサイドバーのスタッキングコンテキスト外へ portal する。**
glass の性能特性を保ったまま、閉じ込めだけを回避できる。
`admin-compact-sidebar.tsx` の JSX 変更になる。

当たり判定の是正（40px → 52px / 44px）は方式に依存しないので、
どの方式でも併せて入れる。

### 3-6. 再設計でどう解消するか — **ポップオーバーを廃止する**（Phase 4）

`z-index` を上げる小手先の修正（`.admin-sidebar { z-index: 80 }`）でも直る。
しかし本再設計では**ポップオーバーという部品自体をやめる**。理由:

1. **同じ事故が再発しない構造にできる。** 絶対配置でサイドバーの外へはみ出す部品が無くなれば、
   スタッキングコンテキストの問題は起きようがない
2. **操作が1クリック減る。**（今: レール → ポップオーバー → 項目 = 2クリック）

グループは区切り線と余白だけで示す。9項目 × 48px ＋ 区切り = 約 440px で、
800px 高の画面にも収まる。

## 4. Workspace 実効幅 — container query が必要な理由

viewport 幅だけでは判断できないことを、数値で示す。

| viewport | 左ナビ | 詳細欄 | プレビュー | **作業面の実効幅** |
|---|---|---|---|---|
| 1600 | 236 | – | – | **1364** |
| 1440 | 236 | – | – | **1204** |
| 1440 | 236 | 400 | – | **804** |
| 1440 | 72（折りたたみ） | 400 | – | **968** |
| **1280** | 236 | 400 | – | **644** |
| **1280** | 236 | – | 440 | **604** |
| 1024 | 72 | 重ねる | – | **952** |
| 768 | 0（下部ナビ） | 全画面シート | – | **768** |
| 390 | 0（下部ナビ） | 全画面シート | – | **390** |

**決定的な事実: 1280px の viewport で詳細欄を開くと、作業面は 644px しかない。
これは 768px のタブレットより狭い。** それでも media query は「1280px = デスクトップ」として
PC 用の規則を当てる。これが「中間幅で PC 用とスマホ用のどちらにもなりきらない」の正体である。

Settings も同様:

| viewport | 左ナビ | 目次 | プレビュー | **フォーム実効幅** |
|---|---|---|---|---|
| 1440 | 236 | 208 | 560 | **436** |
| 1280 | 236 | 208 | 480 | **356** |

**1280px でプレビューを開くと、フォーム本文は 356px。スマホ（390px）より狭い。**
現在の CSS はここに「デスクトップ用の横並びラベル」を適用しているため、不自然な折返しが起きる。

### 決定

- **`.admin-workspace` と Settings のフォーム列に `container-type: inline-size` を付ける**
- Library ツールバー、フォームのラベル配置、下部帯の段組みは**すべて `@container` で分岐**する
- viewport の media query は「Shell の骨格」だけに使う
  （左ナビを出すか／下部ナビにするか、＝ 1024px と 768px の2本だけ）

これで規則の本数が減る。現在の 767 / 768-1023 / 1024-1199 / 1199 / 1200 の5系統は、
**viewport 2本 ＋ container 3本**に整理できる。

### container の分岐点（提案）

| container 幅 | 名前 | Library ツールバー | フォーム |
|---|---|---|---|
| ≥ 1040px | `wide` | 1行（モード｜探す｜出る） | ラベル左・入力右 |
| 720–1039px | `mid` | 2行（1行目=モード＋出る／2行目=探す） | ラベル左・入力右（ラベル幅を縮める） |
| < 720px | `narrow` | 2行＋「その他」へ収納 | **ラベル上・入力下** |

| **保存状態** | サーバーとの同期状態 | **下**（データ操作と同じ帯） | 保存中／保存しました／保存できません／Undo |

**この表が「役割を明確に分ける」の答えである。** 重要な帰結:

- **並び順・表示密度・Grid/Table は「一覧共通操作」**（オーナー暫定回答どおり）。
  データを変えないので全モードで出す。並べ替えがロックされていても手動へ戻せる

  結果的に並べ替えモード内にだけ出る（§12-2 で整合性を検証）
- **「その他」への収納は「一覧共通操作」の中でだけ許す。** モード・データ操作・画面を出る操作は
  隠さない

## 6. 比較する案

### 案A — 左アイコンレール中心（写真最大化）

左ナビは常時 72px のレール。9画面をアイコン＋10px ラベルで直接並べる。展開状態を持たない。

- **メリット**: 作業面が常に最大（1440px で 1368px）。写真が主役という方針に最も忠実。
  状態が1つしかないので、レイアウト規則が最も少ない
- **デメリット**: 9項目のアイコンだけでは画面名の想起が難しい。「シリーズ」と「カテゴリー」の
  区別がアイコンで表現しにくい。オーナーは毎日使うので慣れるが、初回は迷う
- **向いている幅**: 1024px 以上すべて。狭い方が有利
- **Library**: ◎ 作業面が最大。写真が最も広く見える
- **Settings**: ○ フォーム 720px ＋ プレビューが 1280px でも成立する
- **推奨度**: △ — 単独では採らない。理由は下記

### 案B — 左ナビ常時展開（分かりやすさ優先）

左ナビは常時 236px。グループ見出し＋画面名を全部出す。折りたたみを持たない。

- **メリット**: 迷いがゼロ。現在地が常に明確。実装が最も単純で、規則が増えない
- **デメリット**: 1280px で詳細欄を開くと作業面 644px（§4）。写真が主役にならない。
  1024px では成立しない（作業面 788px で、写真2〜3列）
- **向いている幅**: 1440px 以上
- **Library**: △ 詳細欄と併用すると窮屈
- **Settings**: ◎ 目次・フォーム・プレビューの3列が最も安定する
- **推奨度**: △ — 1280px 以下を捨てることになる

### 案C（中間案）— **展開を既定、折りたたみは明示操作。ポップオーバー廃止** ← **推奨**

- 既定は **236px の展開**（案B の分かりやすさ）
- オーナーが畳むと **72px のレールに9画面すべてを直接表示**（案A の広さ）。
  **ポップオーバーは作らない** — §3 のバグ構造ごと消える
- **1024〜1199px では自動でレールになる**（現行の挙動を維持）
- 状態は `localStorage` に保存（現行 `admin:sidebarCollapsed` を維持）

| | 案A | 案B | **案C** |
|---|---|---|---|
| 1440px の作業面（詳細欄なし） | 1368 | 1204 | 1204 / **1368**（畳めば） |
| 1280px の作業面（詳細欄あり） | 808 | 644 | 644 / **808**（畳めば） |
| 1024px | 952 | 788（破綻） | **952** |
| 迷いにくさ | △ | ◎ | ◎（既定が展開） |
| 実装の規則数 | 1状態 | 1状態 | 2状態（現行と同じ） |
| §3 のバグ | 消える | 起きない | **消える** |

- **メリット**: オーナーが「今日は写真を広く見たい」を選べる。既定は迷わない展開。
  1024px の自動レールという既存の挙動と `admin:sidebarCollapsed` をそのまま活かせる
- **デメリット**: 状態が2つあるので、ワイヤーフレームとテストが2倍必要
- **Library**: ◎ 写真の点検時だけ畳める
- **Settings**: ◎ プレビューを開くときだけ畳めば 1280px でもフォームが 592px 確保できる
- **推奨度**: ◎ — **これを推奨する**

**推奨理由**: 現行実装が既に「展開／折りたたみ／1024px 自動レール」の3状態を持っている。
案C はそのうち壊れている部分（ポップオーバー）だけを置き換える。
案A・案B はどちらも状態を1つに減らす代わりに、既存の挙動と localStorage を捨てることになる。
**リスクが最も小さく、得られる作業面が最も大きいのが案C。**

## 8. タイポグラフィのルール

### 8-1. 2書体の役割を決める

| 書体 | 変数 | 役割 | 使う場所 |
|---|---|---|---|
| **明朝** | `--admin-font-title` | **名前を示すときだけ。** その画面／作品が「何であるか」 | ページタイトル、ブランド名、写真タイトル（表示のみ）、プレビュー内の公開サイト（サイト側の設定に従う） |
| **ゴシック** | `--admin-font-ui` | **操作と情報のすべて** | 節見出し、項目ラベル、補足、数値、ボタン、入力欄、ナビ |

**原則: 明朝は「押せないもの」にしか使わない。** 押せる要素は必ずゴシック。
これで「どこが操作か」が書体だけで分かる。

**現行からの変更**: `h2, h3` から明朝を外す（現行は `h1,h2,h3` 全部明朝＋`!important`）。
節見出しはゴシック 16px medium にする。日本語の節名に明朝 0.06em は間延びするため（C5）。

### 8-2. 大きさの階層 — **12px を既定から降ろす**

C1（12px が 314回、14px が 95回）を逆転させる。

| 用途 | 現在 | **変更後** | 書体 | 字間 | 備考 |
|---|---|---|---|---|---|
| ページタイトル | 34px | **26px** | 明朝 | 0.04em | 34px は Admin には大きい。写真より目立つ |
| 節見出し | 17px | **16px** medium | ゴシック | 0.02em | 明朝をやめる |
| **本文・ラベル・ボタン** | 12px | **14px** | ゴシック | 0 | **これを既定にする** |
| 補足・注記 | 12px | **12px** | ゴシック | 0 | 本来の用途に戻す |
| グループ見出し・eyebrow | 10-11px | **11px** | ゴシック | 0.08em | 大文字/カナのみ |
| レールのラベル | 10px | **10px** | ゴシック | 0 | 折りたたみナビ専用 |
| 数値（件数・順位） | 12px | **13px** tabular | ゴシック | 0 | `font-variant-numeric: tabular-nums` |

**`--admin-text-note` の意味を変えない。** 変えるのは**呼び出し側**。
`--admin-text-body`(14px) を既定にし、note(12px) は補足だけに使う。
移行は Phase で段階的に行う（§13）。

### 8-3. 日本語と英語

- **英単語・数値を途中で改行しない**: 操作要素に `word-break: keep-all; overflow-wrap: normal`
- **短いラベルは折り返さない**: ボタン単位で `white-space: nowrap`。
  **親要素へ一括で当てない**（オーナー指示）
- **日本語の1文字改行を防ぐ**: 操作ラベルに `line-break: strict`
- ボタンの最小幅: `min-width: 4em`（2文字のラベルでも潰れない）

### 8-4. 写真タイトル

- 一覧（グリッド）: 表示しない（写真が主役）。hover 時のみ 12px ゴシック
- inspector: 明朝 16px（作品名として扱う）
- 下部帯（並べ替え中の識別）: ゴシック 13px 1行省略（操作の一部なので）

|---|---|---|
| ボタン高（既定） | **36px** | 文字 14px ＋ 上下 11px |

### 9-3. 状態の表現 — **黒塗りをやめる**（§2-2 の解消）

| 状態 | 現在 | **変更後** |
|---|---|---|
| hover | 背景 `ink 3.5%` | 背景 `ink 3%`（維持） |
| **focus** | outline 2px accent | **outline 2px accent, offset 2px（全要素で必須）** |
| **selected / aria-pressed** | **黒塗り** | **下線 2px accent ＋ 文字を ink に**（塗らない） |
| **expanded / aria-expanded** | **黒塗り** | **背景 `ink 3%` ＋ ▾ を回転**（塗らない） |
| **主要操作（保存など）** | 黒塗り | **黒塗りを維持**（画面で1つだけ） |
| disabled | opacity 0.45 | opacity 0.4 ＋ `cursor: not-allowed`（維持） |
| 現在地（ナビ・目次） | 縦線3px ＋ 背景8% | 維持 |

**規則: 塗りつぶしは「1画面に1つの主要操作」だけ。** 状態は線と文字色で示す。
これで黒い塊が 5〜8個 → 1個になる。

### 9-4. 意味色を accent から分離（現行方針の維持・拡張）

```css
--admin-accent:  #5b7fa0;  /* 現在地・選択・focus のみ */
--admin-danger:  #a33b2e;  /* 削除・失敗 */
--admin-warning: #8a6d3b;  /* 注意・ロック理由 */
--admin-success: #4f715e;  /* 保存成功 */
--admin-info:    #5b6b7a;  /* 案内 */
```

**意味色は文字と 1px の線にだけ使う。背景を塗らない。**（「全画面を染めない」の徹底）

### 9-5. CSS の作り方 — §2 の根を断つ

これが再設計で**最も重要**な項目である。

1. **`.admin-atelier button:not(...)` の一括リセットを廃止する。**
   代わりに `.admin-btn`（既定）／`.admin-btn--primary`／`.admin-btn--quiet`／
   `.admin-btn--danger` の4クラスを作り、明示的に付ける
2. **`.admin-atelier` の重ねがけ（28箇所）を 0 にする。**
   一括リセットが消えれば特異度で戦う必要がなくなる
3. **`!important` を 174 → 20 以下にする。**
   残すのは `prefers-reduced-motion` / `prefers-reduced-transparency` の上書きだけ
4. **`admin-glass` を構造レイヤー限定にする。** サイドバーに使う場合は
   **必ず `z-index` を明示する**（§3 の再発防止）。
   加えて「スタッキングコンテキストを作る要素は z-index を明示する」を規約化する

### 11-1. オーナー質問2への回答 — Undo の3案と既存仕様の整合

**まず事実（コード読解による。実測未了）:**

- `reorderUndo` は保存**成功時**にセットされる（`admin.tsx` L3680）
- **モードを arrange から抜けるとき `reorderUndo` と `lastMove` は既に破棄されている**（L4213-4219）
- しかし **`reorderFeedback`（保存中／保存しました／保存できません の文）は破棄されない**
- 表示条件 L6079 は `libraryMode !== "arrange" && (reorderFeedback || reorderUndo)`
  → 並べ替え後に閲覧へ戻ると、**「保存しました」だけが閲覧画面に残る**（A3 の正体）
- 保存中・保存失敗時の引き止めは `retryFailedPhotoOrder` /
  `discardFailedReorderAndExit` として実装済み（L5085-5100）

**3案の評価:**

| 案 | 既存仕様との整合 | 判定 |
|---|---|---|
| **(1) モード退出時に破棄** | §5-0「抜けるとき `lastMove` を破棄する」と**完全に一致**。しかも**既に実装済み** | **採用** |
| (2) 保存済みの直前操作だけ Undo 可能 | §5-0 と**矛盾する**（抜けても Undo が残ることになる） | 不採用 |
| (3) モード退出前に確認 | §4-2 が「保存中は待つ／保存失敗は引き止める」として**既に規定し、実装済み**。ただし**保存が完了している場合に確認を出すのは過剰** | 条件付き採用（§4-2 の範囲のみ） |

**結論: 挙動の変更は不要。** (1) と (3) は既に実装されており、互いに矛盾しない。

> 保存が完了した移動 → 退出時に Undo を破棄（案1、実装済み）
> 保存中に退出 → 完了を待つ（§4-2、実装済み）
> 保存失敗で退出 → 引き止めて「再保存／取り消して終了」（§4-2、実装済み）

**必要なのは表示の整理だけ**である。すなわち、
**閲覧モードで `reorderFeedback` を描画しない**（L6079 の条件から外す）。
これは配置の変更であって、保存経路・ロールバック・競合拒否には一切触れない。
**リスクが最も低い解**であり、オーナーの「この段階では挙動を変更しない」とも矛盾しない。
