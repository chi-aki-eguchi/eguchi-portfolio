# 管理画面刷新のゴール（2026-07-25 オーナー本人の言葉で確定）

> **このプロジェクトの現在のゴールはこれ。** 個別タスクはすべてこのゴールに従属する。
> それまでゴールがリポジトリのどこにも書かれておらず、2026-07-25 のセッションで
> 担当AIが `growth-monetization-plan.md`（事業計画）をゴールと誤認した。
> 同じ取り違えを防ぐため、`CLAUDE.md` の冒頭からもここへ誘導している。

## ゴール

**管理画面（`/admin`）の刷新。** オーナーの言葉をそのまま置く。

> デザインと使用感と完成度と高級感とAI感の削減。あと可愛さ。

Library だけの話ではない。`/admin` の全タブ（はじめに / Library / Hero / Series /
Categories / Profile / Pricing / Portfolio Kit / Settings）が対象。
`docs/specs/library-redesign-spec.md` はこのゴールの Library 部分にあたる下位仕様。

## なぜ管理画面なのか

管理画面はオーナーが毎日使う道具であり、同時に **Portfolio Kit として販売している商品の
中身そのもの**（購入者も同じ画面を使う）。公開ページは「作品」だが、管理画面は「商品」。
だから見た目と使い心地が、そのまま作業効率であり商品価値になる。

## 6つの軸

### 1. デザイン

見た目そのもの。配色・書体・余白・罫線・階層。既存の `docs/specs/design-spec.md`
（雑誌的佇まい・余白主導）の考え方は公開ページ側の正本であり、管理画面にも通じる。

### 2. 使用感

触ったときの手応え。押した場所で反応が返る、迷わない、操作と対象が競合しない。
`library-redesign-spec.md` §2-3 の「反応の作り方」がこの軸の詳細。

### 3. 完成度

「作りかけに見えない」こと。**この軸は最も裏切られやすい。** 具体的には:

- ブラウザによって崩れる（例: Safari でスワイプすると写真がチラつく — 2026-07-25 オーナー報告）
- 画面幅によって崩れる（例: 1024px で写真が5列→2列に減っていた — Q-11 で解消）
- 半端な状態が見える（読み込み中の白抜け、レイアウトの飛び、二重の枠線）
- 押せそうで押せない、押せなさそうで押せる
- 文言の不統一、片方の言語だけ古い

### 4. 高級感

安く見えないこと。派手さではなく、静かさと精度で出す。余白が効いている、
線が細い、動きが小さく速い、色数が少ない。

### 5. AI感の削減

**「AIが作った画面」に見える特徴を消す。** これは定義がないと実行できないので、
設計側（Claude Code）で下記のとおり定義する。**この定義はオーナー未確認。**
違うと言われたら差し替える。

避けるもの:

- 汎用UIキットそのままの見た目（全部が同じ `rounded-lg` + 同じ影 + 同じ余白）
- 紫〜青のグラデーション、ネオン、光る枠
- 絵文字をアイコン代わりに使う
- どの要素にも説明文が付いている（親切の押し売り。読む量が増えて逆に迷う）
- 意味のない完全な左右対称、完全な等間隔
- 「✨新機能」「🚀はじめよう」のような煽り文言
- 空状態が毎回「中央寄せの大きなイラスト＋2行の説明＋ボタン」の型

代わりに置くもの: **この道具固有の判断が見えること。** 写真家の作業に合わせて
密度・並び・語彙が選ばれていて、汎用テンプレートでは出てこない形になっていること。

### 6. 可愛さ

**高級感と矛盾しない置き方をする。** 装飾を足すのではなく、小さな瞬間に入れる。

- 動きの気持ちよさ（数値の入れ替わり、チェックの付き方、シートの出方）
- 文言の温度（事務的すぎない一言。ただし煽らない）
- 細部の遊び（空状態、完了時、何もしていないときの佇まい）

装飾を増やす方向（丸み・パステル・キャラクター）は高級感を壊すので取らない。
**この解釈もオーナー未確認。**

## この6軸の使い方

タスクを起こすとき・レビューするときに、「どの軸のためか」を1つ以上書く。
軸に紐づかない変更は、このゴールの下では優先度が低い。

## 到達点（2026-07-25 設計側で決定）

6軸は「方向」であって、そのままでは終わりが判定できない。**このゴールの到達点を次のとおり決める。**
以下が全部満たされたら「刷新できた」と言う。

1. **タブを切り替えても内容が横に飛ばない。** 全タブが同じ左端・同じ見出し位置・同じ縦リズムを使う
2. **1画面の説明文は最大1つ。** 見出しで分かることは書かない。同じ内容を2回書かない
3. **UIの言葉は日本語で統一。** 英語はタブ名などの固有名詞（Library / Hero / Series）だけ
4. **同じ操作は同じ見た目。** 追加ボタン・行カード・公開トグルが画面ごとに違わない
5. **1440pxで本文が画面の3割しか使っていない画面が無い**
6. **読み込み中に「意味のない灰色の箱」を見せない**
7. **意味のない仮の表示をしない**（説明が空のときに "…" だけを出す等）

## 2026-07-31 全体刷新（Admin Shell / Library / Settings / Hero / Series / Categories / その他Form）

オーナー指示で、機能を保ったまま Admin 全体を一度に作り直した。
指摘された症状は7つ。**どれも「画面ごとに規則が違う」ことが根**だったので、
画面ごとの手当てではなく、共通の視覚言語を1つ作ってから各画面を載せ替えた。

| 指摘 | 直したこと |
| --- | --- |
| 操作の場所が分かりにくい | Library の取り込み一式を見出しから作業バー右端へ移し、「探す/見る/取り込む」を1本の帯に集約 |
| ボタン・枠・角丸・黒塗りが多い | admin 内の角丸を 8/12/18px → 2/3/5px。入力欄を箱から下罫線へ。黒塗りは「その画面で一番強い1操作」だけに限定 |
| 文字と操作が窮屈 | 縦のリズムを `--ax-gap-page: 40px` / `--ax-gap-block: 20px` に統一。一覧行を60pxへ |
| 中間幅で崩れる | 768px 以上はアイコンレール（従来は1024px未満が全部スマホ扱い）。Settings の目次を横帯化する規則を撤去 |
| 写真より UI が目立つ | 分類の色ラベルを原色から低彩度へ。未分類の写真には点を出さない。写真グリッドの左端を見出しに合わせた |
| 画面ごとのデザイン規則が不統一 | 共通部品を `packages/web/src/web/pages/admin-ui.tsx` に集約。9タブすべてが同じページ枠・見出し・行・入力を使う |
| 左ナビ折りたたみ時の操作不能 | 重なり順の原因を特定して `z-index: 80` で解消。レールから各タブへ**実際にクリックして移動できる**ことをテストで固定（`admin-shell-widths.spec.ts`） |

### 決めた原則（実装の正本は `admin-ui.tsx` 冒頭のコメント）

- **面（塗り）で区切らない。余白と細い罫で区切る。** カードは写真・シリーズのような
  「もの」にだけ残す。設定項目と一覧行はカードにしない
- **入力欄は箱ではなく下罫線。** 管理画面はほぼ全要素が入力かボタンなので、
  枠の数を減らすことが「静かさ」に一番効く
- **黒塗りは1画面に1つ。** 選択状態（`aria-pressed`）と開閉状態（`aria-expanded`）は
  「薄い面 + インクの下線 + インクの文字」で示す。状態を実行操作に見せない
- **ページ枠の幅は用途で3種類だけ**（form 640px / list 860px / wide 全幅）。
  画面名ごとに寸法を足さない
- **見出しの左端は9タブ共通。** Settings の目次はページ見出しの下へ置く
  （以前は Settings だけ見出しが 248px 右にずれ、タブ切替で横に飛んでいた）

### 分かったこと（今後の判断材料）

**部分一致セレクタは事故を起こす。** `.admin-content [class*="p-6"]` が `gap-6` に
当たり、Settings のフォーム列だけ 20px 右へずれていた。`[class~="..."]` の
完全一致へ直した。**同種のルールが残っているので、見た目が想定と違ったら
まず `getComputedStyle` で実測し、上書き元を探す**（P3 の教訓と同じ）。

**「左ナビ折りたたみ時の操作不能」の原因が確定した。** `.admin-sidebar` は
`.admin-glass` の `transform` で重なり文脈を作るため、レールのポップオーバー
（`z-index: 60`）はサイドバーの中に閉じ込められる。一方 `.admin-main` は
位置指定を持たないので、その中の Library 作業バー（20）や表示メニュー（70）は
根の重なり文脈に居る。DOM 順で `.admin-main` が後なので、ポップオーバーが
下に潜って押せなかった。**必要な条件は「70より上・スマホの節一覧シート90より下」**で、
`.admin-sidebar { z-index: 80 }` とした。2026-07-30 に「値の根拠を示せない」として
不採用にした方式A（45）は、この条件を満たしていなかったから効かなかった。

**装いを変える差分は、機能の消失を隠す。** 取り込み一式を作業バーへ移した際、
「通常モードのみ」のかたまりへ入れてしまい、選択モード中に取り込めなくなっていた。
見た目のテストは全部通っていた。**移設したUIは「どのモード・どの状態で出るか」を
必ず別に確かめる**（Codex独立監査が検出。回帰テストを追加済み）。

### P3 で分かったこと（今後の判断材料）

**「AI感」の実体は、当初想定した「汎用UIキットの見た目」ではなかった。**
P3 の前提「Settings / Series / Pricing が同じ汎用リスト部品で作られている」は
実測で崩れた。3画面は別々の実装で、Series の行は表紙写真つきのカードだった。
汎用リストに見えたのは、調査用スクリーンショットを写真496枚の読み込み完了前
（1.2秒）に撮っていたため。

実際に見つかった実体は次の2種類だった。

1. **グローバルCSSが要素側の指定を勝手に上書きする。** `aria-pressed="true"` を
   4重特異度+`!important` で黒塗りにするルール、`[class*="fixed"][class*="bottom-"]` で
   背景を紙色に固定するルール（Q-11 で判明）。**要素を見ても理由が分からず、
   逃げ道が `:not(.absolute)` のようなハックしかない。** 新しい部品を作るたびに
   予期しない見た目になるのはこれが原因。今後も同種が出る前提で、
   **見た目が想定と違ったら `getComputedStyle` で実測し、上書き元を探す**
2. **寸法が用途と合っていない。** Series の表紙写真は全幅の帯（約7:1）で
   写真を切り落としていた。P1 で本文を広げた結果さらに悪化していた

**到達点(6)(7)について**: (7) は該当が無かった（「新しいプラン」はオーナーのデータ、
"…" は読み込み中表示で意図的）。(6) の「灰色の箱」は初回読み込みが遅いだけで
2回目以降は500ms以内。**不具合ではないので優先度を下げる**（画像配信の速度の話であり、
デザインの話ではない）。

`admin-page-frame.spec.ts` が到達点(1)を機械で守っている（9タブの見出し左端の一致）。

## 色は公開サイトと同期する（2026-08-17 オーナー判断）

**管理画面の色は、オーナーが admin で選んだ公開サイトの色と同期する。**
背景色・文字色・差し色が、そのまま管理画面にも出る。

> 独立させない。adminで変えられる公開サイトの色と同期させよう。

2026-08-07 には逆の方針（「作品を見る器と、作品を並べる道具の区別が消える」ので
色を切り離す）を設計側で立てていた。**これはオーナー判断で撤回された。**
下の「管理画面が参照すべきは自分のサイトである」と、こちらのほうが一貫している。

同期の範囲と、同期しないもの:

| 対象 | 扱い |
| --- | --- |
| 背景色・文字色（明暗それぞれ） | **同期する。** 公開サイトと同じ解決規則（`themeColorsFor`）を使う |
| 差し色 | **同期する。** 紙の上で 4.5:1 に足りなければ、足りない分だけ濃くする |
| 危険・注意・成功・情報の色 | **同期しない。** 差し色と同じ色になると「消す」と「保存する」が並んで見分けられない |
| 書体 | **同期しない**（2026-08-07 の決定は書体については有効）。道具の文字は静かに保つ |

読めない組み合わせは選ばせない。本文は紙に対して 7:1、補助文字と意味を持つ色は
4.5:1 を満たすところまで自動で寄せる。**オーナーの色を無視するのではなく、
足りない分だけ寄せる。**

実装の正本は `admin.tsx` の `adminThemeFromSettings`。**`styles.css` の
`.admin-atelier` にある色は、JSが当たる前の一瞬に使う控えでしかない。
ここだけ直しても画面は変わらない**（2026-08-17 に実際に起きた）。

暗いモードもこの規則で決まる。以前は admin の根へ付くインライン style が
CSSの `[data-theme="dark"]` に勝つため、暗くしても管理画面の紙が変わらなかった。
現在は明暗を解決してから色を作るので、暗い方の設定（`themeBgDark` /
`themeTextDark`）が無ければ既定の黒へ戻り、OSが描く部品も `color-scheme` で揃う。

## 視覚設計の方向（2026-07-25 オーナー判断「mac風やめる」を受けて決定）

**管理画面が参照すべきは macOS ではなく、自分のサイトである。**

`docs/specs/design-spec.md` は公開サイトの視覚設計の正本で、核は次の3つ。

1. 雑誌／写真集のような「編集された」佇まい。整いすぎず、こなれた抜け感
2. 写真が主役、UIは器に徹する
3. **こなれ感は装飾でなく「余白」と「大小差」から作る。足すより、間を作る**

**macOS 設定風のグループカードは、この3番目の真逆だった。** 面（塗られたカード）で構造を
作るやり方で、しかも全行が同じ高さ・同じ濃度になるため「整いすぎ」で緩急が無い。
2026-07-09 に意図して入れたものだが、**意図的であることと、いまのゴールに合っていることは別。**
オーナー判断（2026-07-25）で廃止する。

### 決定した原則

- **面で区切らない。余白と細い罫で区切る。** 設定項目・フォーム行に塗り・影・角丸を使わない
- **カード（面）は「もの」にだけ残す。** 写真・シリーズのように実体があるものはカード可。
  設定項目はカードにしない
- **余白に緩急をつける。** グループ間は大きく抜き、行間は詰める（design-spec §5「抜く所は
  大胆に抜く」）
- **写真以外で色を主張しない**（design-spec §3）
- **ヒエラルキーは塗りではなくタイポと余白で作る**

### 実装時の決定（2026-07-25）

- 設定行の高さは **40px**（共通ボタンCSSの `min-height:40px !important` に従う）。
  当初 56px を指定したが、実現には styles.css に3つ目の `!important` 例外が必要で、
  得られるものが小さい。**「余白の緩急」はグループ間の余白48pxが担えている**と判断した
- 現在値（「自動（既定）」「フィルム粒子」等）は**行の右端に揃える**。
  以前はタイトル直後に置いていたため行ごとに位置がバラバラで、一覧として読めなかった

### 統一先は既にリポジトリの中にある

新しい視覚言語を発明しない。Portfolio Kit の `ServiceSection`
（`admin-tabs.tsx`）が既に「塗らない・下罫線だけ」の作りで、上の原則に合っている。
**Settings の `SettingsGroup` / `Section` をこちら側へ寄せる**（逆ではない）。

## 実データの事実（2026-07-26 本番データを実測。設計はこれに従う）

「撮影日でまとめる」という方向を検討するにあたり、本番の写真496枚を実測した。
**推測ではなく、この数字に合う設計にすること。**

### 撮影日は全件入っている

| 項目 | 実測 |
| --- | --- |
| 撮影日(shotAt)あり | **496 / 496（100%）** |
| 撮影日の種類 | 94日分 |
| 1日あたりの中央値 | **2枚** |
| 最大 | **121枚**（2026-06-18） |
| 1枚だけの日 | **34日（全体の36%）** |

**素直に「カレンダーの日」で区切ると496枚が94個に割れ、その3分の1が1枚だけの塊になる。
整理にならない。**

### ライブラリは性質の違う2つの塊でできている

| | 枚数 | 日数 | 中央値 | 最大 | 1枚だけの日 |
| --- | --- | --- | --- | --- | --- |
| **フィルム** | 279 | 33日 | 3枚 | **121枚** | 8日 |
| **デジタル** | 217 | 65日 | 2枚 | 22枚 | **29日** |

- **フィルムの `shotAt` は撮影日ではなくスキャン日時。** 121枚が全部同じ `15:02`。
  カメラ情報も279枚すべて空（フィルム枚数と完全一致）。スキャンなのでEXIFにカメラが無い
- **デジタルの `shotAt` は本物の撮影時刻**（17:38 / 17:37 / 17:05 とばらける）

→ **フィルムは少数の大きな塊（スキャンした回）、デジタルは多数の小さな日。**
   同じ「日ごと」ルールではどちらも上手くいかない。
   区切りは**カレンダーの日ではなく「時間の切れ目」**であるべき
   （時刻が固まっているものを1束とし、大きく空いたところで切る）。

### ロールの自動判別はできない

オーナーの希望「ロールで分けれたらいいよね」は自動では実現できない。

- ファイル名が複数世代で混在: `IMG_N.jpg`(73) / `DSCFN.jpg`(43) /
  `IMG_N-positive.jpg`(42) / `N.JPG`(14) など
- 2026-06-18 の121枚の連番は **6〜9380 の範囲に76箇所の飛び**。規則が無い
- オーナー談「本当の撮影日を確認する手段がない」

→ ロール単位を実現するなら**束を作る/分ける操作が必要**。既存279枚を遡って
   自動で分けることはできない。

### オーナーへの聞き取りで確定した事実（2026-07-26）

- **参照物**: iPhone Air / いろはす / Nintendo Switch 2 / Switch 2 Proコン。
  「いいと思う理由」は4択すべて該当（触ったときの応え方 / 薄さ・無駄のなさ /
  見た目のシンプルさ / 道具なのに楽しい）
- **最重要の操作**: 写真の追加と削除
- **追加の痛み**: アップロード後の手間 / どれを上げたか分からない / 選ぶのがしんどい（3つとも）
- **「選ぶ」の中身**: 全体から良いのだけ残す / **順番を決めるのが難しい**
  （「似たカットから1枚選ぶ」は該当せず。比較UIの優先度は低い）
- **順番の決め方**: **時系列・物語**（隣同士のつながりや全体のリズムではない）
- **削除の実態**: 再構築時に大量削除 / 写真が被っている時 / 微妙なものは一枚ずつ
  → **大量削除と一枚ずつの間引き、2つのモードがある**
- **避けたい方向**: 硬派すぎ・業務系 / アニメーション多め
- **佇まい**: 暗室・コンタクトシートを「オシャレにシンプル化」。直訳の質感再現は禁止

## 進め方（この順で行う。決定済み）

**P1. 共通のページ枠を1つ作り、全タブを載せ替える** ← 最優先

軸1〜5に同時に効き、他の作業の土台になる。決めた寸法:

- サイドバー248pxは変えない
- 本文の左端は**全タブ共通で40px**。中央寄せにしない（左端が揃うことが「飛ばない」条件）
- 本文の最大幅は用途で2種類だけ: **一覧・設定=880px / 入力フォーム=560px**
- 見出しは全タブで必ず出す（「はじめに」にも付ける）
- 説明は見出しの直下に1つだけ、最大2行
- セクション間32px、セクション内の要素間12px
- Library は写真グリッドなので幅は全幅のまま。ただし**左端40pxと見出し位置は共通に揃える**

**P2. 言葉と操作の統一** — 「はじめに」へのページ見出し追加（これで
`admin-page-frame.spec.ts` の fixme を解除できる）、Hero の重複説明の解消、
全大文字英語ラベルの日本語化、追加ボタンの統一、空説明の "…" をやめる。

**P3. 行部品の作り分け** — Settings / Series / Pricing が同じ汎用リストを使うのをやめ、
それぞれの用途に合った形にする。ここが「AI感の削減」の本体。

**P4. 可愛さと動き** — 土台が揃ってから。数値の入れ替わり、チェックの付き方、
空状態の佇まい、文言の温度。**先にやると「散らかった画面に飾りを足す」ことになるので後回し。**

**並行して進める完成度の穴**: Q-12（選択モード中も検索を残す）、
読み込み中のプレースホルダ（軸6）。
