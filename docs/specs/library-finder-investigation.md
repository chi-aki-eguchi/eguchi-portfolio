# Library を「写真専用のFinder」へ発展させられるか — 調査と3案

**実装前の調査資料。この文書の時点で製品コードは1行も変えていない。**

Finder の見た目を真似るのではなく、次の性質を写真管理向けに取り入れられるかを、
現在のコードの事実に基づいて検討する。

- 軽いサムネイルと必要な情報だけを一覧で扱う
- 巨大な元画像やRAWは残さず、公開用の軽量画像とサムネイル、
  そして整理に必要な情報だけを持つ
- 列の表示、並べ替え、絞り込み、グループ化
- 選択した写真の右側詳細パネル / 一括編集 / 条件を保存するスマートフォルダ
- グリッド、コンタクトシート、詳細リストを用途で切り替える
- 自動束は固定構造ではなく、グループ表示の一種類
- フィルムとデジタルで撮影日時の信頼性が違う
- スマホでは3ペインを縮小せず、一覧→詳細の画面遷移にする

---

# 0. 事実確認（コードを読んで確かめたこと）

## 0-1. 保存されている画像は3段階。元ファイルは残さない（これは方針どおり）

| 段 | 実体 | 生成 | 場所 |
|---|---|---|---|
| 「原本」 | **最長辺3200pxのJPEG（mozjpeg q92）** | アップロード時に必ず縮小 | `photos/<時刻>-<名前>.jpg` |
| 中 | 幅1920pxのWebP q85 | 同時に生成 | `medium/<名前>.webp` |
| 小 | 幅640pxのWebP q82 | 同時に生成 | `thumbs/<名前>.webp` |

`packages/web/src/api/index.ts:1419`（3200px化）、`:547-550`（サイズ定数）、
`:593-617`（生成）。

**ユーザーが選んだ元ファイルはサーバーへ渡った後、縮小されてから保存され、元は捨てられる。**
コード内のコメントにも「保管しているのは3200pxの最適化済み画像（1〜3MB）で、
60MBのカメラ原本ではない」と書いてある（`:798`）。

さらに **保存版JPEGはEXIFが剥がされている**（`:1445-1446`のコメント）。
つまり**アップロード後にEXIFを読み直すことは永久にできない**。
これは既存496枚について既に起きたことで、後から取り返せない。

> **この方針自体は問題ではない。** 目標は「原本保管庫」ではなく、
> 「軽量な公開用画像と、整理に必要な情報だけを持つ写真管理環境」。
> 巨大な元画像やRAWを残さない構成は、そのまま維持する。
>
> **問題は、捨てる前に十分な情報を抜き取れていないこと。**
> 何が抜けていて何が足りないかは `docs/specs/photo-metadata-extraction.md` に整理した。

なお縮小の基準が2種類ある。原本は `fit:"inside"` で**最長辺**3200px、
サムネと中サイズは `resize({width})` で**幅**基準（`:559`）。
そのため縦位置の写真のサムネは「幅640px・高さはもっと大きい」になり、
横位置より重い。過去に `srcset` を試して失敗したのはこの食い違いが一因。

## 0-2. 一覧は既に「軽いサムネイル」を使っている

グリッドのタイルは `adminPhotoSrc(photo, 400, 70)` を呼び、
幅400px以下なので **640pxのWebPサムネ**が選ばれる（`admin.tsx:5489`、`:1527`）。
原本3200pxは一覧では使われない。

ただし **400px枠に640pxを読み込んでいる**ので、等倍表示では1.6倍、
実際のタイル（PC既定220px前後）では約3倍のピクセルを落としている。

配信は、R2の公開URLが設定されていればサーバーを経由しない。
ただし **`rotationDeg` が0でない写真だけは必ずプロキシ経由**になる
（`src/api/index.ts:570-590`）。

サムネが欠けている写真を後から作り直す口は既にある（`:2596-2660`）。

## 0-3. 保存されているメタデータ

`photos` テーブルは25列（`src/api/database/schema.ts:4-65`）。

**EXIFから取り込んで保存しているのは7項目だけ**（`src/api/index.ts:1456-1495`）:

`shotAt` / `camera` / `lens` / `focalLength` / `fNumber` / `exposureTime` / `iso`

**読んでいるが保存していないもの**: `DateTimeDigitized`。
アップロード時にフィルムの日時を決めるためだけに使い、捨てている
（`admin.tsx:3499`、`src/web/lib/upload-date.ts`）。

**そもそも読んでいないもの**: GPS、EXIFのOrientation、色空間、露出補正、測光方式、
フラッシュ、ホワイトバランス、シャッター回数、レンズのシリアル、
IPTC/XMPのキーワード・著作権・キャプション。

**列として存在しないもの**: 評価（星）、フラグ、キーワード／タグ、
撮影日時の出どころ、平均の明るさや主要色、手動の束。

分類の手段は **カテゴリ（1つ）とシリーズ（1つ）だけ**。
向きは `width`/`height`/`rotationDeg` から毎回計算している（`admin.tsx:2240`）。

## 0-4. 撮影日時の信頼性は、いま「暗黙」でしか区別されていない

デジタルは EXIF の `DateTimeOriginal`（無ければ `Image.DateTime`）をそのまま使う。

フィルムは違う。スキャナや現像所は撮影日を知らないので、
`DateTimeDigitized`（デジタル化した日時）を使い、それも無ければ
**ファイルの更新日時**を使う（`src/web/lib/upload-date.ts:8-32`）。

つまり **フィルムの `shotAt` は「撮った日」ではなく「デジタル化した日」**。
実測でもフィルム279枚のうち121枚が完全に同一時刻だった。

**問題は、どちらの意味で入った値かを記録する列が無いこと。**
`filmType` が「フィルム」かどうかから間接的に推測するしかない。
手で正しい撮影日を入れ直しても、それが「手入力の正確な値」なのか
「スキャン日時のまま」なのかを区別できない。

## 0-5. 一覧のデータ取得は「全件・全列・一度きり」

管理画面は `GET /photos?all=1` を1回呼び、**496枚すべてを全列**受け取る
（`admin.tsx:897`、`src/api/index.ts:1295-1334`）。
ページ送りは無く、`limit` を渡さなければ上限も無い。
`description` や `meta` など一覧に不要な長い文字列も全部載る。

**絞り込み・検索・並べ替えはすべてブラウザ側**。
検索は9つの項目に対する `.includes()` の総当たりで、索引は無い
（`admin.tsx:2406-2422`）。

## 0-6. Finder的な部品は、実はかなり揃っている

| 欲しい性質 | 現状 | 場所 |
|---|---|---|
| 軽いサムネイル | **あり**（640px WebP） | `index.ts:547` |
| 絞り込み | **あり・11種**（検索/カテゴリ/シリーズ/サイズ/媒体/向き/Featured/公開/日時なし/撮影情報なし/最近） | `admin.tsx:2401-2500` |
| 並べ替え | **あり・8種**（手動/登録日±/撮影日±/シリーズ/サイズ/媒体/カメラ） | `admin.tsx:2666-2700` |
| スマートフォルダ | **あり**（12条件のAND、名前を付けて保存） | `admin.tsx:1552-1566` |
| 右側詳細パネル | **あり**（PC固定・タブレット引き出し・スマホ下シート） | `admin.tsx:6568-6590` |
| 一括編集 | **あり**（表形式7列の行内編集＋一括カテゴリ/シリーズ/公開/削除/回転） | `admin.tsx:7379-7445` |
| 仮想スクロール | **あり**（行の高さは一様） | `admin.tsx:1606-1675` |
| 重複検知 | **あり**（内容ハッシュ） | `index.ts:1425` |
| グループ化 | **無い** | — |
| 列の出し入れ | **無い**（表は7列固定） | `admin.tsx:7408-7433` |
| 詳細リスト表示 | **半分だけ**（表モードはあるが仮想化されておらず、並べ替えもできない） | 同上 |

**結論: 足りないのは「グループ化」「列の可変」「表示形式の切り替え」の3つで、
土台はほぼ揃っている。**

## 0-7. スマートフォルダの現状の限界

条件は12個の固定フィールドのANDのみ。
**自由文検索・日付の範囲・OR・入れ子・並べ替えや列構成の保存はできない。**
保存先は `site_settings` の1行にJSON文字列（`admin.tsx:2192`）。

## 0-8. 表モードの現状の限界

`BulkEditTable`（`admin.tsx:7379`）。

- 列は7つ固定（選択/サムネ/タイトル/カメラ/レンズ/シリーズ/Size/媒体）
- **仮想化されていない**。`photos.map()` で全行を描画する
- 列見出しをクリックしても並び替わらない
- 選択モードや並べ替えモードとは排他で、切り替えると選択が消える

496行なら耐えるが、行ごとに複数の入力欄があるため、
グリッドより明らかに重い。枚数が増えると最初に破綻する場所。

# 1. 現在の仕組みで既に使えるもの

そのまま流用できる:

1. **画像の3段構成**（サムネ/中/原本代わり）と幅による自動選択
2. **サムネの作り直し口** — 新しいサイズ段を足すときも同じ仕組みが使える
3. **11種の絞り込みと8種の並べ替えの計算部分** — UIから切り離せば新ビューでも使える
4. **スマートアルバムの条件型** — 拡張の出発点になる
5. **詳細パネル**の3段レスポンシブ（PC固定/引き出し/下シート）— 望む形に既になっている
6. **選択モデル**（3モード・範囲選択・全選択）
7. **仮想スクロール**の考え方（overscan 8行 + 先読み8行）
8. **B-1 の `photo-band.ts`** — 撮影のまとまりを出す計算
9. **B-2 の `virtual-sections.ts`** — 区画ごとに列数・行高が違う一覧の位置計算
10. **一括編集の保存経路**（行内編集の競合対策込み）

考え方だけ流用し、作り直すもの:

- 表モード（列固定・非仮想化のため、拡張より作り直しが近い）
- 検索（総当たり `.includes()` のまま列を増やすと遅くなる）

# 2. 新しく必要なデータ

**必須**（グループ化と信頼性の表示に要る）:

| 項目 | なぜ要るか | 大きさ |
|---|---|---|
| `shotAtSource` | 撮影日時が「EXIFの撮影時刻」「EXIFのデジタル化時刻」「ファイル更新日時」「手入力」のどれかを記録。フィルムの束を正しく扱うために必須 | 列1つ |
| 保存済みビュー | 列構成・並び順・グループ化・絞り込みをまとめて保存（＝本当のスマートフォルダ） | 既存のJSON設定を拡張 |

**あると効く**（Finder的な仕分けに要る）:

| 項目 | なぜ要るか | 大きさ |
|---|---|---|
| `rating`（0〜5）または `flag` | 「採用/保留/没」の仕分け。カテゴリとシリーズは意味が違うので代用できない | 列1つ |
| キーワード（タグ） | 1枚が複数の分類に属せる唯一の手段。いまは1カテゴリ1シリーズだけ | 別テーブル推奨 |
| `searchText` | 検索対象を正規化して1列に持てば、総当たりが1回で済む | 列1つ |

**将来の選択肢**（今は不要）:

- GPS（地図でグループ化するなら）
- 平均の明るさ・主要色（「暗い写真だけ」の絞り込み）
- 手動の束（`docs/specs/library-band-decisions.md` 判断2で検討済み）

**注意**: EXIF由来の追加項目は、**既存496枚については二度と取れない**。
保存版JPEGからEXIFが剥がされているため。新しく足せるのは
「これからアップロードする写真」だけ。既存分は手入力になる。
一方、色や明るさなど**画像そのものから計算できるものは既存496枚でも取れる**。
詳しくは `docs/specs/photo-metadata-extraction.md`。

# 3. 元画像を変更せず高速化する方法

R2の中身も `photos` の画像列も一切書き換えずにできること。

| # | 方法 | 効果 | 難しさ |
|---|---|---|---|
| 1 | **一覧用の軽いAPIを足す** — `description`/`meta` を返さず、一覧に要る列だけにする | 初回読み込みの転送量が減る。DBも画像も無変更 | 小 |
| 2 | **さらに小さいサムネ段（例: 幅256px）を追加** — 詳細リストの16〜40px枠用 | 詳細リストで640pxを読む無駄が消える。既存の作り直し口をそのまま使える | 小〜中 |
| 3 | **回転済みサムネを別キーで持つ** | `rotationDeg≠0` の写真がプロキシを経由しなくなり、R2から直接配信できる | 中 |
| 4 | **検索用の正規化文字列を持つ** | 9項目の総当たりが1回の比較になる | 小（列追加を伴う） |
| 5 | **検索・絞り込みをWeb Workerへ** | 打鍵ごとの引っかかりが消える | 中 |
| 6 | **サムネをブラウザに残す**（Cache API） | 2回目以降の一覧が即座に出る | 中 |
| 7 | **表示枠に合わせたサムネ選択** | いま400px枠に640pxを読んでいる無駄が減る | 中（過去に失敗済み。下記） |

**7は慎重に。** 以前 `srcset` を入れて公開ギャラリーで後退させた。

> **2026-07-28 訂正**: 当時「リサイズAPIが最長辺基準だから縦写真の幅が足りなくなる」と
> 記録していたが、**これは誤り**。実測で確認したところ、画像プロキシは
> `resize({ width, fit:"inside" })` を使っており、**幅だけを指定した場合は幅基準**で、
> `w=400` は横位置でも縦位置でもちょうど幅400pxになる（`src/api/index.ts:953`）。
> 最長辺基準なのはアップロード時の3200px化（`:579`）だけで、配信の経路とは別。
>
> したがって `lib/picture.ts` の `srcset` の幅の記述は正しい。
> 当時の後退の原因は**`sizes` がレイアウトと合っていなかったこと**に絞られる。
> 再挑戦する場合は、実際のグリッド幅を測って `sizes` を合わせることに集中すればよい。

**サイズ段を増やす（2番）ほうが安全**という結論自体は変わらないが、
`srcset` が使えない理由は無くなった。

**やらないほうがよいこと**: 保存している3200px JPEGの解像度や品質を下げる。
元ファイルは残さない方針なので、これが唯一の高解像度データ。落とすと戻せない。

# 4. 管理ビューの画面構成

```
┌──────────┬──────────────────────────────┬──────────┐
│ ソース    │ 一覧（表示形式を切り替え）        │ 詳細      │
│          │                              │          │
│ すべて    │ ┌ グループ見出し ─────────┐    │ サムネ    │
│ 最近      │ │ ■ ■ ■ ■ ■ ■ ■ ■    │    │ 日時      │
│ 未分類    │ └────────────────────┘    │ カメラ    │
│ ──────   │ ┌ グループ見出し ─────────┐    │ レンズ    │
│ 保存した  │ │ ■ ■ ■                │    │ 分類      │
│ 条件 ▸   │ └────────────────────┘    │ 公開      │
│ ──────   │                              │          │
│ シリーズ ▸│                              │ 複数選択時 │
│ 分類 ▸    │                              │ は一括編集 │
│ ──────   │                              │          │
│ ゴミ箱    │                              │          │
└──────────┴──────────────────────────────┴──────────┘
              ↑ グリッド / コンタクトシート / 詳細リスト
```

**一覧は3つの表示形式を切り替える。**

| 表示形式 | 何のため | 1行の中身 |
|---|---|---|
| **グリッド** | 写真を選ぶ・見る | 正方形タイルをN列 |
| **コンタクトシート** | 1本の撮影を見渡す | 小さいタイルを詰めてN列＋見出し |
| **詳細リスト** | 情報を見て直す | 1枚1行＋選んだ列 |

**グループ化は「表示形式」とは別の軸。** どの表示形式にも掛けられる。

| グループ化 | 中身 |
|---|---|
| なし | 一続き（現状） |
| **撮影のまとまり** | **B-1 の自動束**。12時間の切れ目・5枚以上 |
| 日付 | 年/月/日 |
| カメラ / レンズ / 媒体 / 分類 / シリーズ / 向き | それぞれの値ごと |

> **ここが設計の要**。自動束は「Library全体の固定構造」ではなく、
> **グループ化の選択肢のうち1つ**。オーナーの求めている扱いと一致する。

**列の出し入れ**は詳細リストのためのもの。候補になる列は、
いま持っているデータの範囲では: ファイル名 / タイトル / 撮影日時 / 登録日 /
カメラ / レンズ / 焦点距離 / 絞り / シャッター / ISO / 媒体 / 分類 / シリーズ /
表示サイズ / 公開 / 幅×高さ / 向き。

# 5. PCとスマホの操作

## PC

3ペインを同時に出す。左は畳める。詳細パネルは既に固定サイドパネル。

キーボードは既存を維持し、Finder的なものを足す余地がある
（`Space` のクイックプレビューは既にある）。

## スマホ

**3ペインを縮めない。画面を移動する。**

```
[一覧]  ──タップ──▸  [詳細]  ──戻る──▸  [一覧]
   │
   └──上部のボタン──▸ [ソース選択シート]（すべて/保存した条件/シリーズ/分類/ゴミ箱）
   └──上部のボタン──▸ [表示と並びシート]（表示形式/グループ化/並び順/絞り込み）
```

いまの詳細パネルはスマホで「高さ60%の下シート」として一覧に重なる
（`admin.tsx:6589`）。**これを画面遷移に変えるのが、この案でのスマホ側の主な変更点。**

**スマホには現在タッチ専用の処理が1つも無い**（`admin.tsx` に `onTouchStart` なし）。
そのため範囲選択・全選択・クイックプレビュー・回転はスマホから使えない
（詳細は `docs/specs/admin-library-states.md`）。
新ビューを作るなら、ここで長押し＝選択モードを入れるのが自然な機会。

# 6. 案A — 現在のテーブルモードを拡張する

いまの `BulkEditTable` を、列の出し入れ・列見出しでの並べ替え・仮想化・
グループ見出しに対応させる。グリッドと表の2本立てのまま。

**やること**
- 表を仮想化する（`virtual-sections.ts` を1列の区画として使う）
- 列の定義を配列にし、表示する列を保存する
- 列見出しクリックで並べ替え（既存の8種の計算を再利用）
- グループ見出しを表に入れる
- スマートアルバムに「列構成と並び順」を保存できるようにする

**やらないこと**: グリッドの構造、詳細パネル、スマホの画面遷移。

**良い点**
- 変更が `BulkEditTable` とその周辺にほぼ収まる
- 既存のグリッドが無傷なので、壊しても影響が局所的
- 一番重い画面（非仮想化の表）が最初に直る

**悪い点**
- グリッド側にはグループ化が入らないので、**コンタクトシートは実現しない**
- 表とグリッドで「表示形式の切り替え」という考え方が揃わず、
  「Finderのような統一感」は出ない
- スマホの体験は変わらない

# 7. 案B — 新しい管理ビューを追加する

いまのLibraryを残したまま、**別のタブ**として3ペインの管理ビューを新設する。
グリッド／コンタクトシート／詳細リストの3表示、グループ化、列の出し入れ、
保存済みビューを最初からその中に作る。

**やること**
- 新しいタブと3ペインの枠
- 一覧の中身を3表示形式で切り替え（すべて `virtual-sections.ts` の上に載せる）
- グループ化の仕組み（自動束はその1種類）
- 列の定義と保存
- 詳細パネルは既存を再利用
- スマホは一覧→詳細の画面遷移で作る

**やらないこと**: 既存Libraryの削除・変更。

**良い点**
- **既存のLibraryが一切壊れない。** いつでも戻れる
- 3表示形式・グループ化・スマホ遷移を、しがらみ無しに設計できる
- 使ってみて良ければ既存Libraryを畳む、悪ければ捨てる、が選べる
- B-2 の設計がそのまま生きる

**悪い点**
- **写真管理の入口が2つになる**。どちらで何をするか分からなくなる期間ができる
- 絞り込み・並べ替え・選択の処理が新旧で二重になる（共通化しないと両方直す羽目になる）
- 全部作り切るまで「良くなった」と感じられない

---

# 8. 案C — Library全体を再設計する

いまのLibraryを3ペイン構成へ作り直す。既存のグリッドは「表示形式のうち1つ」
として吸収し、表モードは「詳細リスト」に置き換える。

**やること**: 案Bの全部＋既存Libraryの置き換え＋3モード（通常/選択/並べ替え）の
再定義＋既存の全smokeテストの追従。

**良い点**
- 入口が1つのまま、一貫した設計になる
- 「刷新した」と最も感じられる

**悪い点**
- **`admin.tsx` は8332行あり、Libraryはその中心**。段階的に出せない
- 既存の52本のsmokeテストの多くがLibraryに触れており、まとめて直す必要がある
- 途中で止められない。止めると壊れたまま残る
- オーナーが画面を確認できるのが最後になる

# 9. 各案のリスクと工数

| | 案A 表の拡張 | 案B 新ビュー追加 | 案C 全体再設計 |

# 10. 最小の試作範囲

**「表示形式 × グループ化」が本当に成立するかだけを確かめる。**

作るもの（案Bの枠だけ、既存Libraryには触れない）:

1. **グループ化の共通の入口** — 写真の配列と「何でまとめるか」を受け取り、
   区画の配列を返す純関数。自動束（B-1）はその実装の1つ。
   日付・カメラ・媒体も同じ形で足せることを、この時点で確かめる
2. **区画 → 仮想スクロール** — B-2 の `virtual-sections.ts` へ渡すだけ
3. **表示形式を3つ**、ただし見た目は素のままでよい
   （グリッド＝正方形N列 / コンタクトシート＝小さくN列 / 詳細リスト＝1列）
4. 読み取り専用。**編集・保存・選択は入れない**

これで確かめたい問い:

- 同じ区画の仕組みで、3つの表示形式を本当に表現できるか
- グループ化を切り替えたとき、スクロール位置と描画が破綻しないか
- 496枚で速度が保てるか（B-2 の実測では区画1000でも1回0.8マイクロ秒）
- **絞り込みを変えたとき、束の折り畳み状態が保てるか**（下記の問題）

成立しなければ案Aへ落とす。成立すれば案Bを続ける。

# 11. B-2 / B-3 をそのまま進めるべきか

## B-2（高さが揃わない仮想スクロール）— **そのまま進めてよい。むしろ価値が上がる**

`virtual-sections.ts` は「区画ごとに見出しの有無・列数・行の高さが違ってよい」形で
作ってある。これは今回の設計で **3つの表示形式すべてを表現できる**ことを意味する。

- 詳細リスト = 1列・行高は文字の高さ
- グリッド = N列・行高はタイルの高さ
- コンタクトシート = 多めのN列・行高は小さいタイル

B-1 に依存させなかったのも正しかった。区画がどのグループ化から来ても扱える。

**ただし、つなぐ前に決めることが1つある**（コードに明記済み）。
この関数は数値がNaNや負のとき例外を投げるが、既存の仮想スクロールは
安全な既定値を返して描画を続ける。画面につなぐと真っ白になる経路が増える。

## B-3（見出しのUI）— **設計を変えるべき**

当初のB-3は「コンタクトシートの見出し」を想定していた。今回の枠組みでは、
見出しは**コンタクトシート専用ではなく、3つの表示形式すべてに出る共通部品**になる。

変えるべき点:

1. **見出しはグループ化の産物であって、コンタクトシートの部品ではない**
2. 見出しは自分の操作を持つ（その塊だけ選択する／畳む）
3. 表示形式ごとに見た目は変わるが、**中身と操作は同じ**

## B-1 について見つかった問題 — **絞り込みと相性が悪い**

`photo-band.ts` の束のIDは、**その束に入っている写真IDの集合から作っている**。
同じ写真構成なら毎回同じIDになるので、B-1単体では正しい。

しかしFinder的な使い方では絞り込みが日常的に変わる。

> 例: ある撮影の20枚が1つの束になっている。「未公開だけ」で絞ると15枚に減る。
> **写真の集合が変わるのでIDも変わり、同じ撮影なのに別の束として扱われる。**
> 畳んだ状態・選択・スクロール位置が保てない。

**対処の方向**（まだ決めていない。実装もしない）:

- 束のIDを「最も古い写真のID」など**中身に左右されない目印**から作る
- または、グループ化は**絞り込み前の全体**に対して行い、絞り込みは表示だけに効かせる

**どちらを選ぶかで、束が「写真の集まり」なのか「撮影という出来事」なのかが決まる。**
後者のほうがFinder的な使い方には合うが、B-1 の返す形を変えることになる。

**結論: B-2 は進めてよい。B-3 は始める前に設計を変える。B-1 は形を1か所直す必要がある。**

# 12. オーナーが判断すべき点

| # | 判断 | 選択肢 | 決めないと進めないもの |
|---|---|---|---|
| **1** | どの案で進めるか | A 表の拡張 / **B 新ビュー追加** / C 全体再設計 | すべて |
| **2** | **元画像を捨てる前の抽出をどこまで足すか** | 手元に来ている値だけ（4項目）/ 読み取りも足す（11項目）/ いまのまま | `photo-metadata-extraction.md` 参照。**遅れた分だけ永久に欠ける** |
| **3** | 撮影日時の出どころを記録するか | する（列1つ）/ しない | フィルムの束の正しさ |
| **4** | 評価（星）とキーワードを持つか | 両方 / 評価だけ / どちらも無し | 仕分けの手段 |
| **5** | 保存済みビューに何を含めるか | 絞り込みだけ（現状）/ ＋並び順 / ＋列構成とグループ化 | スマートフォルダの意味 |
| **6** | 束は「写真の集まり」か「撮影という出来事」か | 集まり（現状のB-1）/ 出来事（IDを変える） | 絞り込み中の振る舞い |
| **7** | スマホの詳細を画面遷移にするか | する / いまの下シートのまま | スマホ側の作り直し量 |
| **8** | 既存Libraryをいつ畳むか | 新ビューが十分になったら / 当面2つ残す / 畳まない | 案Bを選んだ場合だけ |

**おすすめ: 案B。**
理由は、既存Libraryを壊さずに3ペイン・3表示形式・グループ化を試せて、
うまくいかなければタブごと捨てられるため。案Aはコンタクトシートに届かず、
案Cは途中で止められない。

**先に決めてほしいのは判断1と判断6。** 他は試作の後でも間に合う。
