# 公開サイトとデータモデルの方向（オーナー確定分）

> 2026-08-14 に、外部調査（Manus 2回分）を実リポジトリと照合して評価し、
> オーナーが決めた事項をここへ集約する。**個別の実装依頼はこの文書に従属する。**
> 管理画面の見た目・使用感の正本は `docs/specs/admin-renewal-goal.md`（6軸）であり、
> この文書はそれと競合しない。構造・データ・公開面の判断だけを扱う。

## 0. 前提（この文書を読む人が最初に知るべきこと）

このリポジトリは **akieguchi.com であると同時に、Portfolio Kit として販売する商品**である。
購入者ごとに専用環境へ配布される（`DISTRIBUTION.md`）。

したがって **機能を1つ足すことは、写真が0枚の他人のサイトにも同じ空欄が現れること**を意味する。
新しい入口・新しい入力欄を作るときは、**0件のときに何が見えるか**を必ず先に決める。

## 1. 公開サイトの構造 — 維持する

**Top / Gallery / Series / Series詳細 / About / Contact を維持する。**（+ Portfolio Kit の販売導線）

外部調査で、この規模（写真約500枚・作品群が少数・活動記録なし）で第一層を増やして
良くなっている実例は**見つからなかった**。第一層が多い写真家サイトは、実際に
News / Publications / Articles の中身を持っている。

- **Series を Project に改名しない。** URL・sitemap・canonical・OGP・言語alternate・
  404判定を全部触って、得られるのは呼び名だけ。
- 公開側のフィルター軸を増やさない（現在はカテゴリと媒体の2軸）。

## 2. 作らないもの（再提案しない）

技術的に載らない、または必要なデータが無い:

private link / signed URL / access control / Public-Professional二室 / PDF生成 /
予約公開・期間限定公開 / AI検索・AI推薦 / 版管理(versioning) / 外部共有 /
高解像度ダウンロード / 公開コメント / 3D展示室 / 公開地図 / 場所によるフィルター

理由はいずれか: **認証は共有パスワード1本でユーザーモデルが無い** /
**ジョブ実行基盤が無い（単一プロセス）** / **必要な列が無い（撮影地など）** /
**購入者がホストする商品に運用責任を渡すことになる**。

新エンティティも作らない: Project / Selection / Activity以外 / Publication / CV /
Archive / Private Selection / rights metadata / sequence。

## 3. 写真の時間 — フィルムとデジタル

### 3-1. 実測（2026-08-14 / 本番Turso / 読み取りのみ / HEAD `337bcdd`）

日付・commitを添えた監査結果として記録する。再測定できる値であり、現在の事実として
恒久的に扱わない。

| 測定 | 結果 |
|---|---|
| `shotAtSource` | **496枚が `legacy`**、`exif_original` が1枚。**出どころで判別できない** |
| フィルムの `camera` / `camera_make` / `camera_model` | **すべて0件** |
| デジタルの `camera` | **217枚すべてに有り** |
| フィルムの `shot_at` の散らばり | 全部同じではない。例: 2026-06-18 が 02:45 / 02:57 / 04:10 / 04:15 / 04:36 と分単位で刻まれる |
| 旧 `meta` 列に中身がある行 | **0件** |

> **`docs/specs/admin-renewal-goal.md` の「121枚が全部同じ 15:02」は、この測定と
> 合っていない。** あの記録を前提に判断しないこと。

### 3-2. 決定

**保存の仕方は現状維持。直さない。**

- フィルムはカメラ情報を保存せず、**デュープした時刻だけ**を `shotAt` に持つ。
  これはオーナーの意図どおりの動作である（デュープ機のEXIFは、その写真を撮った
  カメラの情報ではないため）。
- `shotAt` は**時間軸上の位置**として並べ替えに使い続ける。フィルムとデジタルの
  共存はこれで既に成立している。

**公開面での見せ方は「B案 = 何の日付か分かる形で出す」**（オーナー決定 2026-08-14）。

| 場所 | 決定 |
|---|---|
| Lightbox の撮影情報 | 出どころが分かるラベルにする。フィルム＝**スキャン**、デジタル＝**撮影**。いまは両方 `Date` で、Camera / Lens と並ぶため撮影日に見える |
| `large-format` レイアウトのキャプション | **フィルムは年を出さない**。1行のキャプションに注記を足すと写真の下が説明的になり、静けさを損なう。撮影日が分かるときだけ年を出す |

**判定は `filmType` を使う。** `shotAtSource` は使えない（496枚が `legacy`、かつ
**公開API `/photos` の応答から除かれている**ため、そもそもクライアントに届かない）。

### 3-3. 撮影日は別の列にする（次段階）

**分かっている撮影日を、デュープ時刻とは別に持つ。** 理由: いま撮影日を手入力すると
`shotAt` が上書きされ、**デュープ時刻が消える**。オーナーの「別枠の時間管理」に反する。

- 列を1本追加（nullable）。`shotAt` は触らない。データ移行は不要
- 公開面で**年を単独で出すのは、この列に値があるときだけ**
- `schema.ts` / `schema.postgres.ts` の両方 + migration 2本 + 契約チェック

**既に存在する救済操作**（新規に作らない）: 誤って入った撮影日をクリアする
`shotAt_clear`、撮影日が未設定の写真だけへ一括入力する操作。

## 4. シリーズ

### 4-1. Gallery からの除外は**シリーズごと**にする

いまはサイト全体で1つの設定（`galleryExcludeSeries`、既定 off）。これを**既定値**として残し、
**シリーズ側で上書きできる**ようにする。

置き場所は `series.themeConfig`（既にレイアウト・背景色・並べ方を持つJSON列）。
**新しい列も新しい settings キーも要らない。**

### 4-2. シリーズ内の並び順を持てるようにする

オーナー「シリーズごとに配置や並びを変えられると良い」。
**配置は既にできる**（`themeConfig` のレイアウト）。**並びだけが無い。**

いまは `photos.sortOrder` がライブラリ全体で1本しかなく、「シリーズAの中で並べ替える」＝
「ライブラリ全体の並びを動かす」になっている。

→ **`photos` に nullable な列を1本追加**する。`NULL` は「全体の並びに従う」を意味させ、
既存の見え方を変えない。**中間テーブル（多対多）は作らない**（必要である証拠が無く、
作ると Gallery除外・表紙フォールバック・キャプションが全部分岐する）。

### 4-3. Work（仕事）は Series の「種類」として持つ

新しいテーブルを作らない。Series は既に slug / タイトル / 副題 / 説明文 / 表紙 /
専用ページ / 写真の所属 / 並び順 / 公開設定 を持っており、Work に必要なものと同じ。

**種類を1つ足して一覧を分ける**だけにする（作品 / 仕事）。

- **写真がある仕事** → Series（種類 = 仕事）
- **写真が無い実績**（掲載・展示・受賞などの文字情報） → §5 の記録

公開面に出すかは別の判断であり、後から変えられる。仕事が少ないうちは管理画面にだけ
持っていてよい。

## 5. 展示・掲載の記録

**1テーブルだけ作る。** Activity / Publication / Press を分けない。

オーナーの条件は「まだいっぱい活動していない・学生・**緩くできるように**・
ただし**プロ用にちゃんとしたものも**」。1テーブルで両立させる。

- 項目はほぼ全部**任意**にする（日付だけ・場所だけ・リンクだけでも成立する）
- **0件のときは入口ごと出さない。** これで活動が少なくても空欄が見えない
- 記録が増えれば、そのまま展示歴として読める

**「0件なら入口を消す」は既存の仕組みである**（シリーズのナビ、Portfolio Kit の表示制御が
同じ作り）。新しい発明ではない。

## 6. Top のテンプレート

**オーナーが最も重視する機能。** 「いろんなテンプレートが保存できて、切り替えができる。
ランダムでどれかが出るようにすることも**できる**」。

背景にある製品方針: **「あっちも選べるし、こっちも選べる」。ただし最初の画面は
速く、カクつかずに出ること。**

### 6-1. 置き場所

**新しいテーブルは作らない。** `site_settings` にJSONで持つ。
`smartAlbums`（保存した絞り込み条件をJSON文字列で持つ）と同じ作りをなぞる。

### 6-2. テンプレートに含める範囲を先に固定する

**ここを決めないと、170項目の設定を丸ごとスナップショットする作りになり、
テンプレートを切り替えたら書体まで変わる事故が起きる。**

含める範囲は **「Homeを開いたときに見えるもの」だけ**に閉じる。

| 含める | 含めない |
|---|---|
| Top写真の選び方と選んだ写真 | 書体・文字サイズ・色 |
| Topのレイアウトと枚数 | ナビ・フッター |
| Hero の写真と表示方法 | Gallery / Series ページの設定 |
| シリーズ帯を出すか | 連絡先・プロフィール |
| Home の一文 | |

### 6-3. ランダムは速度と引き換えではない

いま `topWorksMode=random` のとき、`server.ts` は **Homeの画像先読みを止めている**。
抽選をブラウザ側でやるため、サーバーがどの写真を出すか知らないからである。

**テンプレートのランダムは、サーバー側で抽選する。** HTMLを返す瞬間にどのテンプレートか
決まっていれば、そのテンプレートの写真の先読みタグを入れられる。HTMLは元々
`Cache-Control: no-store` なので、訪問ごとに違うものを返すことに障害は無い。

→ **固定切り替えもランダムも、先読みが効く。** 既存の「全写真からランダム」だけが
遅いので、ついでに同じ方式へ寄せられる。

### 6-4. 前提

**Top選抜のピッカー（写真IDのCSV入力をやめる）が先。**
写真IDをカンマ区切りで打ち込むものを「テンプレートとして保存」しても、
保存した中身が読めない。選ぶUIができてはじめてテンプレートが意味を持つ。

## 7. note

**note.com へ飛ぶ形は維持する。**（サイト内に文章を書く仕組みは作らない ＝
更新を約束するページを増やさない）

現状: About ページ下部の Journal 節に、サムネイル + 日付 + タイトル + 抜粋の
3列カードで表示している。**中身は既に十分出ている。**

問題は置き場所と抜粋の切れ方。

| 決定 | 内容 |
|---|---|
| 置き場所 | **Home へ移す。** 写真の後、依頼CTAの前。「作品を見た → いま何を考えているか → 声をかける」 |
| About | **消す。** 同じものへの入口を2つ作らない（シリーズの入口を1つに絞ったのと同じ判断） |
| 件数 | **1〜2件だけ。** 3列のカードをHomeに並べると写真より記事が目立つ |
| 読み込み | 最初の画面より下に置き、**Homeの表示開始を待たせない** |
| 抜粋 | 先頭120文字の機械切りをやめ、**句点で止める** |

## 8. 整理

`photos.meta`（旧フリーテキスト。「新UIは書き込まない」とコメント済み）は
**実データ0件**を確認した。廃止できる。

`web/lib/photo-band.ts`（時間の切れ目で写真を束ねる実装）は**テスト以外から参照が無い**。
オーナーの「1ロールずつスキャンしている / その順番は保ちたい」と、実測の
時間の刻まれ方に合うので、**Library へ接続する方向**。ただし現在の定数
（12時間間隔）は実データ（10分〜1時間）に合っていないので、測り直して調整する。

**ロールの切れ目はデータに記録されていない。** 順番は保たれている可能性が高いが、
どこで1本が終わるかは分からない。自動判別に頼らず、**画面で区切る操作**を前提にする
（`photo-band.ts` には手動束ねの型が最初から用意されている）。
