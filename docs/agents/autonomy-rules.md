# 自律実行ルール（Autonomy Rules）

> **ARCHIVED / SUPERSEDED — 2026-07-27**
>
> 旧夜間・自走運用の履歴。現在の通常セッションへ自動適用しない。
> 現行の役割、安全境界、停止条件は`AGENTS.md`、現在地は`task.md`冒頭Current State。
> オーナーが新しい自律実行を直接依頼した場合も、旧ルールをそのまま再開せず範囲を確認する。

対象: このリポジトリで Claude Code（使用モデルは固定しない。作業内容・利用可能性・残りクレジットに応じてその都度選ぶ）が自律的に作業するすべてのセッション。
夜間実行（claude-code-night-run.md）にも常に適用される。
このファイルは CLAUDE.md から参照される補助ルールであり、§0 invariants より優先されることはない。

---

## 1. 大原則

- 作業中に人間へ質問しない。不明点はこのファイルの判断表に従って自分で決め、決定ログに理由を残して先へ進む。
- 迷ったら常に「壊さない方」「あとで元に戻せる方」を選ぶ。
- ゴールは各タスクの「完了の定義」。全項目を満たすまで作業を続け、途中で満足して止まらない。
- 解決できないタスクは止まらず「要相談」に回して次のタスクへ進む（セッション全体を止めない）。
- 着手前に `task.md` 最新 Handoff と `docs/agents/task-queue.md`（指示書の束）を確認する。タスクが task-queue 由来なら、その指示書のタグ（[要オーナー判断] 等）と停止条件が本ファイルより優先される。

## 2. 完了の定義（Definition of Done）

タスク指示に個別の完了条件が書かれていない場合、以下をすべて満たしたら完了とする:

1. 変更がタスクの目的を満たしている
2. `bun run check` がすべて成功している
3. §0 invariants に違反していない
4. 決定ログ（§6）を書いた
5. push はしていない（コミットまでで停止し、承認待ち状態にする）

## 3. 判断分岐表

| 状況                                                                   | とるべき行動                                                                                                                               |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 仕様が曖昧                                                             | 既存コードの慣習・デザイントーン（photographer's atelier）に合わせる。前例がなければ最小限の変更にとどめる                                 |
| 実装方針が2つ以上あって迷う                                            | 影響範囲が小さい方を選ぶ。両案と選んだ理由を決定ログに残す                                                                                 |
| 新しいライブラリが必要に見える                                         | 追加しない。既存の依存関係で解決できなければ「要相談」で保留                                                                               |
| `bun run check` が失敗                                                 | 自分で原因を直して再実行する                                                                                                               |
| 同じ失敗が3回続く                                                      | そのタスクを中断。状況レポートを決定ログに書き、次のタスクへ                                                                               |
| DBスキーマ変更（migration）が必要                                      | 実施しない。「要相談」で保留                                                                                                               |
| 本番環境・本番DBに触れる必要がある                                     | 実施しない。「要相談」で保留                                                                                                               |
| APIキー・パスワード等の秘密情報が絡む                                  | 値を一切ログ・出力に書かない。必要なら「要相談」で保留                                                                                     |
| タスク同士が競合している                                               | 先に指示されたタスクを優先し、競合内容を決定ログに記録                                                                                     |
| テストが落ちて、テスト側を直したくなった                               | 実装の意図的な仕様変更に追随する場合のみ可（理由と再計算根拠を決定ログへ）。**原因を理解せずに期待値を実測値へ合わせて緑にする行為は禁止** |
| 保存キー・URL・ID の生成形式を変えたくなった                           | 既存データ（DB の url / thumbKey 等）が旧形式のまま残ることを必ず考慮。旧形式が読めなくなる変更は「要相談」                                |
| 既存の防御コード（ガード・リトライ・エラーハンドリング）が不要に見える | 消さない。不要に見える理由を決定ログに書き「要相談」へ（過去の障害対策であることが多い）                                                   |
| 新しい書き込み処理を追加する                                           | エラーを握り潰さない。`assertOk` + `onError`（またはtry/catchでユーザー可視のエラー表示）を必ず付ける                                      |
| 変更が5ファイル以上に波及しそう                                        | いったん手を止め、波及先一覧を決定ログに書いてから進める。10ファイル超は「要相談」（大規模リファクタ禁止）                                 |
| R2・DB・ファイルの「削除」を含む処理を書く                             | 新規の削除ロジックは「要相談」で保留（既存の purge 等の挙動維持は可）                                                                      |
| smoke テストを追加・変更する                                           | smoke は**本番と同じDB**につながっている。Save/Delete/Add 確定など書き込み操作をクリックするテストを書かない                               |

## 4. 自己検証ループ

各タスクごとに次のサイクルを回す:

実装 → `bun run check` → 失敗なら修正して再実行（最大3回）→ 成功したら決定ログを書く → 次のタスクへ

- 3回直しても通らない場合は §3 の「3回ルール」に従い中断・記録・次へ。
- check を飛ばして「たぶん動く」で完了扱いにすることは禁止。

## 5. 絶対禁止（Hard Stops）

以下は自律セッション中、いかなる理由でも実行しない:

- `git push` およびデプロイ（秋の手動承認が必須）
- 本番DBへの書き込み・migration の実行
- §0 invariants の変更・回避・「一時的な」無効化
- `.env` の内容や秘密情報をログ・コミットメッセージ・出力に含めること
- knowledge/wiki/ を真実のソースとして扱うこと（あくまで索引レイヤー）
- リポジトリ直下への新規 markdown ファイル追加（5枚ルール。文書は docs/ 配下へ）
- ユーザーがアップロードした写真・画像ファイルの削除や上書き
- テストの skip 化・削除・期待値の根拠なき緩和（§3 の判断表参照）
- Claude Code が設計を省いて Codex に丸投げすること（2026-07-25 にハードストップを差し替え。
  以前の「Codex に実装をさせること」禁止は、役割分担の恒久化により廃止。現行は
  設計=Claude Code / 実装=Codex。実装依頼には AGENTS.md「Codex へ渡す指示書の必須項目」
  の4項目を必ず含める。「この辺りをいい感じに」のような設計判断を含む依頼は出さない）

## 6. 決定ログ

場所: `docs/agent-logs/YYYY-MM-DD.md`（なければ作成）

各タスクごとに追記する内容:

- タスク名
- 選んだ方針（1〜2行）
- 迷った点と、そちらを選んだ理由
- 「要相談」にしたもの（あれば）
- `bun run check` の結果

## 7. セッション終了レポート

セッションの最後に、同じログファイルの末尾へサマリーを書く:

- 完了したタスク一覧
- 「要相談」で保留したタスク一覧
- 秋の判断が必要な項目。それぞれ選択肢を2〜3個に絞り、各案のメリット・デメリットとおすすめを一言添えること
- 次のセッションへの申し送り（あれば）

レポートは専門用語に頼らず、コードを読まなくても状況が判断できる日本語で書くこと。
