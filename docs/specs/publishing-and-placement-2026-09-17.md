## 2. A — 下書き保存と公開の分離（F-01）

### 2-1. 方針: 「現行の表 = 公開版」を保ち、下書きを別の表に置く

公開側の読み手（上記の API と `server.ts`）は**一切変えない**。公開操作は、下書きの内容を現行の表へ
1トランザクションで書き込む。こうすると、

- 移行後も既存の内容はそのまま公開版として残る（下書きの表が空なので、何も「下書き」にならない）。
- 本文・公開API・画像参照・OGP・サイトマップ・ナビ・キャッシュが、同じ表＝同じ公開版を読み続ける。
- 既存の「保存したらキャッシュの世代を進める」仕組みを公開操作にそのまま使える。

公開側を「公開版の表」から読むように全読み手を書き換える案（revision 参照の切り替え）は、読み手が多く
（公開API6本 + `server.ts` の4経路）、取り違えが1つでもあると下書きが漏れる。最初の段階では採らない。

### 2-2. 最初の対象と下書きの形

最初は**サイト設定**と**作品ページ（Series / Work 1本）**だけ。

```
content_drafts
  id            integer PK
  target        text     -- "settings" | "series:<id>"   (一意)
  base_hash     text     -- 下書きを作った時点の公開版のハッシュ
  payload       text     -- JSON。下の形
  updated_at    integer
  updated_by    text     -- 端末の目印（共有パスワード1本なので「人」ではない）
```

- 設定の payload: 変更したキーと値だけ（`{ "siteName": "…" }`）。空文字で既定へ戻す既存の扱いを保つ。
- 作品の payload: `series` の編集項目（題名・副題・本文・表紙・themeConfig・公開フラグ）と、
  **作品内の写真の並び**と**写真ごとの差分**（題名・説明・表示サイズ・回転・焦点・公開フラグ・差し替え画像のキー）。

**写真の共有情報を下書きで直接更新しない。** 作品の下書き中に写真の題名や回転を変えたら、その差分は payload に
残し、公開操作まで `photos` を変えない。題名だけを複製して完了扱いにしない。ライブラリ（写真一覧）からの編集は
従来どおり即時反映で、画面に「この操作はすぐ公開サイトに出ます」と明示する（§2-6）。

### 2-3. 公開操作とトランザクション境界

`POST /api/admin/publish { target, baseHash }`:

1. トランザクション開始。
2. 現在の公開版のハッシュを計算し、`baseHash` と下書きの `base_hash` の両方と一致するか確かめる。
   一致しなければ 409（別の端末で公開済み・ライブラリで変更済み）。**上書きしない。**
3. payload を現行の表へ書く（設定は `writeSettingsAtomic` と同じ書き方、作品は `series` と対象写真の行）。
4. 公開前の内容を `publish_history` に1行残す（§2-5）。下書き行を消す。
5. コミット後に `bumpPublicContentVersion()` / `bumpSettingsVersion()`、画像の後片付け（§2-5）。

途中で失敗すればロールバックされ、半分だけ公開されることはない（libSQL・PostgreSQL とも drizzle の
`db.transaction` を既に使っている）。ハッシュは対象の行を安定した順で JSON にしたものの SHA-256。

### 2-4. 競合の検出

- 下書き保存 `PUT /api/admin/drafts/:target { payload, draftUpdatedAt }`: 保存済みの `updated_at` と違えば 409。
  別の端末で古い下書きを開いたまま保存しても、新しい下書きを上書きしない。画面は「別の端末で更新されました。
  読み込み直す／この端末の内容で置き換える」を出す（置き換えは明示操作だけ）。
- 公開: §2-3 の `base_hash` 比較。

### 2-5. 履歴・復元と画像の保持

- `publish_history(id, target, published_at, before_payload, after_hash)`。対象ごとに**直近 N 件（初期 10）**だけ残す。
- 復元は「履歴から下書きを作る → 差分を確認 → 公開」。公開と同じ経路を通すので、競合検出と後片付けも同じ。
- 画像の保持: 完全削除と旧画像の後片付けは、`photos` だけでなく **`content_drafts` と `publish_history` が参照する
  キーも生存参照として数える**。`purgePhotoFromDb` の sharer 判定と、設定画像の後片付け
  （`settings-image-cleanup.ts`）の両方に同じ判定を入れる。履歴が N 件を超えて消えたときに、参照が0になった
  画像だけを消す。**過去の版を画像なしにしない。**
- ゴミ箱の30日自動削除も同じ判定を通す。

### 2-6. 利用者への見せ方

- 設定と作品の画面に「下書きを保存」「プレビュー」「公開する」を分けて置く。公開の前に、変わる項目・写真・並びを
  一覧で見せる（A-1 はこの一覧だけを先に作る）。
- 下書きのプレビューは、既存の iframe プレビューに payload を送る（作品の payload は公開APIでは読めないので、
  認証済みの `GET /api/admin/drafts/:target/preview-data` を iframe 側が読む。**公開APIへ下書きを出さない**）。
- 即時反映のまま残す操作（写真の公開・非公開、ゴミ箱、ライブラリでの編集、トップ写真の選択）は、その場で
  「すぐ公開されます」と出す。

### 2-7. 複数プロセス

現状は1インスタンス前提でプロセス内の世代番号を使う。2インスタンス以上にするなら、公開操作で
`site_settings` の `contentGeneration`（または専用の1行表）を進め、各プロセスは数秒ごとにそれを読んで
キャッシュを捨てる。**インスタンスを増やす前に入れる**。今回の範囲では1インスタンス前提を文書に明記するだけ。

- 置き場所: `series.themeConfig` の JSON に `layout: "blocks"` と `blocks` を足す。**新しい表を作らない**

## 6. 移行と復旧の共通方針

- **追加だけにする。** 既存の列・表を消さない、型を変えない。適用済み migration は書き換えない。
- PostgreSQL: `drizzle-postgres/` に追加の migration を足す（起動時に適用、台帳で冪等）。
- Turso: 起動時セーフティネットを「表の作成（`CREATE TABLE IF NOT EXISTS`）」にも対応させる（X-1）。
  DDL は drizzle が生成する SQL と一字一句そろえ、隔離した一時 SQLite（`src/api/test-support/isolated-api.ts`）で
  「schema.ts から作った表」と「セーフティネットで作った表」が同じ形になることをテストする。
- コードのロールバック（Railway で前の版へ戻す）: 追加した表は古いコードから無視されるので安全。
  ただし**新しい版で公開した内容は現行の表に書かれている**ので、コードを戻しても公開内容は戻らない。
  内容を戻すのは履歴からの復元（§2-5）で、コードの戻し方とは別の操作として手順書に書く。
- DB の復旧: Turso はポイントインタイム復元／ブランチ、PostgreSQL は Railway のバックアップを候補にする
  （**どちらも、利用中のプランで使えるか・復元にかかる時間は未確認**）。
  **本番で使う前に、隔離した複製で「移行 → 下書き → 公開 → 復元 → DB 復旧」を1回通し、日付を記録する。**
  配布先には `docs/template-release-notes.md` で「DBマイグレーションあり・事前バックアップ必須」と書く。
- 両DBで確認できない変更は「移行できる」と書かない（今回の環境には PostgreSQL が無く、PostgreSQL 経路は未実測）。

## 8. 受け入れテスト（A を実装するとき）

隔離 API（一時 SQLite と偽ストレージ）と、同じ操作の PostgreSQL 版（環境が用意できた場合）で:

1. 作品の題名・説明・並び・写真の回転を下書き保存しても、未ログインの `/api/series/:slug`・`/api/photos`・
   `/series/:slug` の HTML・OGP・サイトマップに出ない。
2. 公開すると上記すべてが同じ内容になり、`bumpPublicContentVersion` 後の HTML も新しい内容になる。
3. 公開の途中で書き込みを失敗させると、何も変わらない（半分だけ公開されない）。
4. 2つの端末に見立てた2つのセッションで、古い下書きの保存・古い基準での公開が 409 になる。
5. 公開 → 別の内容で公開 → 履歴から復元 で、1回目の内容が再現され、画像も表示される。
6. 履歴が参照する画像は、元の写真を完全削除しても消えない。履歴から外れて参照0になったときだけ消える。
7. 既存データを移行した直後、公開サイトの応答が移行前と1バイトも変わらない（同じ fixture で比較）。

## 9. 衝突しない小さな単位（参考。着手は未定）

2026-09-17 の次の作業は smoke の本番接続の遮断（backlog B-29）に決まった。以下は方針と衝突しない候補の記録で、
着手の予定ではない。

**A-1: 設定の保存前に、変わる項目を一覧で確認できるようにする。**

- スキーマ変更なし・本番データの書き換えなし・確定方針との衝突なし。
- 既存の未保存件数（`dirtyKeys`）と節ごとの変更表示を土台に、「項目名・保存済みの値 → 編集中の値」を
  保存ボタンの近くで開けるようにする。保存・Undo/Redo・プレビューの経路は変えない。
- A を実装するときの「公開前の差分確認」の画面として、そのまま使える。
