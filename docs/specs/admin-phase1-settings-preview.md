## 2. 画面幅ごとの領域構成（新）

**Admin Shell の骨格は viewport 基準、Settings 内部の再配置は container 基準**
（`admin-layout-implementation.md` §1-1）。Settings のフォーム列に
`container-type: inline-size` を置く。

| viewport | 構成 | プレビュー |
|---:|---|---|
| **320 / 390** | 1列。上部 sticky に「節名＋編集/プレビュー切替」 | 切替で全面。横並びにしない |
| **768** | 1列。節ナビは本文の上（横スクロール1行のまま） | 切替で全面 |
| **1024** | 左ナビ ＋ 節ナビ ＋ フォーム ＋ プレビュー | 既定 360px |
| **1280** | 同上 | 既定 440px |
| **1440** | 同上 | 既定 480px |
| **1600+** | 同上 | 既定 520px |

**左ナビは利用者が明示的に開閉した状態を維持する。プレビューの開閉で
自動的に畳まない**（オーナー確定 2026-07-31 / §2-1）。

**節ナビは常に縦のまま。**プレビューを開いても横帯へ変えない（P4 の解消）。
フォーム本文が狭くなったときの縦積みは container query で行う（§3-4）。

### 2-1. 【確定】幅が足りないときの優先順位

> **オーナー確定 2026-07-31。左ナビを強制的に畳んで解決しない。**
> 理由: 利用者の操作なしに Admin 全体の配置が変わる／開閉状態の保存と一時状態の
> 区別が分かりにくい／プレビュー開閉のたびに画面が大きく動く／
> 1280px でもフォーム最小 400px は確保できる。

幅が不足したら、上から順に適用する。

1. **Settings 内部を container query で再配置**（ラベル上・入力下へ）
2. **プレビュー幅を許容範囲内で縮小**（下限 320px）
3. **節ナビをコンパクト表示へ**（幅を詰める。横帯化はしない）
4. **インラインではなく「大きく表示」へ誘導**（案内を出す）
5. **狭い幅では編集 / プレビュー切替へ移行**（§7 のスマホ構造と同じ器）

1280px の成立確認: 248（左ナビ）＋ 208（節ナビ）＋ フォーム ＋ 440（プレビュー）
＝ 1096 + フォーム。フォームは 184px しか残らないため、**1280px では手順1〜3を
適用する**。節ナビをコンパクト（208→148）、プレビューを既定440→360へ縮めると
フォームは 1280−248−148−360＝**524px** を確保できる。実装後に実測して調整する。

### フォーム列の container 分岐

| container 幅 | ラベルと入力の配置 |
|---|---|
| ≥ 560px | ラベル左・入力右（現行） |
| 400〜559px | ラベル左・入力右（ラベル幅を詰める） |
| < 400px | **ラベル上・入力下**（縦積み） |

## 3. 可変プレビュー幅の仕様

### 3-1. 値

| 項目 | 値 | 根拠 |
|---|---|---|
| **最小** | **320px** | 現行値。これを下回るとツールバーが4行になる（P5） |
| **標準** | viewport により 360 / 440 / 480 / 520px（§2 の表） | 1280 で 440 にするとフォームは 1280−64−208−440＝568px。container 分岐の 560 をわずかに上回る |
| **最大** | **Workspace の 55%**、かつ**フォーム列が 400px を下回らない**方を優先 | 400px はラベル縦積みの下限。ここを割るとフォームが読めない |
| **スマホ枠** | **375px を下回らせない（等倍）** | P3 の解消。**横方向へ縮めない。** 375px＋枠を確保できない画面幅では、インラインで縮小表示せず「大きく表示」または編集/プレビュー切替へ移行する（オーナー確定 2026-07-31） |

**最大幅は「55%」だけで決めない。** `min(55%, workspace − 400px)` とし、
フォームが潰れないことを常に優先する。

### 3-2. 操作

- フォームとプレビューの**境界をドラッグ**して変更する
- 掴む帯は幅 **8px**、当たり判定は **左右 4px ずつ広げて 16px**（44px は不要だが 8px は細すぎる）
- `role="separator"` ＋ `aria-orientation="vertical"` ＋
  `aria-valuenow` / `aria-valuemin` / `aria-valuemax`
- **キーボードで操作できること**: 矢印で 16px、`Shift`＋矢印で 64px、
  `Home` / `End` で最小 / 最大
- ダブルクリックで標準幅へ戻す
- ドラッグ中は iframe に `pointer-events: none` を当てる
  （iframe がマウスイベントを飲むとドラッグが切れる）

### 3-3. 保存

- `usePersistentState("admin:settingsPreviewWidth", null, "local")`
- **保存するのは px ではなく Workspace に対する比率**（例 `0.34`）。
  px で保存すると別の画面幅で開いたとき最小・最大を外れる
- 範囲外になった値は読み込み時に**安全な範囲へ補正**する。
  **保存値が壊れていても編集不能にしない**
- **標準幅へ戻すリセット操作を用意する**（ダブルクリック＋明示ボタン）

### 3-4. 幅が変わったときの挙動

- フォーム列は container query で自然に縦積みへ移る（§2 の表）
- **横スクロールを発生させない。** これを自動テストで固定する
- 節ナビは縦のまま。現在節と変更/失敗の印を維持する

### 3-5. sticky

- プレビュー列の**上部操作を sticky**（`top: 0`）にする
- **フォーム列と独立にスクロール**する。プレビュー内部（iframe の外側の器）だけが
  必要に応じてスクロールする
- Admin ヘッダーと重ならない `top` を使う
- **開閉ボタンを節ナビの下（保存パネルの上）へ移す**（P6 の解消）。
  本文をどこまでスクロールしても到達できる

## 4. プレビュー上部の操作

### 4-1. 並び（左から）

> **【改訂】オーナー確定 2026-07-31。** 折り返しは意味のまとまり単位。
> 旧「⋯へ収納」案は不採用（理由は下記「旧案」）。

```
[ PC幅 | スマホ幅 ]  [ 同期 | 再読み込み ]  [ 大きく表示 | 別窓 ]  [ 幅を戻す ]
   Segment（排他）        Quiet                  Quiet             Quiet
```

- **短いラベルは途中改行させない。** ボタン単位で `white-space: nowrap`
  ＋ `min-width: 4em`（親へ一括で当てない）
- **1列へ押し込まない。** 幅が足りなければ**グループ単位で折り返す**
- **グループの中は常に `nowrap`。** ボタンが1個ずつ無秩序に折り返されず、
  入らないときはグループ全体が次の行へ移る
- 意味単位として必ず維持するグループは次の4つ。
  1. `PC幅 / スマホ幅` 2. `同期 / 再読み込み` 3. `大きく表示 / 別窓で開く`
  4. `プレビュー幅のリセット`（幅を変えたときだけ出す）
- **どの操作も隠さない。** 幅が足りなくても行数が増えるだけで、
  すべての操作へ到達できる

**旧案（2026-07-31 起票時・不採用）**: 幅が足りなければ後半グループを「⋯」へ
収納し、`PC幅 / スマホ幅` だけは隠さない。不採用の理由は5点。
320px 前後で操作を隠すと到達性が下がる／操作の存在が分かりにくくなる／
メニューが1段増えプレビュー操作として煩雑になる／新しい popover と
重なり順の問題を増やしたくない／現在の操作数なら意味のまとまりを保った
折り返しで足りる。

### 4-2. 表記

現行の `Sync ON` / `Sync OFF` / `Reload` は英語のまま UI に出ている。
i18n 辞書へ移し、日本語では **「同期 中／停止」「再読み込み」** とする。
（`admin-i18n.tsx` の `sitePreview` へ追加）

## 5. 「大きく表示」— 3案の比較

| | 案1: Workspace 全体へ展開 | 案2: 全画面オーバーレイ | 案3: フォームを畳んで拡張 |
|---|---|---|---|
| 実装 | プレビュー列を `flex: 1`、フォーム列を `display: none` | `position: fixed; inset: 0` の新しい層 | プレビュー幅を最大値まで広げるだけ |
| 編集内容の保持 | ◎ アンマウントしない | △ 別ツリーへ移すと iframe が再読込 | ◎ |
| PC幅/スマホ幅 | ◎ 同じツールバー | ◎ | ◎ |
| Sync / 再読み込み | ◎ | ◎ | ◎ |
| Escape で戻る | ◎ | ◎ | ○（幅を戻すだけ） |
| 左ナビ・ダイアログとの重なり | **◎ 事故が起きない**（既存の層に留まる） | **✕ 危険**。`.admin-screen` が transform で層を作るため、全画面 fixed はその箱に閉じ込められる。左ナビを覆えず中途半端になる | ◎ |
| 「大きく」の実効幅（1440） | **1192px** | 1440px | 約 792px |
| 戻ったとき | 元の幅へ復帰 | 元の幅へ復帰 | 元の幅へ復帰 |

**推奨: 案1（Workspace 全体へ展開）。**

理由は3つある。**iframe をアンマウントしないので編集内容と読み込み済みの
プレビューがそのまま残る**こと。**既存の層構造に留まるので重なり事故が起きない**こと
（案2 は Phase 0 の調査で判明した「`.admin-screen` が transform で自前の層を作る」
問題に正面からぶつかる）。そして 1192px は実機の PC 幅として十分で、
案3 の 792px では足りないこと。

### 5-1. 【確定】仕様（オーナー確定 2026-07-31・案1採用）

**「大きく表示」はブラウザ全画面ではなく、Admin Shell 内のプレビュー専用 Workspace。**

- **iframe をアンマウントしない。** 現在のプレビュー状態（読み込み済みページ・
  スクロール位置・PC/スマホ幅）をそのまま保つ
- フォームと節ナビを**一時的に畳み**、Settings の Workspace 内でプレビューを最大化する
- **左 Admin ナビ・言語切替・グローバルナビは維持する**（隠さない）
- PC幅 / スマホ幅・同期・再読み込みは**引き続き操作できる**
- **明示的な「編集へ戻る」操作を用意する**。Escape でも戻れる
- **未保存の入力内容を保持する**（フォームの state をアンマウントしない）
- **全画面 overlay を作らない。新しい最上位スタッキングコンテキストも作らない**
- 状態は `previewExpanded`（保存しない。開き直したら通常幅へ戻る）
- 展開中、未保存があれば上部に件数を文字で残す
- 展開中に保存が失敗したら自動で展開を解除し、該当節を本文へ出す
- **戻ったとき、フォーカスを「大きく表示」ボタンへ返す**

## 6. 「別窓で開く」の範囲

**今回の対象**: **保存済みの公開サイトを新しいタブで開くだけ。**

- `<a href="/" target="_blank" rel="noopener">` 相当。`window.open` は使わない
  （ポップアップブロックと `noopener` の扱いを揃えるため）
- **未保存の編集内容は反映されない。** ボタンの補足に
  「保存済みの内容が開きます」と明記する
- デモモード（`demoSeed`）のときは `?admin-demo-preview=` を付けた URL を開く
- **外部表示であることが分かるラベル/アイコンを付ける**（`↗` ＋「別窓で開く」）

### 6-1. 【確定】既存「サイトで確認」との共通化

> **オーナー確定 2026-07-31: 別実装を増やさず共通化する。**

現状、公開サイトを開く導線は3箇所にある。

| 場所 | 実装 |
|---|---|
| 左ナビ フッター | `<a href="/" target="_blank" rel="noopener">`（`admin.tsx` / `admin-compact-sidebar.tsx`） |
| Library ヘッダー「サイトで確認」 | **同じ画面内の iframe プレビューを開閉するトグル**（別物） |
| Settings プレビュー「別窓」 | 今回追加 |

**Library の「サイトで確認」は別窓ではなくインラインプレビューの開閉**なので、
意味が違う。共通化するのは**左ナビの「サイトを見る」と Settings の「別窓」**の2つ。
