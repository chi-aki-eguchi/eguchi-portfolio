## 1. 確認済み事実（Phase C。根拠の行付き）

1. 既存 Library には検索・11種の絞り込み・並べ替え・保存条件・詳細欄・一括編集・選択・
   仮想スクロールが既にある。未充足の中心は**グループ表示**。
2. 現在の Table は固定列で全写真を一度に描画する。496枚では動く。
3. **Table の各行は編集状態と自動保存を持つ**（`admin.tsx:7693`, `:7755`）。
   行が画面外へ出て消える場合の保存も絡むため、Table の仮想化は単純な表示改善ではない。
4. Library 本体は `GalleryTab` 1つに、取得・絞り込み・並べ替え・アップロード・選択・
   詳細編集・Table・グリッドが同居している（`admin.tsx:1752`, `:2103`, `:2407`）。
   `GalleryTab` だけで約5800行。
5. 絞り込みと表示用並べ替えは `GalleryTab` 内部で直接計算している（`:2407`, `:2661`）。
   独立タブで同じ操作を持たせるなら共通化か複製が要る。
6. タブ一覧の写真用入口は `gallery` だけ。独立タブ追加はタブ型・ナビ・モバイルメニュー・
   画面切替へ波及する（`admin-shared.ts:6`, `admin.tsx:773`）。
7. 「今回追加」は表示中の並びを二分し、追加写真を先頭区画へ移して重複を除く仕組み
   （`lib/recently-added-photos.ts:10`, `admin.tsx:2743`, `:5947`）。絞り込み外も表示する。
8. **`library-band-decisions.md` の判断1は古い。** 現行コードに「今回追加」区画があり、
   追加写真は画面上部で確認できる。
9. **束のIDは「表示写真IDの集合」ではない。** 現行は時系列で最初の写真IDから作る
   （`lib/photo-band.ts:90`, `:100`, `:122`）。
10. 絞り込みは、全写真から先にイベントを作り、その後で表示写真を抜き出す二段構成。
    このため**絞り込みだけではIDは変わらない**（`photo-band.ts:204`, `photo-band.test.ts:215`）。
11. イベントIDが変わる条件: 後ろへ追加=変わらない / 先頭より古い写真を追加=変わる /
    先頭写真を削除=変わる / 中間削除で12時間超の空白=分割されて後半が別ID /
    日時修正で先頭が変わる・分割結合=変わるか消える / 絞り込みだけ=変わらない。
12. **束の入力は写真ID・撮影日時・登録日時だけで、媒体（フィルム/デジタル）を見ていない**
    （`photo-band.ts:8`, `:158`）。時刻が近ければ両者が同じイベントに混ざり得る。
13. フィルム279枚中121枚が同一時刻。その時刻は撮影ではなくスキャン／取り込み時刻。
14. B-2 は画面未接続の計算部品。区画ごとの列数・行高・見出し高から表示位置を計算するが、
    **折り畳み状態・選択・キーボード操作・スクロール位置の維持は担当しない**。
15. B-2 ブランチのcommitは3件（`a394de0` 試作 / `e81b13c` main取り込み /
    `acf6f6d` 不正な寸法値で画面を止めない修正）。製品画面へ接続する変更は無い。
16. 現行の詳細欄は既にPC横並び・タブレット右側・スマホ下シートの3段（`admin.tsx:6801`）。

## 2. 推測（Phase C。確定事項ではない）

- 困りごとの中心が「同じ撮影をまとめて見渡せないこと」なら、新しい管理画面全体ではなく
  コンタクトシート表示だけで価値の大半を確認できる。
- 案Bを独立タブとして始めると、見た目より「検索・絞り込み・並べ替え・選択・詳細欄を
  どちらの Library が所有するか」の整理に作業量が流れる。
- 現在のイベントIDは「出来事そのもの」ではなく「先頭写真を目印にした推定」。
  日時修正が日常的なら、折り畳み状態を長期保存するIDとしては不安定。
- フィルムを「取り込みイベント」、デジタルを「撮影イベント」と呼び分ければ同じ画面構造は
  使える。ただし同じ12時間規則で混ぜるのは誤解を生む。
- 496枚でコンタクトシートの意味を判断するだけなら、B-2 無しでも体感確認はできる。

## 3. 未解決の反論と Claude の処置

> Phase C の本文は書き換えていない。各項目の最後の行だけが Claude の処置。

**反論1. 本当に新しい管理ビューが必要か** — 必要性は未証明。既存 Library に管理機能の
大半がある。未充足は主に「グループを見渡す表示」であり、独立した管理画面全体と同義ではない。
→ **採用。** 独立タブを作らず、既存 Library 内の**表示モード追加**（feature flagで無効化可）に縮める。

**反論2. Table 拡張の方が小さく安全ではないか** — 半分正しい。列の表示・並べ替え・情報確認が
目的なら Table 拡張が小さい。一方、現 Table は行ごとに編集と自動保存を持つため、仮想化まで
含めると安全とは言い切れない。コンタクトシートの価値は Table 拡張では確認できない。
→ **採用（部分）。** Table には触らない。試作は Table の外に読み取り専用で作る。

**反論3. 案Bが機能重複を生まないか** — 生む。独立タブに検索・絞り込み・並べ替え・選択・
詳細欄を置けば二重管理になる。読み取り専用試作でそれらを作らない限り回避できない。
→ **採用。** 試作は**既存の検索・絞り込み・並べ替え結果を受け取るだけ**。自前で持たない。

**反論4. `admin.tsx` の肥大化** — 全面案Bを同ファイルへ加えるなら明確に悪化する。
`GalleryTab` だけで約5800行あるため、新ビュー本体をここへ直接書くのは停止条件にすべき。
→ **採用。停止条件にする。** 試作本体は新しいファイルへ置く。`admin.tsx` 側の追加は
入口と受け渡しだけ（目安50行以内。超えるなら止めて報告）。

**反論5. 独立コンポーネントへの分離** — 分離可能で問題なし。境界は
`GalleryTab`=既存の取得と絞り込み / 新部品=表示対象と全写真を受け取り描画 /
`photo-band.ts`=イベント計算 / B-2=必要になった時だけ。
→ **採用。この境界をそのまま実装の指定にする。**

**反論6. Grid／Table／コンタクトシートの共通基盤** — データ計算の共通化は利点が大きいが、
描画まで1つに押し込むと Table の編集行・グリッドの選択・見出しという別責任が絡む。
**データ計算は共通化、画面描画は別部品**が妥当。
→ **採用。** 試作は描画だけを担当し、既存の描画には手を入れない。

**反論7. B-2 を使う必然性** — 現段階では無い。最初の問いには過剰。B-2 を入れても
折り畳み状態やスクロール位置維持は自動的には解決しない。
→ **採用（B-2 は使わない）。** ただし後述のとおり、全DOM描画はしない
（オーナー指定の完成条件）。B-2 を使わずに済む単純な窓だけを試作内に持つ。

**反論8. B-2 を使わない小さい試作** — 496枚を読み取り専用の小さいサムネイルで全件描画し、
見出しだけ付ける案がある。既存 Table も496行を全描画している。
→ **不採用（理由あり）。** オーナーの完成条件に「大量写真でも全DOM描画しない」が明示されている。
既存 Table が全描画なのは事実だが、それに合わせない。試作内に単純な窓を持つ。

**反論9. デジタルとフィルムを同じモデルで扱う危険** — 重大。表示形式は共通でよいが、
出来事の意味は分ける必要がある。現行計算は媒体を見ないため、同時刻帯のフィルムと
デジタルを一つにまとめる可能性がある。少なくとも媒体をまたいで束ねない境界が必要。
→ **採用。** 試作では**媒体をまたいで束ねない**。フィルムは「取り込み」、デジタルは「撮影」と表示する。
`photo-band.ts` 本体は変更せず、試作側で媒体ごとに分けてから渡す。

**反論10. 写真変更によるイベントID変化** — 絞り込みには耐えるが、データ変更には耐えない。
日時修正で先頭写真が別イベントへ移ると、IDが写真について移動する。永続的な出来事IDが
必要なら現在の自動IDだけでは足りない。
→ **オーナー判断待ち。** 試作は折り畳み状態を保存しないので今回は影響しない。
「出来事に永続IDを持たせるか」は製品化を決める段階の判断として残す。

**反論11. 絞り込み変更時の束状態維持** — 同一画面を開いている間は現行の二段計算で維持できる。
ここは問題なし。ただし日時修正・削除・分割結合をまたぐ維持は未解決。
**絞り込み耐性とデータ更新耐性を混同してはいけない。**
→ **採用（記録として保持）。** 試作の完成条件には「絞り込みを変えても表示が壊れない」だけを入れ、
データ更新耐性は主張しない。

**反論12. スマホへ新ビューを足す価値** — 現時点では低い。PCで価値が確認できる前にスマホを
作ると、タッチ選択や画面遷移という別問題まで抱える。
→ **採用（部分）。** スマホ専用の操作体験は作らない。ただしオーナー指定どおり
**320 / 390 / 768 / 1440px で表示が破綻しないこと**は完成条件に残す（作り込みではなく破綻防止）。

**反論13. 最小試作で判断できること／できないこと** —
判断できる: 撮影／取り込み単位が既存グリッドより分かりやすいか / 密度と見出しが役立つか /
フィルムの取り込み区画が意味を持つか / 独立入口が要るか。
判断できない: 編集と一括操作の使いやすさ / 保存済みビュー / Table 仮想化 / 最終性能 /
スマホ操作 / 長期の折り畳み維持 / 3ペイン全体の完成体験。
→ **採用。この切り分けをそのまま試作の評価軸にする。**

**反論14. 「今回追加」区画との競合** — 競合する。先に分離するとイベントから写真が抜け、
後から分離すると二重表示になり得る。最小試作では持ち込まないのが安全。
→ **採用。** 試作では「今回追加」を表示しない。将来統合するならグループではなく
一時的な表示条件か目印として扱う。

**反論15. 編集・保存・一括操作なしの価値** — 問題なし。価値はある。ただし確認できるのは
「写真の見え方とまとまり方」だけで、写真管理画面全体の価値を確認したと結論づけてはいけない。
→ **採用。報告時にこの限定を必ず書く。**

**反論16. 試作の廃棄条件** — 実写真で既存グリッドより把握しやすくならない / フィルムの
121枚同一時刻区画が大きすぎて整理単位にならない / 独立入口より既存の表示切替の方が迷わない /
編集や一括操作が無いと良否を判断できない / 媒体を正しく分けるのにDB項目追加が不可欠になる /
「何を素早く終えられるようになったか」をオーナーが挙げられない。
単に496枚の描画が重いだけなら廃棄ではなく、そこで初めて B-2 を試す判断。
→ **採用。この6つを廃棄条件として確定する。**

## 7. 試作の結果（2026-07-28・commit `7b041fa`）

**main へは入れていない。** 隔離ブランチのままにした。理由は、分離度は十分だが
（`admin.tsx` への追加は25行、URLクエリが無ければ描画経路に入らない）、
**役に立つかどうかがまだ誰にも分かっていない**ため。判断材料としては完成している。

### オーナーが実際に触る手順

```
cd /Users/chiaki/eguchi-finder-proto
bun run dev
```

ブラウザで **`/admin?finder-prototype=1`** を開き、Library の道具列にある
「Finder試作」を押す。戻るときはもう一度押す。クエリを付けなければ、
いつもの Library と1つも変わらない。

### 見てほしいこと（この6つだけ）

1. 撮影／取り込みの単位でまとまって見えることが、いまのグリッドより分かりやすいか
2. コンタクトシートの密度（小さい写真が並ぶ形）が実際に使えるか
3. フィルムの区画が「取り込み」として意味を持つか。
   実データでは121枚が同じ時刻に固まる想定なので、大きすぎて使えないかもしれない
4. 詳細リストの情報量が足りているか、多すぎるか
5. 独立した入口が要るか、いまのように Library の表示切替で足りるか
6. **「これがあると何を早く終えられるか」を一言で言えるか**

### 判断（2〜3択）

| | 選択肢 | 次に起きること |
|---|---|---|
| **A** | 続ける（案Bを製品化へ） | 折り畳み・選択・詳細欄・大量写真の性能を順に足す。B-2 はその時に初めて使う |
| **B** | 縮めて続ける（表示切替の1つとしてだけ残す） | 独立ビューは作らず、いまの Library に「イベント表示」を足す形にする |
| **C** | 捨てる | ブランチを残したまま終了。既存 Library の改善に戻る |

**おすすめは、実際に触ってから決めること。** 上の6つのうち3つ以上が「良い」なら A、
1〜2つなら B、0なら C が妥当。

### この試作で分からないこと（反論13より）

編集・一括操作の使いやすさ / 保存済みビューの価値 / Table の仮想化 /
大量写真での最終的な性能 / スマホ操作 / 折り畳み状態の長期維持 / 完成版の3ペイン体験。
**「写真の見え方とまとまり方」以外を、この試作で判断しないこと。**

### 廃棄条件（反論16。1つでも当てはまれば捨てる）

実写真で既存グリッドより把握しやすくならない / フィルムの同一時刻区画が大きすぎて
整理単位にならない / 独立入口より既存の表示切替の方が迷わない / 編集や一括操作が
無いと良否を判断できない / 媒体を正しく分けるのにDB項目追加が不可欠になる /
「何を素早く終えられるようになったか」を挙げられない。
