## 2. 推測（Phase A。確定事項ではない）

- 「使用感が良くない」の主因は見た目ではなく「1操作ごと即保存なのに画面は先に動かず、保存中表示も無い」こと。
- スマホ3列でボタンが出ないこと、2列で先頭・末尾が出ないことは、496枚での並べ替えを実質不可能にする。
- PCの縦線は処理上は正しいが、複数列Gridでは「この写真の右か、次の行か」が読み取りにくい。
- 複数枚移動は連続した写真を一区画として動かす場合に価値がある。ただし現状の最大問題は1枚の長距離移動。
- 121枚が同一時刻でも撮影日順は安定ソートで同順位内の手動順を維持するため、順序がランダム化する問題ではない。

## 5. 今回やること（オーナー確定 2026-07-28）

### 必須の安全修正

1. 公開ギャラリーの並び順が手動以外なら、Library の並べ替えを禁止し
   「現在の公開並びは手動順ではないため、ここでは並べ替えできません」と明示する。
   手動へ変更する導線は出してよいが、**自動で設定を変更しない**。
2. 並べ替え開始時に、画面の配列が保存対象の手動順として妥当か確認する。
   APIの並びと Library 内の表示値の食い違いを解消し、
   **撮影日順などを誤って `sort_order` として保存できないようにする**。
3. 保存処理: 保存中は次の操作を禁止／保存中・保存済み・失敗を並べ替え欄の中に表示／
   失敗時は見た目の順序を元へ戻す／古い要求が新しい要求を上書きしない／
   複数タブ・競合について現在のAPIで安全に防げる範囲を確認する。
4. Undo: 直前1回の並べ替えを戻せる。Undo も保存結果まで含めて成功・失敗を明示する。

### 操作改善

5. 文言: 「完了」→「並べ替えを終了」／並べ替え中は「公開ギャラリーの手動順を変更中・
   1操作ごと自動保存」と常時表示／絞り込み中は全体順へ反映されることを必要に応じて説明。
6. ドラッグ: 明確な取っ手を用意／挿入位置を3pxの細線より明確に／
   **上下でドロップ位置の意味を統一**／自動スクロールを調査し、長距離に耐えないなら補完。
7. スマホ: 並べ替えモードで2列へ切り替え／先頭へ・末尾へを必ず表示／
   ドラッグだけに依存しない／390pxで操作が欠けないことを自動テスト。
8. 長距離移動: 「何番目へ移動」か「選んだ写真の前／後へ移動」の**自然な方を採用**。
   先頭／末尾だけで終わらせない。
9. キーボード: 機能していない `⌘/Ctrl + ↑↓` の案内はいったん削除。
   対象写真を明確に選択・表示できる構造まで安全に作れるなら修正してよい。中途半端なら次段階へ。

### 今回入れない

複数枚の並べ替え／保存前の編集セッション方式／Undo・Redo履歴／Finder試作のmain統合／
左ナビ／独立詳細パネル／3ペイン／DB schema変更／本番DB・R2操作。

## 6. 壊してはいけない既存挙動（症状つき）

- **複合絞り込み中の並べ替え禁止**。壊すと、見えていない写真との位置関係が意図せず変わる。
- **シリーズ単独の例外と全体順への差し込み**（`lib/reorder.ts`）。表示中のシリーズだけを
  0番から振り直すと、他の写真と順位が重なる。
- **大一覧の描画範囲を絞る仕組み**（`computeVirtualGridWindow`）。外すと496枚を同時描画して重くなる。
- **「今回追加」を並べるモードで隠し、ID集合は保つ挙動**。消すと取り込み後の目印が失われる。
- **カテゴリ・シリーズ・料金の保存中停止と失敗時復帰**。外すと画面と保存結果が食い違う。
- **Settings と Service の保存・破棄バー**。外すと未保存の順序変更を失いやすい。
- **撮影日が同じ写真で元の手動順を維持する安定ソート**。外すと121枚が不安定に並ぶ。

## 7. Phase C（反対レビュー・別セッション・読み取り専用）の結果と処置

**判定: 条件付きで進めてよい。**「事実12〜14への認識は正しいが、現在の計画のままでは
Table・複数タブ・写真追加との競合が残る。API側の完全性検査と競合拒否を必須条件として
追加すれば進めてよい」。

### Phase C が付け加えた確認済み事実

- **事実12〜14の連鎖は正しい。訂正なし。**
- **API応答には保存済みの `sortOrder` が含まれている**（`api/index.ts:98-127` の `PHOTO_LIST_COLUMNS`）。
  一方、管理画面の `Photo` 型にはこの項目が無い（`admin-shared.ts:211-236`）。
  → **APIを変えなくても、管理画面側で手動順を再構成する材料はある。**
- 保存成功処理は再取得の**開始を指示するだけで完了を待たない**（`admin.tsx:3499-3503`）。
- **Table でも「この並びを保存」は使え、同じ並べ替えAPIを呼ぶ**（`admin.tsx:4422-4481`）。
- APIは整数だけを残し、**重複・未知ID・抜け・全件揃いを検査しない**。順位列に重複禁止も無い
  （`api/index.ts:705-711`、`reorder-sql.ts:16-29`、`schema.ts:50-85`）。
- **シリーズの公開順にはギャラリーとは別の設定がある**（`seriesSortOrder` とシリーズ個別設定、
  `api/index.ts:2357-2408`）。`gallerySortOrder` だけでは、いま見ているシリーズの公開順が
  手動かを判定できない。

### 未解決の反論と Claude の処置

**反論1. 公開設定ロックだけでは保存経路を封鎖できない** — Gridのドラッグと矢印を止めても、
共通領域の「この並びを保存」が同じAPIを呼べる。直接APIを呼ぶ経路も残る。
→ **採用。** Grid と Table の保存を同じ安全な保存処理へ統一する。API側の検査も入れる（反論2）。

**反論2. 管理画面だけでは複数タブ・写真追加との競合を完全には防げない** —
タブAが取得 → タブBが追加や別の並べ替え → タブAが古い全IDを送る → APIが古い配列をそのまま受理。
新しい写真の順位が重なる、またはタブBの変更が上書きされ得る。
→ **採用（必須条件とする）。** API に完全性検査（重複なし・未知IDなし・削除済みを除く全件が
過不足なく揃う）と競合拒否を追加する。**DB schema は変更しない。**

**反論3. 保存中ロックの解除時点が曖昧** — 成功応答時か、最新一覧の再取得完了時か。
前者では古い画面状態を基に次の保存を送りうる。
→ **採用。再取得の完了まで解除しない。**

**反論4. 1回Undoにも競合条件が必要** — 通常保存の完了前にはUndoを出さない、Undo保存中は他操作を
止める、Undo失敗時は「Undo前の保存済み順」へ戻す、別タブで順序が変わった後のUndoは拒否する。
→ **採用。全4条件を実装条件にする。**

**反論5. シリーズ単独時に見るべき公開設定が不足している** — ギャラリー設定が手動でも、対象シリーズの
実際の公開順は撮影日順などの場合がある。
→ **部分採用。** オーナー指示どおり `gallerySortOrder` によるロックと明示は入れる。ただし
**データ安全性の中心はロックではなく `sortOrder` からの再構成に置く**（Phase C の推奨1）。
シリーズ個別設定まで見て警告を出すかは **オーナー判断待ち**（今回は実装しない。安全性は
再構成と API 検査で担保されるため）。

**反論6. 「何番目」の意味をシリーズ単独時に決める必要がある** — 全写真中の10番目か、シリーズ内の
10番目か。自然なのは「表示中シリーズ内の10番目」で、保存時は既存の全体差し込み規則を使う形。
→ **採用。その定義で実装する。**

**問題なし（Phase C の明言）**: シリーズ差し込み・「今回追加」のID集合・今回入れない機能
（複数枚移動、編集セッション、Undo/Redo履歴）。

### Phase C の推奨のうち、計画から削るもの

- 「選んだ写真の前／後へ移動」→ **不採用（削除）。**「何番目へ移動」だけにする。
  理由: 対象写真を再度探して選ぶ状態管理が増え、仮想表示の大一覧では操作が複雑になる。
- 「公開設定が手動以外なら必ずロック」を**データ安全性の中心に置く考え方**→ 中心から外す。
  ロックはオーナー指示どおり残すが、位置づけは補助的な制限。

### 実装順（Phase C の推奨を採用）

1. 保存APIの完全性検査と競合拒否
2. 管理画面で `sortOrder` から手動順を再構成
3. Grid・Table 共通の保存処理
4. 楽観更新、保存中表示、失敗時復帰、1回Undo
5. 「何番目へ移動」だけを追加
6. シリーズ単独差し込み、「今回追加」ID、スマホ表示の確認

### Claude が独立に測った事実（Phase C 後）

- **自動スクロールの速度**: 端から72pxの帯で `速度 = ceil(距離 ÷ 5)` px/フレーム。
  最速でも約15px/フレーム（60fpsで約900px/秒）。長距離移動をドラッグだけに任せるのは無理がある。
- **既に正しい前例がある**: Table の「この並びを保存」は `librarySort !== "manual"` のときだけ現れ、
  絞り込み中と `reorder.isPending` の間は無効化され、**確認ダイアログを挟む**（`admin.tsx:4422-4470`）。
  つまり「手動以外の並びを `sort_order` へ書く」ことは既に**意図的で確認が要る操作**として
  扱われている。サイト設定経由で同じ結果が無言で起きるのが、今回塞ぐ穴。
