**どんなルールか**: `kill -9` は、**動いているプログラムを問答無用で強制終了する**
命令である。AIがこれを使えないように禁止設定が入っている。

**なぜ「要判断」なのか**: この設定が入ったコミット（2026-07-13）の説明文に、
**なぜ入れたのかが書かれていない**。必要になった場面の記録も無い。
つまり「効いている証拠」も「困っている証拠」も無い。

**守ると、どう不便か**: ほぼ不便は無い。**実際、この禁止に当たったことは一度も無い。**
強いて言えば、開発用サーバーが応答しなくなって止められない、という珍しい場面で
AIが自力で片付けられず、秋さんに「ターミナルを閉じてください」と頼むことになる。

**外すと、何が起こりうるか**: AIが「反応が無いから」と判断して、**別の大事な
プログラムまで強制終了してしまう**可能性がある。`kill -9` は道連れが出やすい命令で、
たとえば書き込み途中のプログラムを殺すとデータが半端な状態で残ることがある。
起きる確率は低いが、起きたときに気づきにくい種類の事故である。

**私の見立て**: **外す理由が無い。**守っていて実害がゼロ、外して得られるものも
ほぼゼロなら、そのままでよい。ただし「理由が記録されていないルールは残す」を
一般則にすると掃除ができなくなるので、**ここだけは例外扱いで残す**と決めて
おくのが正直だと思う。判断は秋さんにお任せする。

### 6. 過去ログに残っている管理パスワード

**何の話か**: ルールではなく、**未処理の宿題**である。
`docs/archive/task-handoffs.md` という過去の作業記録の中に、
**管理画面のパスワードが、そのままの文字で1箇所書かれている**。

経緯は、当時「こういう危ないものが置きっぱなしになっている」と説明するために、
その値を引用してしまったこと。**説明対象のファイルは消えたが、引用は残った。**

**放っておくと、何が起こりうるか**: このリポジトリは**他の写真家へ販売する予定**の
ものである。過去ログも一緒に配られると、購入者が管理パスワードを読める。
また GitHub のリポジトリを誰かに見せた時点で同じことが起きる。

**なぜ「消せばいい」で済まないか**: 一度コミットされた文字は、**その行を消しても
過去の記録の中には残り続ける**。完全に消すには履歴そのものを作り直す必要があり、
それはそれで危険な作業になる。

**現実的な選択肢は2つ**:

1. **Railway の管理画面で `ADMIN_PASSWORD` を新しい値に変える**（推奨）。
   過去ログの文字列は「もう使われていない古い値」になるので、読まれても害が無い。
   所要時間は数分で、リスクもほぼ無い。
2. その行を伏字に書き換える。履歴には残るが、目に触れる機会は減る。

**私の見立て**: **1を強く勧める。**2は気休めで、根本的には解決しない。
1をやったうえで2もやるのが一番きれいだが、1だけでも実害はほぼ消える。
