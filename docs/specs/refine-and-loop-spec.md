## グループR: 今すぐ直す具体的な不具合【最優先】

### R1. シリーズのサムネイルに名前が出ない（公開側）

**症状**: 公開サイトのシリーズ一覧（/series または Works のSeries表示）で、サムネイル（タイル）にシリーズ名が表示されていない。管理画面ではなく**公開側**の話。
**確認・修正**:

- SeriesGrid.tsx（公開側のシリーズグリッド）でタイル下にシリーズ名を表示する。
- 仕様の経緯: works-series-grid-spec P2 では「タイル＝表紙写真のみ・文字なし」としていたが、**方針変更**。秋の希望で**サムネイルの下にシリーズ名を表示する**。
- 表示位置: タイル（表紙写真）の直下に、シリーズ名を控えめなタイポで。design-specの静かなUIに合わせる（小さめ・余白）。
- サブタイトルがあれば名前の下にさらに小さく出してもよい（任意）。
  **受け入れ基準**: シリーズ一覧の各タイル下にシリーズ名が表示され、クリックで詳細へ飛ぶ。

### R2. Lightbox（写真拡大）の表示が小さい・画質が低い

**症状**: 写真をクリックして拡大したとき、画像が画面に対して小さく、画質も物足りない。
**修正**:

- **画面占有率を上げる**: Lightboxの画像が画面の縦横をできるだけ大きく使うようにする。余白（画像と画面端の隙間）を減らす。目安として viewport の 90〜95% を画像表示に使う。
- **画質を上げる**: Lightboxで読み込む画像の幅・品質を上げる。現状の幅（例 1600px）より大きく（例 2000〜2400px）、品質パラメータ（?q=）も上げる。ただしファイルサイズとのバランスを取り、極端に重くしない。
- **高解像度ディスプレイ対応**: Retina（devicePixelRatio 2以上）では2400px相当を配信。
- モバイルでは画面幅に合わせて適切なサイズを配信（過剰DLを避ける）。
- ズーム機能がある場合は、ズーム時にさらに高解像度（2400px）を読む既存挙動を維持。
  **受け入れ基準**: 拡大時に写真が画面いっぱい近くまで大きく表示され、くっきり見える。モバイルでも見やすい。

## グループS: 機能の追加・削除の検討【ループで継続】

サイトの目的は「作家性を持った写真家が、作品を美しく見せ、宣材・ポートレート撮影の依頼につなげる」こと。この目的に照らして、機能の要否を判断する。

### S1. 追加を検討すべき機能（目的に資するもの）

ループの中で、以下のような「あった方がいい機能」を見つけたら提案・実装する。判断軸は「作品が美しく見えるか」「依頼につながるか」。

- 例: 作品の見せ方を高める小さな改善、依頼導線の自然な強化、表示速度の改善など。
- ただし**過剰な新機能は避ける**（下記S2の方針）。

### S2. 削除・整理を検討すべき機能（過剰なもの）

このプロジェクトは機能過多の傾向がある（グリッド11種、スマートアルバム等）。**目的に対して使われていない・複雑すぎる機能は、削除または簡素化を提案する**。

- 判断軸: 「秋が実際に使うか」「閲覧者・依頼者の役に立つか」。
- いきなり削除せず、**まず「これは不要では?」と報告**し、秋の判断を仰ぐ。ただし明らかな死にコード（どこからも呼ばれていない関数・未使用の変数/インポート）は自動で削除してよい。
- グリッドレイアウトは11種あるが、実用上ほぼ使われないものがあれば候補として報告する。

### S3. デバッグ・審査・最適化（毎回やること）

ループの各周で以下を必ず行う:

- バグ・表示の崩れ・スマホでの不具合・空状態での崩れを探して直す
- 仕様書と実装のズレを探して直す
- パフォーマンス（表示速度・画像・バンドル）を計測し改善
- コードの重複・複雑さ・未使用を整理
- セキュリティ・アクセシビリティの確認

### S4. 体験レンズ【2026-06-12 視点変更・以後の周はこちらを主軸に】

S1〜S3 のコード監査・セキュリティ・設定同期の確認は一巡した（秋確認済み）。以後の周は下記4レンズをローテーションし、「実際に触って試す」ことを主軸にする。各周の報告は「何を試して何が問題だったか」の形式で書く。

1. **使う人の目線でサイトを触る**
   - 初めて来た人がトップを見て「依頼したい」と思えるか
   - 写真クリック→Lightbox の体験がスムーズか
   - スマホで全ページを操作して詰まる箇所がないか
   - 問い合わせまでの導線が自然か
2. **デザイン設定が実際に効いているか**
   - グレイン・アクセントカラー・余白・ヒーロー演出・ナビホバーが設定変更で正しく反映されるか
   - グレインは「設定しても変化がない」報告があった件（2026-06-12 に Layout の不透明背景が原因と特定し修正済み。公開反映には ZIP の再デプロイが必要）
3. **写真が増えたときの体験**
   - 100枚以上でギャラリー・トップのスクロールが気持ちよく動くか
   - Lightbox の前後移動が快適か
4. **管理画面を実際に操作して詰まる箇所**
   - アップロード→シリーズ割り当て→公開の一連の流れが自然か
   - 並び替えが思い通りにできるか

問題を見つけたら修正して `bun run check` 確認後、完了報告する。`git push` はしない（オーナーの手で行う）。

## グループT: 継続ループの運用【重要・ここが今回の肝】

### T0. 起動・ペース配分【2026-06-15 改定: 固定30分 → クレジットリセット駆動】

秋さん確定方針（この節が正本。CLAUDE.md「自走改善ループ運用方針」/ memory `autonomous-improvement-loop` と同期）:

- **起動はクレジット（利用枠）のリセット駆動。固定時刻・固定間隔の cron は使わない（イベント駆動）。** → 下記 T1 の「30分ごと」は本節で置き換える。
- **1サイクル**: ①「今サイトと秋のために何をすべきか」を一度考える → ②安全な範囲で**1件だけ**実装・改善 → ③「何を考えて何をしたか・次に気になること」を報告 → ④`bun run check` で確認（tsc -b → lint → test → build。失敗したら止まる） → ⑤**push はしない**。オーナーが確認して push するまで待つ → ⑥上限メッセージの `resets HH:MM (Asia/Tokyo)` を読み、その直後（+2〜3分）に次の起動を予約。
- **やること**: バグ/表示崩れ/スマホ不具合・既存機能の使いやすさ・パフォーマンス/SEO/アクセシビリティ・参考サイト調査の取り込み。**「変更なし」報告は避け、毎回1件の価値を出す**。
- **やらないこと**: 危険な大規模リファクタ（git管理外＝巻き戻し不可）・枠を消費するだけの無意味な変更。
- **前提**: ターミナルが開いている間だけ動く（セッション内ループ）。近々 Mac mini で常時起動予定。クレジット切れ中はターミナルを開いたまま待機し、復活したら次のリセット直後に自動再開。

### T1. ループの設定（2026-06-12 改定: 60分→30分・空き周の使い方を定義）

- 起動ペースは **T0（クレジットリセット駆動）** に従う（旧: 30分固定間隔は廃止）。クラウド `/schedule` は最小間隔1時間 + git リポジトリでないため使えず、セッション内ループで運用する。
- 問題が見つかったら修正して `bun run check` で確認する。push はしない（オーナーの手で行う）。
- 問題がないときは以下の**どれか**をやる（枠消費のための無意味な変更は引き続き禁止）:
  1. 視点を変えて別の角度から点検（使う人の目線・依頼者の目線・初見の目線等）
  2. 今ある機能の使いやすさを改善・拡張
  3. 他のフォトグラファーサイトや参考サイトから取り入れられるアイデアを調べて実装
  4. パフォーマンス・アクセシビリティ・SEO の細かい改善
  5. 管理画面の操作性改善
- 毎周「何を試したか・何をしたか・次に気になること」を報告する。
- 各周で `bun run check` を実行する。push はしない（オーナーの手で行う）。

### T2. クレジット切れへの耐性【最重要の要望】

秋の要望: **クレジット（利用枠）が切れてもループを止めず、枠が復活し次第また実行を再開してほしい。**

実装方針（Claude Codeの機能でできる範囲で）:

- **session loop（/loop）はターミナルが開いている限り継続する**。枠が切れている間はAPIが応答しないが、ターミナルを開いたままにしておけば、枠が復活したタイミングの次のtickで自然に再開する。
- そのため秋には「**Macのターミナルを開いたままにし、スリープさせない**」設定を案内すること（電源接続＋システム設定でスリープ無効）。
- もし `/schedule`（クラウドベースのスケジュール）が使えるなら、そちらはセッションを閉じても継続するため、より要望に近い。使える場合は `/schedule` を優先し、1時間ごとのデバッグ・最適化ループとして登録する。
- ループのジョブIDを報告し、停止方法（CronDelete <id> または「ループ止めて」）も毎回明記する。

### T3. ループが「やることがない」と判断した場合

- 明確なバグや改善が見つからない周があってもよい。その場合は無理に変更を加えず、「今周は問題なし」と報告して次のtickを待つ。
- **枠を消費するためだけの無意味な変更（目的なきリファクタの繰り返し等）はしない**。品質を下げるくらいなら何もしない方がよい。

## 実装順

1. **R1**（シリーズ名表示）→ **R2**（Lightbox拡大・高画質）を即実装
2. その後、**T1/T2** に従って1時間ごとのループを開始（可能なら /schedule、無理なら /loop 60m）
3. ループ内で **S1/S2/S3** を継続実行。各周で `bun run check` を実行し、push はしない（オーナーの手で行う）

## 全体の受け入れ基準

- [ ] 公開シリーズ一覧のタイル下にシリーズ名が表示される
- [ ] Lightboxの写真が画面いっぱい近くまで大きく・高画質で表示される（PC/スマホ/Retina）
- [ ] 1時間ごとのループが動き、各周でデバッグ・最適化・`bun run check` が行われる（push はオーナーの手で）
- [ ] 枠が切れてもターミナルを開いたままなら復活後に再開する（運用手順が秋に案内されている）
- [ ] 不要機能は勝手に消さず報告される（死にコードを除く）
- [ ] 各周でジョブIDと停止方法が報告される
