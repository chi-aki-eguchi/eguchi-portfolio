# デザイン自由度の拡大 — 設計

**状態:** 設計中（オーナー確認待ちの判断が3件ある）
**起点:** 2026-08-07 のオーナー指示「配置・レイアウトの種類・方向性を、公開サイトでも
admin でも変えられるようにしたい」「方向性はぜんぶ変えられるといいね」
**関連:** `design-spec.md`（公開サイトの designの核）/ `admin-renewal-goal.md`（admin の6軸）

---

## 0. いま何が足りていないか（2026-08-07 実測）

設定キーの台帳は `packages/web/src/shared/settings-keys.ts`、Settings の節の一覧は
`admin-tabs.tsx` の `SETTINGS_SECTION_KEYS`（数は変わるのでここには書かない）。
ヒーロー5種・ナビ位置3種・写真の並べ方12種・余白4軸・文字と色の細かい指定は**すでに可変**。

**つまみの数は足りている。足りないのは次の3つ。**

1. **完成形へ一発で行く手段がない。** 「詳しい設定」に入っているつまみを1つずつ回して
   自分で着地させる必要がある。デザインの訓練がないと途中で止まる。
   → 自由はあるが使えない。
2. **構造が固定。** トップの並び（ヒーロー→Works→問い合わせ）、About/Contact の
   レイアウト、色の役割（実質3色）はコード側にある。
3. **admin に自由度がゼロ。** `/admin` は `Provider` の中にあり、`.admin-atelier` は
   `--background` / `--foreground` を公開サイトの設定から継承する。
   **公開サイトを黒くすると admin も黒くなり、避ける設定がない。**

参照した実例集（`good-web-design.com/webdesign/photograph`・257件）には、
強い色面と階段状の写真配置で構成する作例がある。**今の設定では到達できない。**
到達できないのは偶然ではなく `design-spec.md` §9「色数を増やさない」で決めたためだが、
現状は「作らない」と「作れない」が同じ状態になっている。

---

## 1. 基本方針

**つまみを増やすのではなく、選べる完成形を増やす。**

つまみを足すと自由度は上がるが、使用感が下がり AI感が増える（admin 6軸のうち2つが逆に振れる）。
そこで二層にする。

| 層 | 役割 | 実装 |
|---|---|---|
| 第1層 **方向性** | まとまった見た目を1回の選択で決める | 新規キーは最小。適用時に既存キーへ展開する |
| 第2層 **微調整** | 既存の19節のつまみ | **一切削らない。今できることは全部残す** |

第1層は出発点であって檻ではない。適用後に第2層でいくらでも上書きできる。

## 2. 「方向性」の4つの軸（オーナー回答＝全部）

### A. サイト全体のテイスト

「静かな白」「温かい紙」「夜の展示室」「雑誌」「余白最大」のような**完成された見た目**を
5〜7個用意し、1回の選択で色・余白・文字・動きをまとめて当てる。

**設計判断（決定済み）: 適用時に既存キーへ展開する「スナップショット方式」を採る。**

- 展開方式: 適用ボタンで既存の設定キー群に値が書き込まれる。以降は普通の設定と同じ。
  ライブプレビュー・保存・`ignoredKeys` の検証、どれも**今の仕組みがそのまま動く**。
- 参照方式（プリセット名だけ保存し、表示時に解決する）は採らない。
  「どの値が効いているか」が第2層のつまみと二重管理になり、
  `settings-preview.ts` の4箇所同期の前提が崩れる。

必要な新規キーは実質1個（`themePreset`＝最後に適用した名前。表示と「戻す」のためだけ）。

**取り消し:** 適用直前の値を1回分だけ保持して「元に戻す」を出す。
プリセットは大量のキーを一度に書き換えるので、取り消せないと怖くて押せない。

### B. スクロール方向・読む向き

- **横スクロールのギャラリー**は、既存12種と排他（行組みや masonry と両立しない）。
  よって**13番目のレイアウトとして追加**する。既存の「未知の値は mosaic へフォールバック」
  規則にそのまま乗る。**スマホでは縦へ落とす**（横スクロールはスマホの操作と競合する）。
- **縦組み（`writing-mode: vertical-rl`）** は日本語の写真集で強い表現になるが、
  ナビ・キャプション・本文すべてに影響が及ぶ。
  **About とシリーズ詳細の本文だけに限定**して入れる。全面適用はしない。

### C. ページごとに違う方向

写真の並べ方は既に `galleryLayout` / `seriesLayout` / `topWorksLayout` でページ別。
一方、色・余白・文字は**サイト共通**。

**設計判断（決定済み）: ページ別に持つのは「方向性の指定」1つだけ。**
（例: トップ＝大胆 / ギャラリー＝静か）
その指定がそのページの余白・写真サイズ・キャプション表示に効く。
個別のつまみはサイト共通のまま置く。ページ別に全部を持つと設定が3倍に膨らみ、
第1層で減らしたはずの負荷が戻ってくる。

### D. 写真の見せ方の振り幅

- 既存の `gallerySizeVariation` / `galleryGapScale` / `gallerySizeScale` は
  **上限を広げるだけで振り幅が増える**。最小の変更で効果が出る。
- **キャプション（撮影情報）の出し方が設定にない。** `design-spec.md` §4 は
  「囁く程度に出すと雑誌感が出る」と書いているのに、出す/出さないを選べない。ここは追加する。

#### 列数が指定どおりに出ない問題（2026-08-07 修正済み）

オーナー報告「列の数が変えられない」。保存は正常で、原因は**つまみの範囲と
レイアウトが表現できる範囲のずれ**だった。列数は `floor(枠の幅 / 最小タイル幅)` で
決まるのに、枠は `max-w-5xl`（実測928px）に固定。既定の写真サイズでは4枚しか入らず、
**5〜8はどう動かしても届かない範囲**になっていた。届かないことの通知もない。

修正は「枠を広げる」方向（オーナー選択）。`galleryFrameWidth()` が指定列数に必要な幅を
求め、グリッドだけがページの器を越えて広がる。**設定を触っていないサイトは不変**
（既定3列は928pxに収まるため広がらない）。

#### 同じ形のずれを5件まとめて修正（2026-08-07）

上の1件を直したあと、**管理画面が出す範囲と、実際に効く上限**を全つまみで突き合わせた。
食い違っていたのは次の5件。いずれもスライダーの上側が何もしない状態だった。

| つまみ | 管理画面 | 実際に効いた上限 |
|---|---|---|
| 写真の大きさ（ギャラリー / トップ） | 3.0 | 2.0 |
| 余白倍率（ギャラリー / トップ） | 5.0 | 3.0 |
| シリーズの列数 | 8 | 6 |

**1件ずつ直すと必ず再発する**ので、範囲を `shared/setting-ranges.ts` の1か所に置き、
管理画面のスライダーと実行時の clamp が同じ表を読む形にした。上限は
「広げるだけで振り幅が増える」方針どおり、管理画面側（広いほう）に合わせた。
`setting-ranges.test.ts` が、どちらかが独自の数値を書き戻したら落ちる。

#### さらに見つかった2件（2026-08-07）

範囲を1か所に集めても、**設定を読んだ後の1段深い場所**にもう1つ上限があると見えない。

- `buildGalleryLayout` が `opts.emptyRate` を 0.3 へ切り戻していた（管理画面は 0.4）。
  **その場にキー名が無いので、キー名で探す検査には引っかからない。**
  つまみを足すときは、値が渡された先も追う。
- 管理画面の見出しが「モザイク／コラージュだけの調整」だったが、collage は
  抜け頻度もサイズの緩急も読んでいない。**動かないつまみを「動く」と書いていた。**
  見出しを直した。collage 側を対応させるかは見た目が変わるため**オーナー判断**。

**調べて問題が無かったもの**（再調査しないための記録）: 許可リスト157キーに読む側が
無いキーはゼロ / レイアウト選択肢12種と `KNOWN_LAYOUTS` は完全一致 /
プレビューの4箇所同期（CSS変数以外は一括ミラーで正常）/ `lib/` の他の clamp。

**この形のずれは他のつまみにも起こりうる。** つまみを足すときは、
範囲を `setting-ranges.ts` に書き、「今のレイアウトでその値が実際に見た目へ出るか」を
確認する。API の default 行に範囲をコメントで書き写さない（実際に3か所古くなっていた）。

## 3. admin 側の自由度

**まず公開サイトの色から切り離す。** これが admin 6軸の「使用感」「高級感」に直結する。

admin が独自に持つべきものは3つだけ。

1. 明るさ（明 / 暗 / 端末に従う）
2. 文字の大きさ
3. 余白の詰め具合（ゆったり / ふつう / 詰める）

**admin に「テイスト」は要らない。道具は静かであるべき**（6軸の「AI感の削減」）。
公開サイトのテイストを admin へ持ち込むと、作品を見るための器と道具の区別がなくなる。

保存先は site_settings ではなく admin 側の設定にする（公開サイトの見た目と混ざらないように）。

### 色は切り離した（2026-08-07 完了）

`.admin-atelier` の紙とインクを `var(--background)` / `var(--foreground)` から外し、
admin 自身の値として宣言した。明暗の追従は残している。

実測（同じ宣言を再現して `getComputedStyle`）: `--background: #101010` のとき、
旧宣言では `--admin-paper` が #101010 になり、新宣言では #f7f7f7 のまま。

### **フォントはまだ繋がっている（オーナー判断待ち）**

同じ形の結合がフォントに残っている。

```
--admin-font-title: var(--font-en), "Cormorant Garamond", "Georgia", serif;
--admin-font-ui:    var(--font-ja), "Hiragino Sans", ...;
```

実測（2026-08-07）: 公開サイトへ `--font-ja: 'Dela Gothic One'` /
`--font-en: 'Bungee Shade'` を当てると、**管理画面の本文と見出しがまるごとその書体になる。**
装飾的な書体を選ぶと、情報量の多い管理画面が読みにくくなる。

ただし色と違い、**これは意図的な設計の可能性がある**（admin の見出しが公開サイトの
欧文書体を借りて「アトリエ」の顔を作っている）。勝手に切らない。

- 案(a) 色と同様に切り離す。admin は自前の書体を持つ
- 案(b) 見出しだけ公開サイトの欧文を借り続け、本文UIは切り離す
- 案(c) 現状維持

**オーナーが決めるまで触らない。**

## 5. 実装の順序

小さい単位から。**各段階は単独で完結し、途中で止めても壊れない。**

| 順 | 内容 | 依存 | 大きさ |
|---|---|---|---|
| 0 | ~~暗い表示でオーナーの色が文字を読めなくする~~ | — | **2026-08-07 完了**（`9a85073`） |
| 1 | admin を公開サイトの色から切り離す（§3） | なし | 小 |
| 2 | 写真の見せ方の振り幅（D） | なし | 小 |
| 3 | テイスト・プリセット（A） | 2（プリセットの中身に使う） | 中 |
| 4 | ページごとの方向（C） | 3 | 中 |
| 5 | 横スクロール・縦組み（B） | なし（ただし影響が最も広い） | 大 |

1 と 2 は他のどれにも依存しないので、判断待ちの間でも進められる。
3 以降は §4 の衝突1（色数の歯止め）の判断が要る。

## 6. 守ること

- 既存のつまみを削らない。**今できることを減らす変更はしない。**
- 新規 settings キーは4箇所同期（台帳 / API default / `provider.tsx` の DB適用 /
  `handlePreviewMessage`）。正本は `AGENTS.md`「製品コードの不変条件」。
- 設定の保存は `postAdminSettings()` を経由する（`ignoredKeys` を見ないと無言で欠ける）。
- 写真の並べ替えは `photo-reorder-safety.ts` の競合検知を壊さない。
- レイアウトを増やすときは、未知の値が `mosaic` へ落ちる既存の規則を保つ。
- 明るい表示用の色を暗い表示へ流用しない（`lib/theme-colors.ts` / B-21 の回帰テスト）。
