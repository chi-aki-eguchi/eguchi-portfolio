# Library「束」機能 — オーナー判断が必要な項目

第1A（取り込んだ写真を見失わない）は実装・検証済み。
第1B（自動で束にする）は B-1（計算）と B-2（仮想スクロールの試作）まで進んだ。
ここから先は**好みと運用の判断**が要る。判断が必要なものだけをここへ並べる。

見た目そのものは、実際の画面を見てから決めるべきなので確定していない。
この文書は「何を選ぶことになるか」を先に見えるようにするためのもの。

---

## 判断1. 取り込んだ直後、一覧をどう動かすか

### いま起きていること（実測）

写真をアップロードすると、DB上は `sort_order = 現在の最大値 + 1` が入る
（`packages/web/src/api/index.ts:1691`）。Library の既定の並び順は「手動」なので、
**新しい写真は496枚の一番下**に置かれる。画面には出ていない。

第1Aで「今回追加した写真だけを選択し、左端に細い線の目印を付ける」ようにしたが、
**画面は動かないまま**なので、上部の「今回追加した◯枚を選択中」を読んで、
自分で下までスクロールする必要がある。

### 選択肢

| | やること | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 何もしない（現状）** | 選択と目印だけ | 見ている場所を勝手に奪わない | 追加した写真が画面外のまま。取り込みの手応えが弱い |
| **B. 最初の1枚まで移動** | 追加した写真の先頭までスクロール | 追加物がすぐ見える。予測しやすい | 直前に見ていた場所を失う。連続で取り込むと毎回飛ぶ |
| **C. 追加分だけを表示** | 一時的な絞り込みを掛ける | 追加分の確認・一括編集が最短 | 「絞り込み中」だと気づかないと写真が消えたように見える |
| **D. 上部へ移動** | 新しい写真を一覧の先頭に置く | 常に同じ場所を見ればよい | 手動の並び順を書き換える＝公開側の並びも変わる |

### 補足

- **D は公開ページの並びを変えうる。** 公開ギャラリーの並び順は設定で選べるが、
  既定は「手動」で、その時は `sort_order` をそのまま使う
  （`packages/web/src/api/index.ts:1320-1329`）。設定が「手動」のままなら、
  取り込みのたびに公開側の先頭が入れ替わる。
- **C を選ぶ場合、解除方法が見えていないと事故になる。** 過去に
  「写真が全部消えた」と誤解される作りを何度か作っている。
  絞り込み中であることを常に画面に出し、Esc で解除できることが条件。
- B と C は組み合わせられる（絞り込んだ上で先頭へ）。

### おすすめ

**B**。理由は、Dのように公開側へ影響せず、Cのように「消えた」と誤解される
経路も作らないため。Bで手応えが足りなければ後からCを足せるが、
逆（Cを入れてから戻す）は使い方が定着した後だと戻しにくい。

## 判断2. 手で束を作り直せるようにするか、するならどう保存するか

自動の束は「12時間以上あいたら別の束」「5枚未満は束にしない」で決まる。
実データでは496枚中370枚（75%）が26個の束に入った。残りは単発として流れる。

自動で必ず正しくなるわけではない。**フィルムは特に危ない**。
実測では、フィルム279枚の日時はスキャンした日時であり、121枚が全部同じ時刻だった。
これは「同じ日に現像に出した束」であって「同じ日に撮った束」ではない。

### 選択肢

| | やること | DBの変更 | 良い点 | 悪い点 |
|---|---|---|---|---|
| **A. 自動だけ** | 手で直せない | なし | 作るものが少ない。壊れる場所も少ない | 間違った束を直せない。フィルムで確実に困る |
| **B. 撮影日時を直せるようにする** | 束ではなく元の日時を直す | なし（既存の `shot_at` を使う） | 束が自動で正しくなる。公開側の並びも正しくなる | 1枚ずつ直すのは重い。まとめて直す口が今は日付単位しかない |
| **C. 束のIDを写真に持たせる** | `photos` に列を1つ足す | 小（列1つ） | 実装が軽い。1枚が1つの束に属する形は分かりやすい | 束の名前やメモを持てない。束だけを消せない |
| **D. 束のテーブルを作る** | テーブル1つ＋列1つ | 中 | 束に名前・メモ・表紙を持たせられる | `series`（作品群）と役割が近く、二重管理になりうる |

### 補足

- **既存の一括変更APIでは足りない。** いまの一括 `shotAt` 変更は
  「日時が無い写真だけ」「日付のみ（時刻なし）」なので、
  Bを選ぶなら書き込みAPIの追加が必要。
- **Dは `series` と衝突しやすい。** `series` は既に「作品群」として
  写真をまとめる仕組みを持っている（`schema.ts:77`）。
  束が「撮影の単位」、seriesが「発表の単位」だと言い切れるなら別物として作れるが、
  言い切れないなら、Cで足りるか先に確かめたほうがよい。

### おすすめ

**B を先に、C/D は保留**。理由は、束のズレの原因が「日時が実際と違う」ことなので、
束の側で例外を持つより元の日時を直すほうが、公開ページの並びも同時に正しくなるため。
Bで直しきれない場合だけ C を検討する。DはA〜Cを試した後でよい。

**いまは実装しない。** どれを選んでもDBかAPIを触ることになる。

## 判断3. 束をどう見せるか（B-3）

**まだ何も決めていない。実装もしていない。**
実際の画面を見ないと決められないので、ここでは論点だけ挙げる。

- 束の見出しに何を書くか。日付だけか、枚数も出すか、名前を付けられるようにするか
- 見出しは、その束をスクロールしている間ずっと上に貼り付くか、流れて消えるか
- 束の中の写真と、単発の写真で、大きさを変えるか同じにするか
- 束をたたんで表紙1枚にできるか
- 束の表示と、いまの3つのモード（通常・選択・並べ替え）がどう噛み合うか
- 束の見出しを選択すると束ごと選択されるか

**先に決めるべきはこれ**: 束の表示は**4つ目のモード**なのか、
それとも**いまの並び順の選択肢の1つ**なのか。
後者なら既存の構造にそのまま乗るが、前者ならモードの切り替えを作り直すことになる。

## 判断4. 1つの束の長さに上限を設けるか

束の区切りは「隣り合う2枚の間隔」だけで決まる。
そのため、11時間おきに撮り続けた30枚は、**全体が約2週間でも1つの束**になる。

実データでは6〜24時間の間隔が495個中9個しかないので、いまは起きない。
写真が増えて旅行の記録などが入ると起きうる。

- **A. 上限を設けない**（現状）— 規則が1つで済む。まれに長すぎる束ができる
- **B. 「1つの束は最大◯日」を足す** — 予測しやすい。規則が2つになり、
  「なぜここで切れたか」が説明しにくくなる

**おすすめ: A のまま。** いま起きていない問題のために規則を増やさない。
実際に長すぎる束ができてから決める。コードとテストには既知の性質として書いてある。

## 判断5. Esc を押した時の順番

第1Aで「今回追加した目印を消す」段を最後に足した。現在の順番は上から:

```
ダイアログが開いている        → 何もしない（ダイアログ自身が閉じる）
ショートカット一覧が開いている → 一覧を閉じる
写真のクイックプレビューが開いている → プレビューを閉じる
通常モードではない            → 通常モードへ戻る
写真の詳細欄が開いている       → 詳細欄を閉じる（未保存なら確認）
今回追加の目印が付いている     → 目印を消す
```

`packages/web/src/web/pages/admin.tsx:4026` 付近。

**判断が要る点**: 目印を消すのが最後でよいか。
いまは「Escを6回押さないと目印が消えない」場面がありうる。
逆に上へ持ってくると、プレビューを閉じるつもりのEscで目印が消える。

**これは体感の問題なので、実際に触って決めてほしい。**
「確認済み」とは扱っていない。

## 判断6. 目印の見た目

写真の左端に、高さいっぱいの**幅2pxの線**を出している。
色は文字色の20%の濃さ。点滅や動きは付けていない。

- 弱すぎて気づかないか
- 強すぎて写真の邪魔か
- 線ではなく別の形（角の点、枠、背景の色）がよいか

**画面を見ないと決められない。確定していない。**

## 測った数字

判断の材料として実測した値。すべてローカル。

### 撮影日時の分布（本番496枚）

- 撮影日時が入っている: 496 / 496（100%）
- 1日あたりの枚数の中央値: 2枚
- 写真が1枚だけの日: 34日（全体の36%）
- カレンダーの日で割った場合: 94個に分かれる

写真同士の間隔（495個）:

| 間隔 | 個数 |
|---|---|
| 5分未満 | 288 |
| 5分〜1時間 | 83 |
| 1〜6時間 | 29 |
| **6〜12時間** | **2** |
| **12〜24時間** | **7** |
| 1〜7日 | 35 |
| 7日超 | 51 |

6〜24時間が谷になっている。12時間はその真ん中で、6時間でも24時間でも
ほぼ同じ結果になる。だから「カレンダーの日」ではなく「時間の切れ目」で割る。

### 12時間・5枚以上で割った結果（本番496枚）

- 束: 26個 / 370枚（75%）
- 流れ: 126枚

**これは今の写真での観察であって、将来も成り立つ約束ではない。**
写真が増えれば変わる。テストにはこの数字を固定していない。

### 計算にかかる時間（実測、ローカル）

束を作る計算（496枚）:

- 全部が1つの束になる最悪の場合: 2.52ms
- 全部が単発になる場合: 1.36ms

高さが揃わない仮想スクロール（試作）:

| 規模 | 準備 | スクロール1回あたり |
|---|---|---|
| 50区画 / 496枚 | 0.37ms | 2.5マイクロ秒 |
| 1000区画 / 10000枚 | 0.70ms | 0.8マイクロ秒 |

区画が20倍になってもスクロールが遅くならない（二分探索のため）。
ただし**準備の計算は、区画の並びが変わった時だけ**行う必要がある。
毎回の描画でやり直すと2.5msが毎フレーム乗る。
