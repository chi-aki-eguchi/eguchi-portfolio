# 元画像を捨てる前に、何を抜き取っておくべきか

**方針は「原本保管庫」ではない。** 巨大な元画像やRAWは残さず、公開用の軽量画像と
サムネイル、そして**整理に必要な情報だけ**を持つ。この方針自体は変えない。

問題は別のところにある。**元画像を捨てるのは一方通行**で、その瞬間に抜き取らなかった
情報は二度と手に入らない。いま何が抜けていて、何が足りないかを整理する。

## 前提となる事実

アップロードの流れ（`packages/web/src/api/index.ts:1393-1535`）:

```
元ファイル ──▶ EXIFを読む（一部だけ） ──▶ 3200pxへ縮小 ──▶ 保存
    │                                          │
    │                                    メタデータは全部剥がれる
    └── ここを過ぎると元ファイルは消える
```

`withMetadata()` / `keepExif()` / `keepIccProfile()` は**どこにも呼ばれていない**。
sharp の既定どおり、保存されるJPEGとWebPからEXIF・IPTC・XMP・ICCがすべて剥がれる。

つまり **保存済みの画像からメタデータを読み直すことはできない。**

# 1. 現在保存しているメタデータ

`photos` テーブル25列（`packages/web/src/api/database/schema.ts:4-65`）。

## EXIFから取り込んでいるもの（7項目）

| 列 | EXIFのどこから | 備考 |
|---|---|---|
| `shotAt` | `Photo.DateTimeOriginal` ?? `Image.DateTime`（デジタル）<br>`Photo.DateTimeDigitized` ?? ファイル更新日時（フィルム） | **意味が2種類あるのに区別が無い** |
| `camera` | `Image.Make` + `Image.Model` を**連結した1文字列** | 分けて持っていない |
| `lens` | `Photo.LensModel` | |
| `focalLength` | `Photo.FocalLength` を `"35mm"` の形へ | 数値ではなく文字列 |
| `fNumber` | `Photo.FNumber` を `"f/1.8"` の形へ | 同上 |
| `exposureTime` | `Photo.ExposureTime` を `"1/250s"` の形へ | 同上 |
| `iso` | `Photo.ISOSpeedRatings` を `"ISO 400"` の形へ | 同上 |

**フィルムの場合、`camera`・`lens`・`focalLength`・`fNumber`・`exposureTime`・`iso` は
すべて空にされる**（`admin.tsx:3510-3538`）。スキャナのEXIFが入るのを避けるため。

## アップロード時に計算しているもの

| 列 | 出どころ |
|---|---|
| `width` / `height` | **縮小後**の画像の寸法（`index.ts:1443`） |
| `fileHash` | 縮小後のバイトのSHA-256（重複検知用） |
| `filename` | 元ファイル名 |
| `url` / `thumbKey` / `mediumKey` | 保存先のキー |

## 人が入れる・画面で決めるもの

`title` / `meta`（旧形式）/ `description` / `category` / `seriesId` / `filmType` /
`displaySize` / `isPublished` / `rotationDeg` / `focalX` / `focalY` / `sortOrder`

`filmType` は**EXIFではなく、アップロード時の「デジタル/フィルム」の選択**から入る。

## 仕組み上のもの

`id` / `createdAt` / `deletedAt`

# 2. 現在読み取っているが保存していない情報

**すでに手元まで来ていて、捨てているもの。追加の読み取りコストはほぼゼロ。**

| # | 情報 | いまどこまで来ているか | なぜ惜しいか |
|---|---|---|---|
| **1** | `Photo.DateTimeDigitized` | サーバーが読み、クライアントへ渡し、フィルムの `shotAt` を決めるのに使って**捨てている**（`index.ts:1471`、`upload-date.ts`） | フィルムで「いつスキャンしたか」を後から知る唯一の手段。**最も惜しい** |
| **2** | どちらの日時を採用したか | `shotAtForUploadedPhoto` の中だけで決まり、結果しか残らない | 「この日時は撮影時刻か、スキャン時刻か」が永久に分からなくなる |
| **3** | **元画像の幅・高さ** | `sharp(inputBuf).metadata()` を呼んでいるが、`{ exif }` だけを取り出して**残りを捨てている**（`index.ts:1464`） | 元がどれだけ大きかったか＝RAW由来かスマホかの手がかり |
| **4** | 縮小後のバイト数 | 応答に `size` として返しているが、保存には送っていない（`index.ts:1518`） | 「重い写真」の把握 |
| **5** | 元ファイルの更新日時 | フィルムの `shotAt` の最後の手段として使い、値は残さない | 上の2番と同じ理由 |
| **6** | 元ファイルの形式 | `isAllowedUploadImageFile` で判定するだけ | HEIC由来かJPEG由来か |

**3番は特に典型的**。同じ1行で元画像の寸法も色空間も向きも全部読めているのに、
`exif` だけ取り出して捨てている。

# 3. 今後の検索・並べ替え・グループ化に有用な情報

## 3-A. 時間の正確さ（グループ化の土台）

| 情報 | 何に効くか |
|---|---|
| **`shotAtSource`** | 撮影時刻 / デジタル化時刻 / ファイル更新日時 / 手入力 のどれかを記録。**自動の束がフィルムで崩れる問題の根本**。「日時が信用できる写真だけで束ねる」ができる |
| `Photo.DateTimeDigitized` の実体 | フィルムを「スキャンした回」でまとめられる。実測でフィルム279枚中121枚が同一時刻＝1回のスキャン |
| `Photo.OffsetTimeOriginal` | 撮影地のタイムゾーン。旅行の写真で日付の境目がずれない |
| `Photo.SubSecTimeOriginal` | 連写の順序。同一秒の写真が並ぶとき正しく並べられる |

> **いまの `shotAt` はタイムゾーンの無い「壁時計の時刻」**として保存されている
> （`index.ts:1445`のコメント）。束の計算もそれを前提にしている。
> 日常的にはこれで正しい（「その日の撮影」は現地時間で考えるため）。
> タイムゾーンを持てば、絶対時刻と現地時刻を選べるようになる。

## 3-B. 分類と仕分け

| 情報 | 何に効くか |
|---|---|
| `Image.Make` / `Image.Model` を**分けて持つ** | 「カメラでグループ化」が正確になる。いまは連結済み文字列なので分解できない |
| `Image.Rating`（カメラで付けた星） | 撮影時に選別している場合、そのまま仕分けに使える |
| IPTC / XMP のキーワード・説明・作者 | 他のソフトで付けた情報を引き継げる。**いまは読んでもいない** |
| `Image.Software` | Lightroom書き出しかカメラ直出しかが分かる |
| `Photo.FocalLengthIn35mmFilm` | 焦点距離の並べ替えが揃う。いまの `focalLength` はセンサー基準なので、APS-Cとフルサイズが混ざると意味を成さない |

## 3-C. 場所

| 情報 | 何に効くか |
|---|---|
| `GPSInfo.GPSLatitude` / `GPSLongitude` | 場所でグループ化。「同じ場所で撮った回」は撮影日時の束と別の切り口になる |

## 3-D. 画像そのものから計算できるもの

sharp の `.stats()` が返す（**いまは呼んでいない**）:

| 情報 | 何に効くか | 既存496枚でも取れるか |
|---|---|---|
| 主要な色（`dominant`） | 色でグループ化・並べ替え | **取れる** |
| 明るさ（チャンネルごとの平均） | 「暗い写真だけ」の絞り込み | **取れる** |
| ざらつき・情報量（`entropy`） | 空や壁だけの写真を見分ける | **取れる** |
| 鮮鋭度（`sharpness`） | ピンボケ候補の洗い出し | **取れる** |

**ここだけは元画像を捨てた後でも計算できる。** 保存済みの3200px JPEGに
ピクセルは残っているため。急がなくてよい。

## 3-E. 速くするための派生データ

| 情報 | 何に効くか |
|---|---|
| `searchText`（正規化した検索用文字列） | いまは9項目に対する総当たり。1列にまとめれば1回の比較で済む |
| 向き・縦横比を列にする | いまは毎回 `width`/`height`/`rotationDeg` から計算している |

# 4. 保存しなくてよい情報

**判断の基準**: 抽出は一方通行なので、迷ったら取っておくのが安い。
数値1つを496行に足しても大きさは無視できる。だから「保存しない」と決めるのは、
**大きい・解析できない・個人を特定しうる・整理に一切使わない**のどれかに当たるものだけ。

| 情報 | 保存しない理由 |
|---|---|
| MakerNote（メーカー独自領域） | メーカーごとに形式が違い、解析できない。数KB〜数十KBと大きい |
| ICCプロファイルの中身 | 数KB。公開画像はsRGBに揃えて出しており、整理には使わない |
| IPTC / XMP の**生バイト** | 大きい。**中身から必要な項目を取り出して列にすれば足りる** |
| EXIFに埋め込まれたサムネイル画像 | 自前で640px/1920pxを作っているので不要 |
| `StripOffsets`・`StripByteCounts`・`PlanarConfiguration` などの構造タグ | ファイルの内部構造の話で、写真の整理と無関係 |
| `BodySerialNumber` / `LensSerialNumber` | 機材の個体番号。整理に使わず、個人を特定しうる |
| `GPSTimeStamp` / `GPSDateStamp` | 撮影日時があれば冗長 |
| 露出プログラム・測光方式・フラッシュ・ホワイトバランス・露出補正 | 数値としては面白いが、**検索・並べ替え・グループ化のどれにも効かない** |
| `chromaSubsampling` / `isProgressive` / `depth` / `channels` | 圧縮方式の詳細。整理と無関係 |
| 元ファイルのフルパス | 個人のフォルダ構成が残る。ファイル名だけで足りる |

# 5. 元画像を破棄する前に抽出すべき最小項目

**これだけは、元ファイルが手元にある一瞬でしか取れない。**
優先度の高い順。

| # | 項目 | いまの状態 | 大きさ |
|---|---|---|---|
| **1** | **`shotAtSource`** — 採用した日時の出どころ | 計算しているが残していない | 短い文字列 |
| **2** | **`DateTimeDigitized`** の実体 | 読んでいるが捨てている | 文字列 |
| **3** | **元画像の幅・高さ** | 読める状態なのに捨てている | 整数2つ |
| **4** | **`Make` と `Model` を分けて** | 連結して1列に入れている | 文字列2つ |
| **5** | `OffsetTimeOriginal`（タイムゾーン） | 読んでいない | 短い文字列 |
| **6** | `SubSecTimeOriginal`（連写の順序） | 読んでいない | 短い文字列 |
| **7** | GPS 緯度・経度 | 読んでいない | 数値2つ |
| **8** | `FocalLengthIn35mmFilm` | 読んでいない | 整数 |
| **9** | `Image.Rating`（カメラで付けた星） | 読んでいない | 整数 |
| **10** | IPTC / XMP のキーワード・説明・作者 | 読んでいない | 文字列 |
| **11** | 元ファイルの形式と更新日時 | 判定・使用しているが残していない | 短い文字列2つ |

**1〜4は、追加の読み取りをせずに済む。** いま既に手元に来ている値を保存するだけ。

---

# 6. 既存496枚では復元できない項目

## 復元できない（保存版から剥がれている）

上の**1〜11のすべて**。加えて:

- 元ファイルのバイト数
- EXIFにあった向き（`Orientation`）
- 元の色空間
- 他のソフトで付けたキーワード・評価・ラベル（XMP）

既存分にこれらを入れるには、**オーナーが元ファイルを持っている場合に限り**、
手作業で入力するしかない。持っていなければ空のまま。

## 既存496枚でも今から取れる

| 項目 | 取り方 |
|---|---|
| 主要な色・明るさ・情報量・鮮鋭度 | 保存済み3200px JPEGから `.stats()` で計算。既存の「サムネイル作り直し」の口と同じ形で回せる |
| `searchText` | いま持っている列から作るだけ |
| 向き・縦横比の列化 | 同上 |
| 撮影日時の**推定的な**出どころ | `filmType` が「フィルム」なら「デジタル化時刻の可能性が高い」と推定できるだけ。**確定はできない** |

# 7. 新規アップロード分だけ改善できる項目

**5章の1〜11すべて。** 今日入れれば今日以降の写真から効く。
入れるのが1か月遅れれば、その1か月分は永久に欠ける。

> **これが、この文書で唯一「試作より先にやる価値がある」ことです。**
> 表示の設計は後からいくらでも変えられるが、抽出は待った分だけ取り返せない。

# 8. DB / API の変更が必要なもの

## 列を足すだけで済むもの

`shotAtSource` / `shotAtDigitized` / `sourceWidth` / `sourceHeight` /
`cameraMake` / `cameraModel` / `timeZoneOffset` / `subSecond` /
`gpsLat` / `gpsLng` / `focalLength35` / `cameraRating` / `sourceFormat` /
`sourceModifiedAt` / `searchText` / 色と明るさの数値

変更が要る場所（`AGENTS.md` の不変条件）:

1. `schema.ts` と `schema.postgres.ts` を**両方**そろえる
2. `POST /admin/upload` の応答に項目を足す
3. `POST /admin/photos` の受け取りに項目を足す
4. アップロード画面の受け渡しに項目を足す
5. `GET /photos` は `db.select()` なので**自動で増える**（＝一覧の転送量も増える。
   一覧用に列を絞った軽いAPIを足す動機になる）

## 別テーブルが要るもの

- **キーワード（タグ）** — 1枚が複数持つため、写真とタグの対応表が必要
- **手動の束** — `docs/specs/library-band-decisions.md` 判断2で別途検討

## 設定の拡張で済むもの

- 保存済みビュー（列構成・並び順・グループ化・絞り込み）— いまのスマートアルバムと
  同じく `site_settings` のJSONを広げる

# 9. Finder型管理ビューの試作に必須なもの

**新しいデータは1つも要らない。**

試作で確かめたいのは「表示形式 × グループ化」が成立するかであって、
いま持っている列だけで次はすべて作れる。

| グループ化 | 使う既存の列 |
|---|---|
| 撮影のまとまり（自動束） | `shotAt`（B-1 の `photo-band.ts`） |
| 日付（年/月/日） | `shotAt` |
| カメラ / レンズ | `camera` / `lens` |
| 媒体 | `filmType` |
| 分類 / シリーズ | `category` / `seriesId` |
| 向き | `width` / `height` / `rotationDeg` |
| 公開状態 | `isPublished` |

詳細リストの列も、いまある項目だけで17列ぶん作れる。

**唯一の注意**: 自動束はフィルムで正しくない（`shotAt` がスキャン時刻のため）。
試作では `filmType` で「フィルムは別扱い」と割り切れる。
`shotAtSource` があればもっと正確になるが、**試作の前提条件ではない**。

# 10. 試作の後でも間に合うもの

| 項目 | なぜ後でよいか |
|---|---|
| 色・明るさ・鮮鋭度 | 保存済み画像から後でいつでも計算できる |
| `searchText` | 既存の列から後で作れる |
| 向き・縦横比の列化 | 同上 |
| 評価（星）とキーワードの**画面** | 列とテーブルさえ用意すれば、UIは後から |
| GPSの**地図表示** | 値さえ取っていれば、見せ方は後から |
| 保存済みビュー | 表示形式が固まってから決めるほうがよい |
| 一覧用の軽いAPI | 列が増えてから効く |
| 手動の束 | 自動束の使い勝手を見てから |

# 11. すすめかた

```
いますぐ          ▶  抽出だけ足す（5章の1〜11）。画面は変えない
                     ＝ 今日以降の写真が欠けなくなる

試作              ▶  表示形式 × グループ化（新しいデータ不要）

試作が成立したら   ▶  評価・キーワード・保存済みビューの画面
                     色や明るさは既存496枚もまとめて計算

いつでも          ▶  既存496枚の欠損は、オーナーが元ファイルを
                     持っている分だけ手で埋める
```

**抽出（1段目）と試作（2段目）は独立している。** 順番を待つ必要はなく、
同時に進めても衝突しない。抽出はアップロード経路だけ、試作は表示だけを触る。

## オーナーが判断すべき点

| # | 判断 | 補足 |
|---|---|---|
| 1 | 抽出の追加を、試作より先に入れるか | **先を推奨**。遅れた分だけ永久に欠ける |
| 2 | 5章の11項目のうち、どこまで取るか | 1〜4は追加の読み取り不要。5〜11は読み取りを足す |
| 3 | GPSを取るか | 場所でのグループ化が要るかどうか。公開画像には出さない前提 |
| 4 | キーワード（タグ）を持つか | 別テーブルが要る。カテゴリ・シリーズと役割が重なるか要検討 |
| 5 | 既存496枚の欠損を手で埋めるか | 元ファイルが手元にある分だけ可能 |
| 6 | 一覧用の軽いAPIを先に足すか | 列が増えると一覧の転送量も増えるため |
