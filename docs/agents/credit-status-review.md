## 1. 確認済み事実

  `credit-status.mjs:70`
- Claudeについては、5時間枠と週枠のうち悪い方を採用し、どちらかの `willLastToReset` が
  `false` ならさらに一段悪化させます。`credit-status.mjs:90`
- リセット時刻と枯渇予測は保存していますが、リセット時刻そのものは現在の判定に
  使っていません。`credit-status.mjs:97`
- Codexの取得精度が `exact` 以外なら、残量にかかわらず最低 `closing` になります。
  `credit-status.mjs:109`

  なります。片方だけ正常な値を残す仕組みはありません。`credit-status.mjs:135`
- cache（前回結果の一時保存）は、5分以内なら正常値として再利用されます。取得に失敗した

- cacheの経過時間は「現在時刻－保存時刻」です。保存時刻が未来になった場合、負の時間でも

- 現在の状態順には `unknown` がありません。`credit-status.mjs:23`
  単純に `unknown` を追加するだけだと、悪い方を選ぶ処理では無視され、行動文も
  「通常運転」へ落ちます。`credit-status.mjs:24` `credit-status.mjs:155`
- hook（作業の節目に自動で動く監視処理）は、Gitや製品コードを直接変更しません。一方、
  表示文には `commit` や「新規作業禁止」という命令形の行動指示が含まれます。
  `credit-status.md:6` `credit-status.mjs:155`
- 提案されている3方針はまだ抽象方針だけで、`unknown` 時に何を表示するか、既知の危険状態と

## 3. 未解決の反論

### 反論1：「unknownを深刻度から外す」は、設計次第で危険側へ倒れる

「情報の品質」と「実際の残量」を別軸にする考え自体は正しいです。しかし、`unknown` を
深刻度から外すだけでは、「不明だから通常運転してよい」と誤解されます。

特に現在の関数へ文字列だけ追加すると、`unknown` は状態順に存在しないため、悪い方を選ぶ
処理で無視されます。最終的に「通常運転」という行動文が出る可能性があります。これは
名指しされた事故条件そのものです。

実際の残量が数%なのに取得だけ壊れた場合、長い実装を始めた直後に利用不能になる可能性が
あります。その場合、次が残ります。

- dirty tree（変更はあるが、まだ確定記録されていない状態）
- 複数ファイルのうち一部だけ変更された実装
- テスト前またはテスト失敗中の状態
- Current Stateへ記録されていない設計判断
- Codexへ依頼済みだが、Claudeが結果を確認していない作業
- 「何が完成し、何が未完成か」が人間にも次のAIにも分からない状態

また、一方の利用率だけ壊れた場合も、現在は正常なもう一方まで捨てます。`unknown` を全体
状態として一つ追加する前に、ClaudeとCodexを別々に「既知／不明」として保持しなければ、
既知の危険情報まで失います。

したがって、「不明を深刻度にしない」と「不明時に安全策を取らない」は分ける必要が
あります。不明だから範囲を縮める必要はありませんが、少なくとも長い作業の前に再開可能な
区切りを作る必要があります。

→ **採用。** 私の方針2は `worse()` の実装を見ずに書いた。文字列追加だけでは
「通常運転」へ落ちる指摘は正しい。取得軸と残量軸を分け、Claude と Codex を別々に
保持する形へ改める。

### 反論2：週枠が持っても、5時間枠は工程継続に必要

方針3は「プロジェクト全体の範囲を縮める理由にしない」という意味なら妥当です。しかし、
「新しい工程を始める判断材料にしない」まで広げると危険です。

週枠は「今週あとどれだけ使えるか」、5時間枠は「今この作業を連続して進められるか」です。
役割が違います。週枠が80%残っていても、5時間枠が数分で尽きれば、現在の工程は中断します。

中断で特に危険なのは、次のような境目です。

- DB設定など、複数箇所を同時にそろえる必要がある変更の途中
- テストを実行する前
- 失敗原因を特定したが、修正や記録がまだの状態
- commit（変更をひとまとまりとして確定記録する操作）の直前
- Codexの実装結果をClaudeが独立確認する前
- Current Stateを書き換える前

「数時間待てば戻る」は残量問題の解決であって、途中状態の安全化ではありません。待った後、
作業意図や未検証箇所が自動で復元されるわけではありません。

したがって5時間枠は、「仕事を捨てる理由」ではないものの、「長くて途中停止しにくい作業を
今始めない理由」にはなります。方針3はこの二つを混同しています。

→ **採用。** 混同していた。5時間枠は「範囲を縮める理由」ではないが「長い不可分作業を
今始めない理由」にはなる、と分けて書き直す。

### 反論3：リセット時刻は、信用条件を決めなければ誤判定を増やす

現在のコードはリセット時刻を文字列のまま保存するだけです。方針1には以下がありません。

- 時刻にタイムゾーンがない場合の扱い
- 無効な日付や過去時刻だった場合の扱い
- PCの時計が進んでいる、または遅れている場合の扱い
- cacheがリセット時刻をまたいだ場合の扱い
- リセット直後に大量消費した場合の再取得条件
- リセット時刻と `willLastToReset` が矛盾した場合の優先順位

時計が後ろへずれると、現在のcache判定では負の経過時間が「新しい」と見なされます。つまり、
古い結果を長時間freshとして使う穴が既にあります。

さらに「あと1時間でリセットだから安全」という判断も、現在の消費速度が続くという前提に
依存します。大きなCodex依頼や長い調査を始めれば、直前までの平均速度は役に立ちません。
反対にリセット直後の残量100%を5分間cacheしている間に大量消費すれば、実際より多く
見えます。

`willLastToReset` がすでに時刻と消費速度を使った予測なら、リセットまでの時間を別に
加点すると同じ材料を二重に評価する危険もあります。

→ **採用。** 特に「負の経過時間が fresh と判定される」は現存バグで、方針とは独立に
直す価値がある。時刻を判断に使う信用条件を明文化する。

### 反論4：「警告だけ」は誤命令を減らすが、完全な放任では足りない

現在の文書は「警告と状態保存だけ」と言いながら、実際の表示文は `commit` や
「新規作業禁止」を命じています。これは、今回のようにユーザーが「git操作禁止」と指定した
タスクと衝突します。hook自身はcommitしませんが、一般的な自動警告が個別依頼より強そうに
見える設計は避けるべきです。

純粋な警告だけにすれば、誤った `closing` によって作業範囲を縮める事故や、許可されて
いないcommitを促す事故は減ります。一方、警告が無視されれば、実残量が少ない取得失敗時の
事故は防げません。

したがって、完全な「情報だけ」よりも、原因にかかわらず害の小さい一つの安全行動だけを
添える方が安全です。

> 残量不明、または5時間枠が途中で尽きそう。長い工程の開始前に、現在地と未検証事項を
> 残して再開可能な区切りを作る。commitは依頼で許可され、変更が一貫している場合だけ行う。

これは工程全体を止めず、取得失敗が本当の枯渇を隠していた場合にも被害を抑えます。

→ **採用。** 実際にこのセッションで、hook の「新規作業禁止」に従って作業を止め、
オーナーから「それが妨げになっている」と指摘された。指摘と一致する。

## 4. 推奨

**3方針はそのまま承認せず、修正が必要です。** より簡単で安全なのは、単一の
`normal/saving/closing/critical/unknown` に全情報を押し込まないことです。

最低限、次の3項目だけを別々に表示します。

1. **取得状態**：現在値／5分以内の過去値／古い値／不明
2. **週枠**：十分／少ない／不明
3. **作業継続性**：5時間枠が持つ／途中で尽きそう／不明

行動は次の二つに限定するのが安全です。

- 週枠が実測で少ない場合だけ、作業範囲を縮める。
- 5時間枠が危険、または取得不能なら、範囲は縮めず「再開可能な区切りを先に作る」。

加えて、リセット時刻を判断材料にする条件として、タイムゾーン付きで解析可能、未来時刻と
して妥当、取得結果が新しい、cacheがリセットをまたいでいない、端末時刻との差が異常でない
ことが必要です。一つでも満たさなければ時刻は判断に使わず「不明」とします。

警告だけにする案との比較では、**現在の細かな行動命令より警告中心の方が事故は少ない**
です。ただし完全放任ではなく、「まず再開可能な区切りを作る」という一つの控えめな安全策
だけ残すことを推奨します。

→ **採用（オーナー最終確認待ち）。** 単一状態に押し込むのをやめ、3軸表示と行動2つに
する設計を採る。実装前にオーナーの合意を取る。
