## P0 — 放置すると実害（このセッションで修正済み）

### P0-1. `#` `?` `%` 等を含むファイル名の写真は、アップロード成功後も永遠に表示されない ✅修正済み

- **何が起きるか**: 「#tokyo.jpg」「50%off.jpg」のような名前の写真をアップロードすると、成功と表示されるのに、サイトでも管理画面でも画像が壊れたまま二度と表示されない（データ自体は保存されているのに、呼び出す住所が壊れる）。
- **再現条件**: ファイル名に URL の区切り文字（`#` `?` `%` `&` `/` など）を含む画像をアップロード。`#` はハッシュタグ風の命名で現実に起こり得る。
- **原因**: 写真/ヒーロー/プロフィールのアップロードは `file.name` を無加工で保存キーに使っていた（フォントだけはサニタイズ済みだった）。`#` 以降はブラウザが URL として送信せず、`%` は不正エンコードでサーバが 500 を返す。
- **修正内容（実施済み）**: `security.ts` に `sanitizeUploadBaseName()` を追加（日本語などの文字・数字は保持、URL を壊す記号のみ `_` に置換）。写真/ヒーロー/プロフィールの3経路に適用。あわせて画像プロキシの `decodeURIComponent` を try/catch し、不正な `%` エンコードは 500 ではなく 404 を返すようにした。
- **検証**: 単体テスト追加（security.test.ts、日本語名の保持・記号置換・空名フォールバック）。`bun run check`（273 tests）+ `bun run smoke`（23 passed / 0 failed）通過。
- **残作業**: 既存の本番データに問題キーが無いかの確認 → task-queue「Q-2」（読み取りのみ・低リスク）。

## P1 — 実害の芽。早めに直したいが緊急ではない

### P1-1. withRetry が「全ての DB エラー」を一時的エラーと誤認して3回再試行する

- **何が起きるか**: データベース操作の失敗が本物のエラー（重複登録など）でも、サーバが無駄に3回やり直してから諦めるため、失敗時の反応が約1秒遅くなる。まれに「実は成功していた書き込み」をやり直して写真の行が二重登録される芽もある。
- **再現条件**: 任意の DB エラー。drizzle-orm 0.45 が全てのクエリ失敗を「Failed query: …」というメッセージで包むようになったため、`withRetry` の判定 `message.includes("Failed query")` が常に真になる（`packages/web/src/api/database/libsql.ts:26`）。本来は ECONNRESET 等の通信断だけを再試行する設計だった。
- **修正方針**: `err.cause`（drizzle が包む前の元エラー）に対して ECONNRESET / "socket connection was closed" 判定を行い、「Failed query」単独マッチは削除する。withRetry.test.ts に cause 包み形式のテストを追加。
- **想定規模**: 小（1関数+テスト）。
- **Sonnet適性**: 可。ただし DB 全クエリに効く共通部品のため **[Codexレビュー必須]**。→ task-queue「Q-1」

### P1-2. 本番の既存写真に P0-1 の壊れキーが残っていないかの点検

- **何が起きるか**: P0-1 の修正は「これからのアップロード」を守るが、過去に記号入りファイル名でアップロードした写真が既にあれば、それは壊れたまま。
- **再現条件**: 修正前に該当ファイル名でアップロードしていた場合のみ。
- **修正方針**: 読み取りのみの点検（管理画面で壊れサムネイルを目視、または photos テーブルの url/thumbKey に `# ? %` を含む行の有無を確認）。該当があれば「複製→旧行をゴミ箱→purge」で作り直すのが安全（R2 オブジェクト共有の purge 規則があるため、手順は指示書に明記）。
- **想定規模**: 点検は小。該当ゼロなら終了。
- **Sonnet適性**: 点検は可（読み取りのみ）。修復はオーナー承認後。→ task-queue「Q-2」

## P2 — 品質・保守性の改善。指示書化して順次

### P2-1. 設定の複数キー保存が「途中まで反映」になり得る

- **何が起きるか**: 設定画面の保存が通信断などで途中失敗すると、一部のキーだけ保存された中途半端な状態になり得る（エラー表示は出るので気づける。再保存で直る）。
- **再現条件**: `POST /admin/settings` の複数キー保存中に接続断（`api/index.ts` の逐次 upsert ループ）。
- **修正方針**: ループを1トランザクション（または libsql batch）にまとめる。
- **想定規模**: 小〜中。**[Codexレビュー必須]**（DB書き込みの共通経路）。→ Q-3

### P2-2. ヒーロー/プロフィール画像を差し替えると旧画像が R2 に残り続ける

- **何が起きるか**: プロフィール写真などを差し替えるたびに、古い画像ファイルがストレージに永久に溜まる（表示は正常。費用と散らかりの問題）。
- **再現条件**: `/admin/hero/upload` `/admin/profile/upload` で差し替え。photos と違い DB 行が無いので purge 経路が存在しない。
- **修正方針**: 差し替え時に旧 URL のオブジェクトを削除（旧値が同じキー形式のときのみ）。削除は他参照が無い前提を確認してから。
- **想定規模**: 中。誤削除リスクがあるため **[Codexレビュー必須] [昼推奨]**。→ Q-4

### P2-3. `/admin/settings` が任意のキー名を受け付ける

- **何が起きるか**: 管理画面のバグや古いクライアントが変なキー名を送っても、そのまま DB に保存される（実害は薄いが、設定テーブルにゴミが溜まり調査を難しくする）。
- **修正方針**: `SETTINGS_PREVIEW_KEYS`（143キー台帳）+ 内部キーの許可リスト照合で弾く。台帳に無い正当キーが無いか先に洗うこと。
- **想定規模**: 小。ただし正当キーの取りこぼしがあると保存が壊れるため **[Codexレビュー必須]**。→ Q-5

### P2-4. 同時 purge で共有画像がまれにストレージへ残る（安全側のレース）

- **何が起きるか**: 複製関係にある2枚を同時に完全削除すると、互いに「相手がまだ使っている」と見えて画像ファイルが残ることがある（消えすぎる方向には倒れない=安全側）。
- **対応**: 仕様として許容。文書化のみ（本書が記録）。修正不要。

### P2-5. サムネイル一括生成（generate-thumbnails）の R2 取得にタイムアウト・リトライが無い

- **何が起きるか**: ストレージが一瞬詰まると、一括生成がその1枚で長時間止まる。通常の画像配信（getOriginal）には両方あるのに、この管理用経路だけ無い。
- **修正方針**: `getOriginal` と同じ `AbortSignal.timeout` + 1リトライを適用。
- **想定規模**: 小。→ Q-6

### P2-6. 画像の 304 応答に `Vary: Accept` が無い

- **何が起きるか**: 中間キャッシュが稀にブラウザごとの画像形式（AVIF/WebP）を取り違える理論的余地。実害は未観測。
- **修正方針**: 304 分岐にも 200 と同じ `Vary` を付ける（`fmt` 指定なしの場合のみ）。
- **想定規模**: 極小。→ Q-6（同梱）

### P3（記録のみ・対応不要）

- `PATCH /admin/photos/:id` に既知フィールドゼロの body → drizzle が throw → 500（現行クライアントは必ず1つ以上送る）
- 同一ファイル2枚の同時アップロードは重複検出をすり抜け得る（後から片方を削除すれば済む）
- categories 追加の sortOrder が「現在の件数」由来で、削除後に重複し得る（並べ替え保存で自然修復）
